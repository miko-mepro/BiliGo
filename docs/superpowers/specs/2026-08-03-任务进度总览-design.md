# BiliGO BugFix 任务进度总览设计

## 目标

在保留 `docs/修复方案/修复状态追踪.md` 的前提下，新增一份面向执行进度的快照文档 `docs/修复方案/任务进度总览.md`。

新文档根据阶段0至阶段4的方案范围、`Devlogs/` 的实际改动记录和状态追踪表重新统计任务进度，明确说明：

- 当前处于哪个阶段、哪个具体任务；
- 哪些任务已经完成代码或测试执行；
- 哪些任务仍停留在 `needs_review`，为什么不能算正式完成；
- 哪些任务尚未开始、被什么依赖阻塞、下一步应做什么。

## 文档职责

采用四类文档职责，其中前三类是进度汇总使用的事实来源：

| 文档 | 职责 | 权威范围 |
| --- | --- | --- |
| 阶段0至阶段4目录 | 定义计划范围、实施步骤、验收标准和依赖 | 计划内容 |
| `Devlogs/` | 记录实际改动、测试输出、偏离和遗留缺口 | 实际执行证据 |
| `修复状态追踪.md` | 维护正式状态、阻塞关系和状态变更规则 | 正式状态 |
| `任务进度总览.md` | 汇总当前快照，计算执行进度并指出当前位置 | 进度视图，不替代状态源 |

新文档不得把阶段方案中的示例代码、未勾选步骤或预期测试结果当作已完成证据。

## 统计口径

### 状态分类

| 分类 | 解释 | 是否计入正式完成 |
| --- | --- | --- |
| `completed` | 验收标准、代码审查和必要运行时验证均已达成 | 是 |
| `needs_review` | 实现或测试已经执行，但仍缺最终审查、运行时补验或阶段关闭 | 否，单独计入已执行待关闭 |
| `in_progress` | 正在实施，尚未达到待审查条件 | 否 |
| `pending` | 尚未开始 | 否 |
| `blocked` | 被硬依赖或无法解决的阻塞条件卡住 | 否，单独计入阻塞 |

### 统计对象

1. **核心问题任务**：11项已确认问题，按问题编号统计，不与阶段0和阶段4的基础设施工作混算。
2. **阶段工作**：阶段0至阶段4共5项，按阶段状态统计。
3. **阶段4专项任务**：独立统计7项测试覆盖缺口、8类E2E回归场景、5类跨域集成点和11项运行时假设。

### 当前已知统计

以当前仓库状态为快照：

- 核心问题正式完成 `0/11`；R-1、S-3为 `needs_review`，其余9项为 `pending`。
- 五阶段正式完成 `0/5`；阶段0、阶段1、阶段2为 `needs_review`，阶段3、阶段4为 `pending`。
- 阶段0、R-1、S-3均有实际执行记录，但运行时补验或最终复核尚未使其进入 `completed`。
- 阶段4的7项测试缺口、8类E2E回归、5类跨域集成和11项运行时假设尚未开始。

## 目标文档结构

`docs/修复方案/任务进度总览.md` 按以下顺序组织：

1. 快照日期、当前提交和文档职责声明；
2. 当前位置和一句话结论；
3. 全局数字摘要；
4. 阶段0至阶段4进度表；
5. 11个核心问题任务明细；
6. 阶段4专项任务明细；
7. 强依赖、软依赖、产品决策和运行时证据阻塞；
8. 下一步执行顺序；
9. 统计一致性检查结果。

阶段明细至少包含：计划范围、已执行内容、剩余验收、当前状态、证据来源和下一动作。

## 证据与一致性检查

生成进度文档后必须检查：

- 11个问题编号均出现且只归属于一个核心修复阶段；
- 阶段0至阶段4均有一行状态记录；
- 阶段4专项数量与方案目录一致：7、8、5、11；
- `needs_review` 不被计入正式完成率；
- R-1、S-3和阶段0的剩余缺口与对应Devlog一致；
- 当前定位与状态追踪中的依赖关系一致；
- 原 `修复状态追踪.md` 不被覆盖或改写。

## 范围约束

- 只新增进度快照文档，不修改源码、测试和原阶段方案。
- 不把进度快照当成正式状态源；正式状态仍以 `修复状态追踪.md` 为准。
- 不复制阶段方案全文，只保留统计所需的范围、证据、缺口和下一动作。
- 不修改与本任务无关的工作区变化。
