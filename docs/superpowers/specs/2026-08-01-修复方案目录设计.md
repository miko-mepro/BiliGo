# BiliGO BugFix 修复方案目录设计

## 目标

在现有 `docs/问题档案/` 之外新增 `docs/修复方案/`，将三份问题记录拆分为按执行阶段组织的多步修复方案。修复方案只描述实施步骤、依赖、测试和验收，不修改 `Main/` 源码、测试或原始问题记录。

## 选择的组织方式

采用按执行阶段组织、按问题编号落档的方式：

- `问题档案/` 负责按技术域保存调查结论和问题证据。
- `修复方案/` 负责按优先级和依赖关系安排实施顺序。
- 每份方案通过问题编号、来源文档和相对路径链接回问题档案。

按问题域直接复制目录虽然便于检索，但会隐藏 `S-3 -> S-4`、`N-1 -> N-4` 等执行依赖，因此不采用。

## 阶段划分

| 阶段 | 目标 | 包含内容 |
| --- | --- | --- |
| 阶段0 | 恢复验证能力 | E2E 扩展挂载阻塞、测试探针和运行时证据采集 |
| 阶段1 | 消除已确认的致命渲染入口 | R-1 历史标题类型校验 |
| 阶段2 | 处理核心可用性问题 | S-3 视频批次模型、S-4 排序优先级、N-2 聊天流总超时、S-2 自动滚动保护 |
| 阶段3 | 收敛中优先级体验和诊断问题 | S-1、N-1、N-4、N-3、R-2、R-3 |
| 阶段4 | 补齐回归验证 | 测试覆盖缺口、E2E 场景回归和跨域集成验证 |

## 依赖规则

- 阶段0应先恢复最小 E2E 启动能力，但不阻塞 R-1、N-2 等可由静态证据确认的修复。
- R-1 是 CRITICAL，应优先于常规体验优化完成。
- S-3 完成协议、状态和渲染层的批次归属后，S-4 才能定义最终排序行为。
- N-1 先定义统一错误分类，N-4 再接入 Bilibili 工具网络错误语义。
- N-3 与 R-3 共用 `TestConnectionButton` 状态管理，方案必须一起检查 listener、timer、取消和过期结果。
- 所有文档中的运行时验证只记录采集要求，不把尚未验证的现象写成已确认根因。

## 方案文档统一格式

每份问题方案包含：问题定位、修复目标、依赖关系、修改范围、分步执行、测试策略、验收标准、运行时验证、风险与回滚、完成状态。

## 范围约束

- 本次只新增 Markdown 方案文档。
- 不修改 `Main/` 源码和测试。
- 不移动、删除或重写 `docs/` 根目录的三份原始记录。
- 不修改工作区中与本任务无关的 `.gitignore`、`Docs/` 删除项、`Main/test-results/` 或未跟踪调查文档。
