# S-3 E2E 批次保留验证设计

## 目标

验证用户连续发起两次独立搜索后，第一次搜索的视频仍保留在页面中，第二次搜索的视频追加为新的批次，不再出现新结果直接覆盖旧结果的行为。

## 范围

- 只修改 `Main/e2e/agent-flow.spec.ts`。
- 复用现有扩展 fixture、`context.route`、AI SSE mock 和 B站搜索 mock。
- 不修改生产代码、协议、状态 reducer 或渲染组件。
- 本用例只验证两个搜索批次的保留，不声称覆盖 rerank 同批次复用或 insight 与视频锚点对齐。

## 测试数据流

1. 拦截 AI `/chat/completions` 请求：第一次和第三次请求返回两次不同的 `bilibili_search` tool call，第二次和第四次请求返回对应的最终文本。
2. 拦截 B站搜索接口：第一次返回批次 A 的两张视频卡，第二次返回批次 B 的两张不同视频卡。
3. 打开真实扩展面板，发送第一条搜索消息，等待批次 A 的两张卡片出现。
4. 等待第一轮流结束后发送第二条搜索消息，等待批次 B 的两张卡片出现。
5. 断言页面总计有四张卡片，且批次 A、批次 B 的唯一标题均存在。

## 验收标准

- AI mock 至少收到四次请求：两次工具调用和两次最终文本请求。
- B站搜索 mock 恰好收到两次请求。
- 第一次搜索的两张视频卡在第二次搜索完成后仍存在。
- 第二次搜索的两张视频卡在第二次搜索完成后存在。
- 用例不出现渲染错误边界。

## 失败解释

- 第二次搜索后只有两张卡片：说明视频数组仍被新批次替换，S-3 未满足。
- B站接口只收到一次请求：第二次消息未触发完整 Agent 搜索流程，不能据此判断批次模型。
- AI 请求未达到四次：mock 会话时序或发送按钮等待条件不满足，应先修正测试驱动链路。

## 后续验证边界

本用例通过后，只能证明两个独立搜索批次在真实扩展运行时共存。S-3 日志中记录的 rerank 批次策略、多批次数量上限和跨标签页同步仍需单独验证；S-4 是否解除还需遵守状态追踪文件的 `completed` 规则。
