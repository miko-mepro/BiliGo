# 高频点击不同按钮后渲染崩溃问题记录

## 记录范围

本记录只记录本次调查得到的证据、可疑代码路径和复现缺口，不修改 `Main/` 业务代码，也不把未经运行时确认的假设写成根因。

调查对象是 `Main/` 中的 React + Vite + Chrome MV3 扩展，重点关注历史下拉、设置页、连接测试、面板视图切换和错误边界。

调查时间：2026-08-01。

## 结论摘要

1. 已确认一个可在渲染阶段抛错的代码入口：历史记录标题不是字符串时，搜索过滤会调用 `r.title.toLowerCase()`，触发 `TypeError`。它可以被 `ErrorBoundary` 捕获并显示渲染异常，但目前没有证据证明“频繁点击按钮”会制造异常标题数据。
2. 历史重命名、删除、清空和连接测试都存在异步操作完成时机晚于视图切换的竞态。当前证据更支持“过期状态、错误结果覆盖或卸载后状态更新”，不能直接认定为渲染崩溃。
3. 现有 Playwright E2E 在 content script 挂载前失败，未执行任何目标按钮点击，因此没有获得用户现象对应的浏览器崩溃堆栈。
4. 面板历史下拉的 `useEffect` 提前返回目前不构成已确认的监听器泄漏：React 会先执行上一次 effect 的 cleanup，再执行新的 effect。该候选不应作为已确认根因记录。

## 已确认的渲染崩溃入口

### 历史标题类型未校验导致搜索渲染抛错

**证据位置：** `Main/src/components/HistoryDropdown.tsx:214-219`

```tsx
const filtered = searchQuery.trim()
  ? records.filter((r) =>
      r.title.toLowerCase().includes(searchQuery.trim().toLowerCase()),
    )
  : records
```

数据流如下：

1. `HistoryDropdown` 的 `getIndex()` 返回值在 `Main/src/components/HistoryDropdown.tsx:94-98` 被直接保存到 `records`。
2. `Main/src/lib/history/store.ts:59-65` 只判断存储值是否为数组，随后将数组强制转换为 `ConversationRecord[]`，没有逐条校验 `id`、`title` 和时间字段。
3. `Main/src/lib/history/sync.ts:52-56` 对跨标签页同步数据也只判断是否为数组，再直接回调给组件。
4. 搜索框输入任意非空字符后，组件 render 期间执行 `r.title.toLowerCase()`。
5. 若历史索引中存在 `title: null`、数字、对象或缺失字段，render 会抛出 `TypeError`。

这是当前唯一通过静态代码审查确认的“render 阶段直接抛异常”路径。`Main/src/content/error-boundary.tsx:36-68` 可以捕获这类 render 错误并显示“BiliAgent 渲染异常”，但它不会修复数据，也不会捕获按钮事件处理器内部的同步异常。

**最小复现条件：**

1. 让 `bili-agent-history-index` 存在数组元素，但至少一条记录的 `title` 不是字符串。
2. 打开面板并展开历史下拉。
3. 在“搜索历史记录”输入框中输入至少一个非空字符。
4. 观察控制台 `TypeError` 和错误边界 UI。

**与按钮快速点击现象的关系：**

当前没有证据证明按钮点击会写入这种异常标题。正常写入路径 `Main/src/lib/history/store.ts:97-104` 使用字符串 `tempTitle` 或已有字符串标题。因此该问题应标记为“真实崩溃入口，触发来源待确认”，不能直接写成快速点击的最终根因。

## 高风险交互竞态，但尚未证实为渲染崩溃

### 历史重命名完成晚于视图卸载

**证据位置：** `Main/src/components/HistoryDropdown.tsx:172-194`

`handleRenameConfirm` 在 `await onRename(id, newTitle)` 返回后才执行 `setRecords`，并在 `finally` 中执行 `setEditing(null)` 和 `editingRef.current = false`。而 `Panel` 在 `Main/src/components/Panel.tsx:608-631` 会在切换到设置视图时不再渲染 `HistoryDropdown`。

可能的时序：

1. 在历史下拉中进入重命名并确认。
2. `onRename` 尚未返回时点击设置按钮。
3. `HistoryDropdown` 因 `!isSettingsOpen` 条件改变而卸载。
4. 异步操作返回后，旧闭包仍执行状态更新和 ref 写入。

这会产生过期结果或卸载后的状态更新风险。当前 React 运行时通常会忽略卸载组件的 `setState`，并没有证据表明此处必然触发 render crash；`editingRef` 的写入也更接近逻辑状态竞态，而不是渲染异常。

### 连接测试结果可能覆盖新的 Provider 状态

**证据位置：** `Main/src/components/model-settings/TestConnectionButton.tsx:115-189`

连接测试使用 `Promise.race` 等待 service worker 响应或 12 秒超时。Provider 变化或组件卸载时，现有 cleanup 只移除 listener 和 timer，没有取消已经创建的 Promise。若用户在等待期间切换 Provider 或离开设置页，旧请求仍可能在 `:175-185` 完成并调用 `setStatus`、`setErrorMessage`、`setIsTimeout`。

当前可确认的影响是：旧 Provider 的结果可能覆盖新 Provider 的 UI 状态，或者在视图切换后产生无效状态更新。尚无运行时堆栈证明该路径直接导致 render crash。

### 历史同步数据和数组排序存在数据完整性风险

**证据位置：**

- `Main/src/components/HistoryDropdown.tsx:97`
- `Main/src/components/HistoryDropdown.tsx:120`
- `Main/src/lib/history/sync.ts:52-56`

组件对 `fetchedRecords` 和 `newIndex` 原地调用 `.sort()`。如果未来调用方传入冻结数组，排序会抛出异常；但当前存储 API 返回的数组是否被冻结尚未被运行时证明，因此这里只记录为低置信度风险，不作为本次崩溃根因。

## 已排除或暂不成立的候选

### 历史下拉外部点击监听器泄漏

**代码位置：** `Main/src/components/Panel.tsx:351-371`

effect 在 `!isHistoryOpen || isSettingsOpen` 时提前返回，但当依赖变化导致 effect 重新执行时，React 会先调用上一轮 effect 返回的 `removeEventListener` cleanup，再执行新 effect。当前代码不能据此证明监听器累积。

快速执行“展开历史 -> 设置 -> 聊天”仍值得加入运行时检查，但不能将“early return 导致 cleanup 被跳过”写入问题结论。

### 设置 Port 与聊天 Port 短暂并存

**代码位置：** `Main/src/components/Panel.tsx:425-445`、`:634-657`

设置分支和聊天分支互斥渲染，设置 Port 在设置视图关闭时执行 `disconnect`。当前静态代码未证明两个视图会同时渲染导致 React render crash；若出现问题，更可能表现为 Port 断开、请求无响应或连接测试超时。

### 拖拽阈值与外部点击竞态

`App.tsx:60-83` 使用 `composedPath()` 判断点击是否位于面板内，`useDraggable` 的 5px 阈值只在拖拽开始后设置交互状态。面板内部的手柄和按钮仍会出现在 composed path 中，当前没有发现可确认的渲染崩溃链路。

## 实际运行证据

### 构建

测试代理执行 `cd Main && npm run build` 成功，Vite 构建完成。仅出现 chunk 大小警告，没有编译错误。

### Playwright E2E

测试代理先安装了缺失的 Chromium，然后执行了目标 smoke 测试。测试在 `Main/e2e/fixtures/extension-harness.ts:85-87` 等待 `[data-bili-agent-toggle]` 时失败，未进入打开面板和按钮交互阶段。

诊断文件 `Main/test-results/smoke-BiliGo-panel-UX-no-b-a381c-e-edge-and-expands-on-hover-chromium-extension/error-context.md:15-23` 记录：

```text
Error: Channel closed
Error: page.goto: Target page, context or browser has been closed
```

因此本次没有获得以下目标证据：

- 点击顺序和点击间隔；
- React 错误边界文案；
- 浏览器控制台中的 render stack；
- 事件处理器异常或 `Maximum call stack size exceeded`；
- 目标点击序列期间的网络/Port 时间线。

当前稳定复现的只是 E2E 前置失败：扩展页面在限定时间内没有出现 `[data-bili-agent-toggle]`。这可能是扩展注入、测试页面、浏览器上下文关闭或 service worker 启动问题，不能等同于用户描述的按钮渲染崩溃。

## 建议的后续复现记录

本次按用户要求只记录问题，不实现修复。下一次复现应至少记录：

1. 页面 URL、面板初始状态和完整点击序列，例如“展开历史 -> 设置 -> 返回聊天 -> 新建对话 -> 测试连接”。
2. 每次点击之间的间隔，以及是否在异步 loading、重命名确认或连接测试期间切换视图。
3. DevTools Console 中的完整第一条异常和调用栈，不要只记录最后的 ErrorBoundary 文案。
4. `bili-agent-history-index` 的字段形状，尤其是 `title` 的运行时类型；不要记录 API Key 或 Cookie。
5. service worker 和 Port 的连接/断开时间，区分 UI render crash、Port 断线和请求超时。
6. 单独验证异常历史记录 + 非空搜索，因为这是目前已确认的 render crash 最小入口。
