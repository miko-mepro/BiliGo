## 问题描述
stream.ts 在消费 AI SDK 流的 tool-result 事件时，先调用 postToolAuxiliaryMessages，再推送 tool_result。bilibili_search 输出转换为 `{ type: 'videos', videos: ... }`；理解、查询扩展、重排和澄清结果转换为 insight 消息。协议允许 videos 和 insight 作为独立 UI 消息传递。因此工具辅助 UI 消息不等待最终 tool_result 或整段文本结束，就先进入 content script。

## 根因分析
问题的核心在于流式推送时序与 UI 状态切分的不一致。

1. **后端推送时序**：stream.ts 在消费 AI SDK 流的 tool-result 事件时，先调用 `postToolAuxiliaryMessages`，再推送 `tool_result`。bilibili_search 输出转换为 `{ type: 'videos', videos: ... }`；理解、查询扩展、重排和澄清结果转换为 insight 消息。协议允许 videos 和 insight 作为独立 UI 消息传递。因此工具辅助 UI 消息不等待最终 tool_result 或整段文本结束，就先进入 content script。

2. **前端状态切分**：MessageList 从 context 读取视频和 insight，把消息和 understanding、expansion、rerank insight 合并后按时间排序；有视频时展示 `FilterSortControls` 和 `bili-agent-video-grid`。搜索工具的辅助结果不是作为同一个"搜索输出块"写入消息，而是分成三类状态：
   - 视频结果进入单独的 `state.videos`
   - understanding、expansion、rerank 进入独立 insight 数组
   - tool_result 只更新工具步骤完成状态，不为视频数组建立消息锚点

3. **协议层允许独立传递**：port-protocol.ts:6-17 允许 videos 和 insight 作为独立 UI 消息传递，没有强制要求它们与 tool_result 绑定或等待工具完成。

4. **chat-context 派发路径**：chat-context.tsx:389-459 接收到这些消息后会分别派发到不同的 state 字段（videos、insight 等），进一步强化了"分块即时展示"的行为。

关键代码片段（stream.ts:182-220 区域逻辑）：
```typescript
// 先推送辅助消息（视频/insight）
await postToolAuxiliaryMessages(...)
// 再推送 tool_result
port.postMessage({ type: 'tool_result', ... })
```

## 影响范围
- **用户体验影响**："Search 过程中多个 UI 区域立即变化"是当前实现可以静态确认的行为。在单次搜索过程中，用户可能依次看到：
  - understanding insight 卡片先出现
  - expansion insight 卡片出现
  - 视频网格出现
  - rerank insight 卡片出现
  - 最终 tool_result 完成状态更新
  这一系列分散的 UI 变化可能造成视觉跳动和认知负担。但浏览器实际是否出现用户看到的特定渲染顺序、闪烁或视觉跳动，还需要运行时录制确认。
- **技术债务影响**：辅助消息与 tool_result 解耦，使得"搜索完成"这一语义边界在 UI 层面没有明确锚点，后续若要实现"工具进行中"与"工具完成"两阶段差异化展示，需要重构当前的三状态切分模型。
- **与其他问题的关联**：
  - 与 S-2 关联：即时展示的多次状态更新会触发 MessageList 的自动滚动 effect（依赖 renderItems、videos 等），加重自动滚动问题。
  - 与 S-3 关联：rerank insight 的即时展示与视频数组的即时推送存在时序耦合，影响重排顺序的可见性。

## 复现路径（如有）
1. 触发一次包含 bilibili_search 工具调用的对话
2. 观察搜索过程中 UI 区域的变化顺序
3. 注意 understanding、expansion、视频网格、rerank insight 是否在 tool_result 完成前就已展示
4. 如需精确确认视觉跳动，需在浏览器中录制屏幕并逐帧分析

## 待验证假设（如有）
- 假设1：浏览器实际渲染中，多个 insight 卡片和视频网格的出现顺序与后端推送顺序一致（需运行时录制确认）
- 假设2：视觉跳动感知主要来自视频网格与 insight 卡片的布局重排（需用户测试确认）

## 建议的修复方向
考虑将辅助消息与 tool_result 时序对齐，或提供"工具进行中"与"工具完成"两个阶段的差异化展示：
1. **方案A（时序对齐）**：将 videos 和 insight 辅助消息缓存，等到 tool_result 推送时一并下发，确保"搜索输出块"作为一个整体进入 UI。
2. **方案B（两阶段展示）**：保留即时展示，但在 UI 层引入"工具进行中"占位状态，辅助内容以低强调度（如半透明、折叠）展示，待 tool_result 完成后切换为正式展示状态。
3. **方案C（语义锚点）**：为视频数组建立消息锚点，将 tool_result 与视频消息关联，使 UI 能识别"搜索输出块"的边界。
