# S-4 客户端排序覆盖后端重排

## 基本信息
- **严重程度**: HIGH
- **问题类型**: 排序逻辑/数据展示
- **确认状态**: 已确认
- **来源文档**: 搜索结果展示与重排问题记录.md
- **发现日期**: 2026-08-01
- **关联问题**: S-3

## 问题描述
后端 video_rerank 的数组重排可由 service worker 测试确认；但 MessageList 默认 sortField 为 'play'，applySortAndFilter 会覆盖输入数组顺序。

## 代码位置
- `Main/src/components/MessageList.tsx:44-61`
- `Main/src/components/MessageList.tsx:172-177`
- `Main/src/utils/sort-filter.ts:32-57`
- `Main/src/utils/sort-filter.ts:110-117`
- `Main/src/background/stream.ts:200-212`
- `Main/src/background/stream.ts:257-287`

## 根因分析
问题由两个独立但叠加的路径构成：后端重排确实存在且生效，但客户端默认排序会在 DOM 渲染前覆盖重排顺序。

### 后端重排已确认存在（stream.ts:200-212）

1. stream.ts:203 先推送 insight(rerank)
2. :207 从 tool input 提取原始候选视频
3. :209 调用 `reorderVideosByRerank(candidates, rerankResult.items)`
4. :210 推送 `{ type: 'videos', videos: reordered }`

`reorderVideosByRerank` 按 rerankItems 的 bvid 顺序取卡片，再把未涉及的候选按原序追加。现有测试验证：输入 `[BV1, BV2, BV3]`，重排结果为 BV2、BV1、BV3 时，推送的视频消息顺序也是 BV2、BV1、BV3。

关键代码片段：
```typescript
// stream.ts:203-210
await postInsight({ kind: 'rerank', ... });      // 先推送 rerank insight
const candidates = extractCandidates(toolInput); // 提取原始候选
const reordered = reorderVideosByRerank(          // 按重排结果重排
  candidates,
  rerankResult.items
);
port.postMessage({ type: 'videos', videos: reordered }); // 推送重排后数组
```

### 客户端最终顺序覆盖路径

1. **MessageList.tsx:44-47** 默认 sortField 是 `'play'`
2. **MessageList.tsx:58-61** 对视频调用 `applySortAndFilter`
3. **sort-filter.ts:32-57** 的 `sortVideos` 会复制数组并按所选字段降序排序
4. **sort-filter.ts:110-117** 明确先过滤、再排序
5. **MessageList.tsx:172-177** 渲染的是 `processedVideos`，不是未经处理的 `state.videos`

关键代码片段：
```typescript
// MessageList.tsx:44-47
const [sortField, setSortField] = useState<SortField>('play');

// MessageList.tsx:58-61
const processedVideos = useMemo(
  () => applySortAndFilter(videos, sortField, dateFilter, durationFilter),
  [videos, sortField, dateFilter, durationFilter]
);

// sort-filter.ts:32-57
function sortVideos(videos: Video[], field: SortField): Video[] {
  return [...videos].sort((a, b) => /* 按字段降序 */);
}
```

### 排序重置的叠加影响

此外，**MessageList.tsx:49-56** 在 videos 数组引用变化时将 sortField、日期筛选和时长筛选重置为默认值。video_rerank 的第二次 videos 推送会产生新的数组引用，因此它不仅可能覆盖重排顺序，还会把用户此前选择的客户端排序恢复为播放量排序。

```typescript
// MessageList.tsx:49-56
useEffect(() => {
  setSortField('play');        // 重置为播放量排序
  setDateFilter('all');       // 重置日期筛选
  setDurationFilter('all');   // 重置时长筛选
}, [videos]);                  // videos 引用变化即触发
```

### AgentInsightCard 不参与顺序

AgentInsightCard 的 rerank body 只展示策略、裁剪数量和保留结果数量，不读取 bvid 顺序，也不参与 processedVideos 计算。因此 insight 卡片对实际视频顺序没有任何约束作用。

## 影响范围
- **用户体验影响**：
  - 当重排顺序与播放量顺序不一致时，后端送来的重排顺序会在最终 DOM 渲染前被播放量排序覆盖。只有当两种顺序恰好一致时，用户才会看到看似生效的重排。
  - 用户在 rerank 触发前手动选择的客户端排序（如按最新、按时长）会被重置为默认的播放量排序，造成"我的选择丢失"的困惑。
  - 用户无法感知后端重排是否真的生效，因为 UI 上看到的一定是播放量降序，除非两种顺序恰好一致。
- **技术债务影响**：
  - 后端重排与客户端排序存在职责冲突：后端投入计算成本进行语义重排，但结果被前端默认排序静默丢弃。
  - 排序重置逻辑（MessageList.tsx:49-56）与 rerank 的二次推送耦合，是隐性的副作用，难以维护。
  - 缺少"重排顺序优先"或"保持原序"的排序选项，使得后端重排结果无法在 UI 层被显式保留。
- **与其他问题的关联**：
  - 与 S-3 关联：S-3 涉及 rerank 相关的时序与状态问题，本问题的排序覆盖会进一步放大 rerank 结果的可见性缺陷。

## 复现路径（如有）
1. 触发一次包含 video_rerank 工具调用的搜索
2. 构造重排顺序与播放量降序不一致的场景（如 rerank 将低播放量视频排前）
3. 观察 DOM 中视频卡片的实际渲染顺序
4. 预期结果：渲染顺序为播放量降序，而非 rerank 的重排顺序
5. 变体：在 rerank 触发前手动选择"按最新"排序，触发 rerank 后观察 sortField 是否被重置为 'play'

## 待验证假设（如有）
- 假设1：当 sortField 为某个特殊值（如可能存在的 'default' 或 'rerank' 选项）时，客户端不会覆盖重排顺序（需确认 SortField 类型定义是否包含此类选项）
- 假设2：rerank 的第二次 videos 推送与首次 videos 推送之间，用户若快速切换 sortField，可能在 effect 重置前看到短暂的原始重排顺序（需运行时确认时序窗口）

## 建议的修复方向
定义 rerank 与客户端排序的优先级策略：
1. **方案A（rerank 跳过默认排序）**：rerank 后推送的视频数组标记为 `reranked: true`，MessageList 检测到此标记时跳过默认的 'play' 排序，直接渲染原始顺序。
2. **方案B（增加"保持重排顺序"选项）**：在 SortField 中增加 `'rerank'` 选项作为可选项，用户可显式选择保留后端重排顺序；rerank 触发时自动切换到此选项而非重置为 'play'。
3. **方案C（分离重排与用户排序）**：将 rerank 顺序作为"基础顺序"，用户排序作为"叠加视图"，提供切换开关；排序重置逻辑不再在 videos 引用变化时触发，改为仅在显式新搜索时触发。
4. **方案D（取消排序重置）**：移除 MessageList.tsx:49-56 的排序重置 effect，避免 rerank 二次推送静默重置用户选择；新搜索的重置改由搜索会话边界显式管理。
