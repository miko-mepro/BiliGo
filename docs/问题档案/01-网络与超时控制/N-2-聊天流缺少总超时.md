# [N-2] 聊天流缺少总超时

## 基本信息
- **严重程度**: HIGH
- **问题类型**: 超时控制缺失
- **确认状态**: 已由代码静态确认"聊天流缺少独立总超时"；尚未确认用户所述偶发错误是否由该场景触发
- **来源文档**: 网络连接错误问题记录.md
- **发现日期**: 2026-08-01
- **关联问题**: N-3

## 问题描述
`streamText` 调用创建了手动 `AbortController` 并传给 `streamText`，但该调用没有像连接测试（10 秒）和标题生成（10 秒）那样设置 `AbortSignal.timeout(...)`。

经审计，仓库中 `AbortSignal.timeout` 的调用位置包含：

- 标题生成：10 秒
- 连接测试：10 秒
- Bilibili 请求：10 秒
- 工具 / 视觉请求：30 秒

但没有聊天 `streamText` 的总超时。这意味着如果上游 AI 请求既不返回数据也不主动抛错，聊天可能长期保持等待状态。

## 代码位置
- `Main/src/background/stream.ts:315-329`（聊天流式请求入口，创建手动 AbortController 但未设置总超时）

## 根因分析
`stream.ts` 在创建聊天流时，手动构造了 `AbortController` 用于中断控制：

```ts
// stream.ts 关键逻辑示意
const controller = new AbortController();
await streamText({
  signal: controller.signal,  // 仅传入手动 controller，未结合 timeout
  // ...
});
```

与之对比，连接测试、标题生成、Bilibili 请求与工具 / 视觉请求均显式使用 `AbortSignal.timeout(...)` 或将其与手动 controller 合并。聊天流是唯一未接入总超时的请求路径。

进一步需要注意的是，Port 心跳只检测 content script 与 service worker 通道是否存活，并不能证明上游 AI 请求仍在推进。因此即便心跳正常，上游也可能已经卡死，而前端却没有总超时兜底。心跳不能替代流请求的超时。

## 影响范围
- **用户体验影响**：如果上游请求既不返回数据也不主动抛错，聊天可能长期保持等待状态。用户表现为"发出去就转圈不回来"，无任何错误提示，也无法自行判断应该重试还是继续等待。
- **技术债务影响**：聊天流是核心路径却唯一缺少总超时，属于超时控制债务的集中点；未来若上游变更引入新的卡死模式，聊天流将首当其冲。
- **与其他问题的关联**：与 N-3（设置 Port 无断线检测）共享"断线/卡死反馈延迟"这一主题，但二者机制不同——N-3 解决通道断开反馈，N-2 解决上游卡死超时。

## 复现路径（如有）
1. 配置一个会"挂起但不返回也不抛错"的上游端点（例如 mock 一个永不结束的 SSE 流）。
2. 在聊天框发送一条消息。
3. 观察聊天是否长期保持等待状态，且没有任何超时兜底。
4. 对比连接测试与标题生成路径，验证它们能在 10 秒后触发超时。

## 待验证假设（如有）
- 假设1：用户所述"偶发网络连接失败""连接超时"实际由聊天流卡死引起，但因无超时兜底，最终由其他机制（如 Port 心跳或浏览器层关闭）触发反馈。需要运行时日志确认聊天流卡死时长与最终反馈路径。
- 假设2：上游 AI 请求在部分网络条件下会静默挂起而非抛错，导致 `streamText` 永不 resolve。需要抓取该场景的请求生命周期。

## 建议的修复方向
为聊天流式请求添加独立的总超时（`AbortSignal.timeout` 或类似机制），超时后终止流并发送错误：

1. 在聊天 `streamText` 入口处引入总超时信号，与现有手动 `AbortController` 通过 `AbortSignal.any([...])` 合并。
2. 超时阈值需平衡响应速度与长回复容忍度，可参考工具/视觉请求的 30 秒但考虑流式场景适当放宽。
3. 超时后主动 `controller.abort()`，并通过现有错误转发路径向 UI 发送"连接超时"类文案，而非静默等待。
4. 在超时触发时记录上游卡死时长，便于后续与用户偶发反馈对齐。

修复仅描述思路，不包含具体实现代码。
