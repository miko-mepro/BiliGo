## 问题描述
由 `generateText` 抛出的、未被识别为 401/403 或 429 的异常，会经过 `inferErrorCode` 归类为 `NETWORK_ERROR`，UI 通常显示"网络连接失败"。但配置校验失败会直接返回校验错误，`createModel` 在 try 外抛出时由路由层返回原始错误，Port 发送成功后没有结果则由前端显示"连接超时"。

这导致不同根因的错误文案彼此混淆：网络问题、鉴权失败、配置错误、模型不存在等场景，用户看到的提示可能只是笼统的"网络连接失败"，而无法据此判断应该检查网络、API Key、Base URL 还是模型名。

- `Main/src/background/port-protocol.ts:96-132`（inferErrorCode 错误分类逻辑）
- `Main/src/background/stream.ts:514-557`（错误转发与 UI 呈现路径）

## 根因分析
`inferErrorCode` 是连接测试与聊天流的错误归类入口。当前实现仅识别三类 HTTP 状态码：

```ts
// port-protocol.ts 关键逻辑示意
if (status === 401 || status === 403) return 'AUTH_ERROR';
if (status === 429) return 'RATE_LIMIT';
return 'NETWORK_ERROR';  // 其余异常一律归为网络错误
```

这种粗粒度分类把多种本质不同的失败合并到同一文案下：

1. **DNS/TLS/超时**：真正的网络层失败，归为 `NETWORK_ERROR` 合理。
2. **鉴权失败（401/403）**：被单独识别为 `AUTH_ERROR`，提示正确。
3. **限流（429）**：被单独识别为 `RATE_LIMIT`，提示正确。
4. **配置校验失败**：在更早的环节直接返回校验错误，不经 `inferErrorCode`，文案与网络错误完全不同。
5. **`createModel` 抛出（非 try 内）**：由路由层返回原始错误，文案不可控。
6. **Port 发送成功但无结果**：前端展示"连接超时"，与上述路径文案又不同。

因此，仅凭 UI 显示的文案无法单独确定根因。"网络连接失败"既可能是真网络问题，也可能是被归入 `NETWORK_ERROR` 的其他未识别异常。

## 影响范围
- **用户体验影响**：部分用户只能看到"网络连接失败"，无法判断应该检查网络、API Key、Base URL 或模型名；而另一些路径显示"连接超时""连接已断开"或原始错误。错误文案不足以单独确定根因，增加排查成本。
- **技术债务影响**：错误分类缺乏统一出口，新增错误类型时容易再次被吞入 `NETWORK_ERROR`，形成文案债务。
- **与其他问题的关联**：与 N-4（Bilibili 工具网络失败语义不一致）共享同一错误归类出口，Bilibili 网络失败在另一条路径上被展示为"工具执行失败"而非"网络连接失败"，语义割裂。

## 待验证假设（如有）
- 假设1：用户报告中"偶发网络连接失败"实际包含未被识别为 401/403/429 的鉴权或限流变体。需要运行时日志确认 `inferErrorCode` 实际命中的分支分布。
- 假设2：`createModel` 在 try 外抛出的错误，部分情况下 message 中包含可识别的鉴权关键字，但因未经 `inferErrorCode` 而丢失语义。需要抓取该路径的原始错误对象。

## 建议的修复方向
细化 `inferErrorCode` 的错误分类，区分 DNS/TLS/超时/鉴权/配置等不同根因，提供差异化错误文案：

1. 在 `inferErrorCode` 中扩展对错误对象字段（如 `cause`、`code`、`errno`）的识别，将 DNS、TLS、连接超时等区分开。
2. 对 `createModel` 在 try 外抛出的错误也接入 `inferErrorCode`，保证所有路径经过统一分类出口。
3. 为每个错误类型提供独立的用户文案，而非统一"网络连接失败"。
4. 在日志侧记录 `inferErrorCode` 实际命中的分类，便于后续统计触发分布。

修复仅描述思路，不包含具体实现代码。
