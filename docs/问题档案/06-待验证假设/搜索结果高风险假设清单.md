# 搜索结果高风险假设清单

## 基本信息
- **来源文档**: 搜索结果展示与重排问题记录.md
- **发现日期**: 2026-08-01
- **假设总数**: 5项

本文档列出搜索结果展示与重排问题中尚未被证据确认的高风险假设。这些问题表现为用户在连续搜索和流式输出过程中看到视频卡片闪烁、滚动跳动和语义错配，但当前缺少 DOM 顺序记录、滚动位置记录和消息时间线记录，无法定位是后端推送顺序、客户端渲染顺序还是滚动行为导致的。以下假设按从数据层到交互层的顺序排列，每项假设给出验证方法、所需证据和当前状态。所有假设在获得证据前均为待验证状态。

## 假设清单

### S-V1: 多次搜索时旧 insight 与最新视频列表之间产生的语义错配
- **验证方法**: 在同一对话内发起两次搜索，记录第一次搜索的 insight 文案与第二次搜索返回的视频列表是否在 DOM 中产生错配。
- **所需证据**: 两次搜索返回的视频 bvid 顺序、insight 文案内容以及它们在 DOM 中的相对位置。
- **状态**: 待验证
- **说明**: 当用户发起第二次搜索时，新的视频数组会被推送到消息列表，但第一次搜索的 insight 卡片是否仍然保留在原位置，以及它下方是否挂载了新的视频数组，决定了语义是否一致。如果旧 insight 与新视频在 DOM 中相邻，用户会看到文案与视频内容不匹配的现象。

### S-V2: 视频推送造成的滚动动画叠加和用户可见闪烁
- **验证方法**: 在流式输出过程中记录 `scrollIntoView` 的调用次数和最终 `scrollTop`，判断滚动动画是否叠加。
- **所需证据**: 单次流式输出期间 `scrollIntoView` 调用次数、每次调用时的 `scrollTop` 值以及用户可见的闪烁记录。
- **状态**: 待验证
- **说明**: 流式输出过程中每个 chunk、每段 reasoning、每次视频数组更新都可能触发一次 `scrollIntoView`，多次滚动动画叠加会造成用户可见的闪烁和跳动。这一假设与测试覆盖缺口中的缺口2对应，需要通过滚动次数统计验证。

### S-V3: 浏览器实际渲染顺序与代码预期的一致性
- **验证方法**: 记录每条消息、视频数组和 insight 卡片在 DOM 中的相对位置，确认视频网格是否始终位于整个消息列表末尾。
- **所需证据**: DOM 中消息节点、视频网格节点和 insight 卡片节点的相对位置快照。
- **状态**: 待验证
- **说明**: 代码预期视频网格始终位于消息列表末尾，但浏览器实际渲染顺序可能因为 React 重渲染时机、异步更新批量处理或 DOM 操作顺序而与预期不一致。需要通过 DOM 快照确认实际顺序，而非仅依赖代码逻辑推断。

### S-V4: 某次具体搜索中 video_rerank 是否因为候选字段不完整而跳过了重排视频推送
- **验证方法**: 在具体搜索中记录 `stream.ts:233-247` 的过滤行为，确认是否因为候选缺少 `bvid` 或 `title` 而跳过了第二组视频推送。
- **所需证据**: rerank 输入的候选字段完整性和 `stream.ts:233-247` 的过滤结果记录。
- **状态**: 待验证
- **说明**: `stream.ts:233-247` 会过滤缺少 `bvid` 或 `title` 的候选，如果某次搜索返回的候选全部不完整，则不会推送第二组视频，用户只会看到第一组搜索结果而不会看到 rerank 后的顺序。这一行为可能导致用户误以为 rerank 失效，而实际是字段不完整导致跳过。需要通过候选字段记录确认是否真的跳过了重排推送。

### S-V5: service worker 和 content script 消息到达间隔是否造成额外的闪烁或滚动竞态
- **验证方法**: 在 DevTools 中记录每次 `videos`、`insight`、`chunk`、`reasoning` 和 `done` 消息的相对顺序与时间，判断消息到达间隔是否触发额外的渲染或滚动。
- **所需证据**: 各类消息的到达时间戳和相对顺序记录（不记录 API Key、Cookie 或完整请求凭据）。
- **状态**: 待验证
- **说明**: service worker 向 content script 推送消息时，如果 `videos` 和 `insight` 消息到达间隔较长，content script 可能先渲染视频后渲染 insight，或反之，导致中间状态被用户看到。此外 `chunk` 和 `reasoning` 消息穿插在视频推送之间时，可能触发额外的滚动和重渲染，造成闪烁。需要通过消息时间线记录确认到达间隔的影响。

## 后续最小复现证据

以下证据是复现搜索结果展示与重排问题并定位根因的最小集合，采集时注意不记录 API Key、Cookie 或完整请求凭据：

1. **记录完整对话序列**：第一次搜索、展开某个 insight、手动上拉、第二次搜索，以及每次操作发生时是否仍在流式输出。对话序列决定了问题出现的上下文，是判断假设 S-V1 和 S-V2 的前提。
2. **在 DevTools 中记录每次 videos、insight、chunk、reasoning 和 done 消息的相对顺序与时间**：不记录 API Key、Cookie 或完整请求凭据。消息顺序和时间用于验证假设 S-V5，判断消息到达间隔是否造成渲染竞态。
3. **记录两次搜索返回的视频 bvid 顺序、播放量顺序和 rerank items 顺序**：判断后端重排是否与客户端默认播放量排序冲突，对应测试覆盖缺口中的缺口6。如果 rerank 顺序与播放量降序不一致，需要确认客户端展示的是哪一种。
4. **记录用户手动上拉时的滚动位置、scrollIntoView 调用次数和最终 scrollTop**：区分代码触发的滚动与浏览器平滑滚动动画，对应假设 S-V2。如果 `scrollIntoView` 调用次数过高且最终 `scrollTop` 频繁变化，可以确认滚动叠加是闪烁的根因。
5. **记录每条消息、视频数组和 insight 卡片在 DOM 中的相对位置**：确认视频网格是否始终位于整个消息列表末尾，对应假设 S-V3。DOM 快照是验证浏览器实际渲染顺序的直接证据，比代码逻辑推断更可靠。
6. **单独运行包含 MessageList 的测试或补充针对性测试**：验证流式更新、搜索批次、客户端排序覆盖和最终卡片顺序，对应测试覆盖缺口中的缺口5。端到端串联测试可以确认 rerank 数组经过 reducer 和渲染层后顺序是否保持一致。
