# 06-待验证假设

## 分类说明

本类收集所有需要运行时证据才能确认的假设，不能仅凭静态代码分析确定。三份原始问题记录文档在调查过程中均明确区分了"已确认的代码问题"和"待验证的假设"，后者虽然基于代码分析提出，但其触发条件、实际表现或最终根因需要浏览器运行时证据、DOM 录制或用户操作时间线才能确认。

本类不收录已确认的代码缺陷，而是收录假设清单，作为后续复现和验证的指引。每个假设均标注来源文档和验证所需的最小证据。

## 共性问题特征

### 特征一：静态代码确认行为，但无法确认触发场景

N-V1 到 N-V6 的网络层假设均属于此类：代码分析可以确认链路逻辑和错误处理路径，但无法确认用户实际遇到的偶发错误对应哪条链路、哪个 Provider、哪种错误类型。需要运行时日志区分设置页连接测试与聊天发送，区分 DNS 错误、TLS 错误、HTTP 状态码错误和请求超时。

### 特征二：静态代码确认数据流，但无法确认浏览器实际渲染表现

S-V1 到 S-V5 的搜索 UI 假设均属于此类：代码分析可以确认消息推送时机、状态替换逻辑和排序覆盖行为，但无法确认浏览器中实际的视觉表现。用户报告的"闪动""顶掉""重排未生效"可能由多种因素叠加造成，包括：

- service worker 和 content script 消息到达间隔造成的闪烁或滚动竞态。
- CSS 动画或虚拟 DOM diff 造成的视觉效果。
- 多次搜索时旧 insight 与最新视频列表之间的语义错配。

这些需要 DOM 录制、消息时间线和 `scrollIntoView` 调用次数等运行时证据才能确认。

### 特征三：假设不等于根因，不能直接写入修复计划

原始文档强调：这些假设"不能仅凭当前静态代码判定为最终根因"。任何修复计划在实施前应先验证对应假设，确认触发场景和实际表现后再设计修复方案。直接基于假设实施修复可能导致：

- 修复了非实际触发路径，问题仍然存在。
- 引入不必要的复杂度，解决实际不存在的问题。
- 遗漏真正的根因，因为假设可能与其他问题关联。

## 验证方向参考

- 优先解决 E2E 阻塞问题（见 `05-测试与验证缺口`），恢复运行时验证能力。
- 后续复现时按原始文档记录的"后续复现所需最小证据"采集非敏感信息，不记录 API Key、Cookie 或完整请求凭据。
- 验证网络层假设（N-V1 到 N-V6）时，重点记录发生时间、Provider 类型、Base URL、模型名、错误文案和耗时，区分设置页连接测试与聊天发送。
- 验证搜索 UI 假设（S-V1 到 S-V5）时，重点记录完整对话序列、消息相对顺序与时间、视频 `bvid` 顺序和 `scrollIntoView` 调用次数。
- 任何假设被运行时证据确认后，应将其从本类移至对应的已确认问题分类，并更新总索引 README 的统计表。
