# 网络层待验证假设清单

## 基本信息
- **来源文档**: 网络连接错误问题记录.md
- **发现日期**: 2026-08-01
- **假设总数**: 6项

本文档列出网络连接错误问题中尚未被证据确认的假设。网络层错误的表现为用户在设置页连接测试或聊天发送时收到连接错误提示，但当前缺少运行时日志和 DevTools 证据，无法定位错误发生在网络链路的哪一环。以下假设按从上游到下游的顺序排列，每项假设给出验证方法、所需证据和当前状态。所有假设在获得证据前均为待验证状态，不应作为已确认结论使用。

## 假设清单

### N-V1: 具体是哪个 Provider/URL/模型请求失败
- **验证方法**: 记录 Provider 类型、Base URL、模型名和错误展示文案，确认失败发生在哪一个具体的模型请求上。
- **所需证据**: 运行时日志（不记录 API Key），包括 Provider 标识、Base URL、模型名以及前端展示的完整错误文案。
- **状态**: 待验证
- **说明**: 用户报告中只提到"连接错误"，没有区分是 OpenAI 兼容 Provider、Anthropic Provider 还是其他类型，也没有给出具体的 Base URL 或模型名。没有这一信息，无法判断后续假设（DNS、TLS、代理等）应针对哪个端点验证。

### N-V2: 错误发生在 DNS、TLS、代理、CORS/权限、HTTP 状态码还是请求超时
- **验证方法**: 在浏览器 DevTools 的 Network 面板中确认请求 URL、HTTP 状态码，或确认是否根本没有发出请求；结合 service worker 控制台日志判断错误类型。
- **所需证据**: DevTools Network 面板的请求记录（URL、状态码、响应头）和 service worker 控制台的异常类型记录。
- **状态**: 待验证
- **说明**: 网络错误可能发生在多个环节：DNS 解析失败、TLS 握手失败、代理配置错误、CORS 或权限拦截、HTTP 4xx/5xx 状态码、请求超时。不同环节对应不同的修复方向，没有 DevTools 证据无法定位。

### N-V3: service worker 是否在 generateText 返回前被浏览器回收或重启
- **验证方法**: 在 service worker 控制台记录 `test_connection`/`chat` 消息收到时间和 Port `onDisconnect` 时间，判断 service worker 是否在请求过程中被回收。
- **所需证据**: service worker 控制台的 `test_connection`/`chat` 收到时间、异常类型和 Port `onDisconnect` 时间。
- **状态**: 待验证
- **说明**: 浏览器会在 service worker 空闲一段时间后回收它，如果 `generateText` 执行时间较长且期间没有事件维持 service worker 活跃，service worker 可能被回收导致 Port 断开，表现为连接错误。

### N-V4: 用户点击"测试连接"时设置 Port 是否已经断开
- **验证方法**: 在用户点击"测试连接"的瞬间记录设置 Port 的连接状态，判断 Port 是否在请求发起前就已经断开。
- **所需证据**: 点击时间戳和 Port 连接状态记录。
- **状态**: 待验证
- **说明**: 设置页的连接测试通过 Port 与 service worker 通信，如果 Port 在用户点击前已经断开（例如 service worker 重启后未重建 Port），请求会直接失败，与网络层错误表现相似但根因不同。

### N-V5: 对话开始后是否也出现同类错误，还是只有设置页连接测试报错
- **验证方法**: 分别在设置页连接测试和聊天发送两个场景下记录是否出现错误，判断错误是设置页独有还是对话链路也受影响。
- **所需证据**: 两个场景的错误发生记录和错误文案对比。
- **状态**: 待验证
- **说明**: 设置页连接测试和聊天发送走不同的请求路径，如果只有设置页报错，问题可能集中在设置 Port 或连接测试逻辑；如果对话也开始后也报错，问题可能在更底层的网络或 Provider 配置。

### N-V6: 网络恢复后，原聊天流是否需要用户手动重试
- **验证方法**: 在错误发生后等待网络恢复，观察原聊天流是否自动恢复，或是否需要用户手动重试。
- **所需证据**: 网络恢复时间点和聊天流状态记录。
- **状态**: 待验证
- **说明**: 当前代码的设计是断开原流并重连 Port，不自动恢复原请求。这意味着即使网络恢复，用户也需要手动重新发送消息才能继续对话。这一行为是否符合用户预期需要确认，但目前没有用户在网络恢复后的行为记录。

## 后续复现所需最小证据

以下证据是复现网络层错误并定位根因的最小集合，采集时注意不记录 API Key、Cookie 或完整请求凭据：

1. **记录发生时间和当前页面 URL**：区分设置页连接测试与聊天发送两个场景，错误发生在哪个页面直接影响后续排查方向。
2. **记录 Provider 类型、Base URL、模型名和错误展示文案**：不要记录 API Key。这些信息用于定位具体是哪个模型请求失败，对应假设 N-V1。
3. **在浏览器 DevTools 的 Network 中确认请求 URL、HTTP 状态或是否根本没有发出请求**：用于判断错误发生在 DNS、TLS、代理、CORS、HTTP 状态码还是请求超时，对应假设 N-V2。
4. **在 service worker 控制台记录 test_connection/chat 收到时间、异常类型和 Port onDisconnect 时间**：用于判断 service worker 是否被回收或 Port 是否提前断开，对应假设 N-V3 和 N-V4。
5. **记录从点击到错误显示的耗时**：约 10 秒通常对应连接测试的模型请求超时，约 12 秒通常对应前端兜底，约 60 秒可能对应聊天 Port 的 pong 超时。耗时区间是判断错误来源的重要线索。
6. **若对话开始后发生问题，同时记录是否收到过 chunk、error 或 done**：以区分上游流异常、消息链路断开和 UI 状态问题，对应假设 N-V5。

## 后续复现步骤建议

基于上述最小证据集合，建议按以下步骤复现：

1. 在浏览器中打开扩展并进入设置页，准备好 DevTools 的 Network 面板和 service worker 控制台。
2. 点击"测试连接"按钮，记录点击时间、Provider 类型、Base URL 和模型名，同时观察 Network 面板是否发出请求以及请求的状态码。
3. 如果设置页报错，记录错误文案和从点击到错误显示的耗时，并检查 service worker 控制台是否有异常或 Port `onDisconnect` 记录。
4. 进入聊天页面发送一条消息，重复上述记录，特别关注是否收到过 `chunk`、`error` 或 `done` 消息。
5. 如果错误复现，等待网络恢复后观察原聊天流是否自动恢复，或是否需要手动重试，记录行为结果对应假设 N-V6。
6. 将上述证据汇总后，逐项核对假设 N-V1 至 N-V6 的验证状态，将已验证的假设更新为已确认，未验证的继续保留待验证状态。
