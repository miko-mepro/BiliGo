# 测试覆盖缺口清单

## 基本信息
- **来源文档**: 搜索结果展示与重排问题记录.md, 渲染崩溃问题记录.md
- **发现日期**: 2026-08-01
- **缺口总数**: 7项测试覆盖缺口 + 1项 E2E 运行阻塞

本文档汇总当前测试体系中与"搜索结果展示与重排"、"渲染崩溃"两类问题相关的测试覆盖现状与缺口。已有测试主要覆盖了搜索、重排、写入、渲染和排序过滤的主路径，但在用户交互时序、消息批次归属、滚动行为和排序冲突等场景上仍存在缺口。此外，Playwright E2E 在扩展挂载阶段稳定失败，导致无法获得渲染崩溃问题所需的浏览器侧证据，单独列为 E2E 运行阻塞项。

## 已有测试覆盖

以下测试是当前体系中与搜索结果展示、重排和渲染链路直接相关的已有覆盖，作为后续缺口的对照基线：

- **Main/test/background/stream.test.ts:519-555**：覆盖 `bilibili_search` 的视频推送顺序，验证搜索工具返回的视频数组按推送顺序到达 content script。
- **Main/test/background/stream.test.ts:557-620**：覆盖 rerank 后的视频数组顺序，并验证 `insight -> videos -> tool_result` 的消息到达顺序在流式推送中保持稳定。
- **Main/test/content/chat-context.test.ts:159-205**：覆盖 `SET_VIDEOS` 写入数组的 reducer 行为，并验证 reducer 不可变更新不会意外突变原状态。
- **Main/test/components/MessageList.test.tsx:113-162**：覆盖 `message` 与 `insight` 按时间交错渲染的场景，验证时间戳顺序决定卡片排列。
- **Main/test/components/MessageList.test.tsx:164-207**：覆盖视频卡片存在时能够渲染视频网格，验证视频网格在消息列表末尾挂载。
- **Main/test/utils/sort-filter.test.ts:48-80, 154-183**：覆盖播放量等字段排序，以及"先过滤后排序"的链式行为。

这些测试共同构成了搜索 -> 重排 -> 写入 -> 渲染 -> 排序过滤的主路径验证，但均未覆盖下文列出的交互时序、批次归属和排序冲突等场景。

## 测试覆盖缺口清单

### 缺口1：用户上拉后继续流式输出时不应自动滚动
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前没有测试覆盖"用户手动上拉阅读历史消息时，后台仍在流式输出新 chunk 或推送新视频数组"这一场景下自动滚动行为的抑制逻辑。已有测试只验证了流式消息按顺序到达，没有验证用户上拉意图与代码自动 `scrollIntoView` 之间的优先级。
- **风险**: 如果自动滚动未被抑制，用户上拉阅读历史消息时会被持续拉回底部，造成阅读被打断，与用户描述的"滚动动画叠加和闪烁"现象一致。
- **建议验证点**: 用户上拉后 `scrollIntoView` 是否被跳过或推迟；流式输出结束后是否恢复自动滚动；用户重新下拉到底部时是否重新启用自动跟随。

### 缺口2：scrollIntoView 在每个 chunk、reasoning 或视频数组更新时的调用频率
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前没有测试统计 `scrollIntoView` 在单次对话中被调用的次数。流式输出过程中每个 chunk、每段 reasoning、每次视频数组更新都可能触发一次滚动，已有测试只验证最终消息顺序，没有验证中间过程的滚动次数。
- **风险**: 高频 `scrollIntoView` 会造成滚动动画叠加，表现为用户可见的闪烁和跳动，这正是搜索结果展示问题记录中列出的高风险假设 S-V2。
- **建议验证点**: 单次流式输出期间 `scrollIntoView` 的调用次数；多段 reasoning 和多组视频数组推送叠加时的滚动次数上限。

### 缺口3：两次搜索的结果是否应按消息批次同时保留
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前没有测试覆盖"同一对话内发起第二次搜索"时，第一次搜索的视频数组和 insight 是否仍然保留在消息列表中。已有测试只覆盖单次搜索的推送顺序，没有覆盖跨搜索批次的视频数组归属和可见性。
- **风险**: 如果第二次搜索覆盖了第一次搜索的视频数组，用户会丢失第一次的结果；如果两次结果都保留但顺序混乱，会造成视频网格与 insight 的语义错配（对应假设 S-V1）。
- **建议验证点**: 第二次搜索后 DOM 中存在的视频数组数量；第一次搜索的 insight 与第二次搜索的视频之间是否产生语义错配。

### 缺口4：旧视频与旧 insight 的归属是否一致
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前没有测试覆盖"旧视频数组和旧 insight 卡片在第二次搜索后是否仍然归属于同一个消息批次"。已有测试覆盖了 `message` 与 `insight` 按时间交错，但没有覆盖跨搜索批次时旧视频与旧 insight 的归属一致性。
- **风险**: 归属不一致会导致用户看到旧的 insight 文案下方挂着新搜索的视频，或新的 insight 文案下方挂着旧搜索的视频，造成误导。
- **建议验证点**: 旧视频数组的 `batchId`（或等价标识）与旧 insight 卡片的归属标识是否一致；第二次搜索后旧视频是否仍挂在原消息批次下。

### 缺口5：rerank 数组经过 MessageList 后的最终 DOM 顺序
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前 `stream.test.ts:557-620` 验证了 rerank 后的视频数组顺序，`MessageList.test.tsx:164-207` 验证了视频网格能够渲染，但两者之间没有端到端串联测试验证"rerank 数组原样经过 MessageList 后在 DOM 中的顺序"。中间经过 reducer 写入、reducer 不可变更新、React 重渲染后，顺序是否保持一致未被测试覆盖。
- **风险**: 如果 reducer 或渲染层在写入过程中改变了数组顺序，rerank 的重排效果会被客户端静默覆盖，后端重排工作失效。
- **建议验证点**: rerank 数组从 background 推送到 content script 再到 DOM 的端到端顺序一致性；reducer 写入前后数组顺序是否保持。

### 缺口6：rerank 顺序与默认播放量排序冲突时，产品应优先哪一种
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前 `sort-filter.test.ts:48-80` 覆盖了播放量排序，但没有任何测试覆盖"rerank 顺序与客户端默认播放量排序冲突"时的产品优先级。后端 rerank 给出的顺序可能与按播放量降序排列的顺序不同，此时客户端应该展示 rerank 顺序还是播放量顺序，缺少明确的测试约束。
- **风险**: 行为不明确会导致用户在不同场景下看到不一致的顺序，且无法判断是 rerank 失效还是客户端排序覆盖。
- **建议验证点**: rerank 到达后客户端是否立即覆盖默认排序；用户手动切换排序后 rerank 顺序是否被保留；产品需求中 rerank 与播放量排序的优先级定义。

### 缺口7：视频数组更新后是否应该重置用户手动选择的筛选/排序
- **来源**: 搜索结果展示与重排问题记录.md
- **缺口描述**: 当前 `sort-filter.test.ts:154-183` 覆盖了"先过滤后排序"的链式行为，但没有任何测试覆盖"视频数组更新（第二次搜索或 rerank 推送）后，用户之前手动选择的筛选条件或排序字段是否应该被重置"。这一行为影响用户在连续操作中的一致性预期。
- **风险**: 如果不重置，用户在第一次搜索时选择的"按播放量降序"会沿用到第二次搜索，可能不是用户期望的默认行为；如果重置，用户需要重新选择，增加操作成本。两种行为都没有测试约束。
- **建议验证点**: 视频数组更新后筛选状态是否重置；排序字段是否重置；用户手动选择与默认值的优先级。

## E2E 运行阻塞

除上述单元/组件测试缺口外，渲染崩溃问题记录.md 中提到的 Playwright E2E 在扩展挂载阶段稳定失败，单独列为运行阻塞项：

- **位置**: `Main/e2e/fixtures/extension-harness.ts:85-87`
- **现象**: E2E 在等待 `[data-bili-agent-toggle]` 选择器时超时，未进入打开面板和按钮交互阶段。
- **错误**: `Channel closed` + `page.goto: Target page, context or browser has been closed`
- **影响**: 未获得任何目标按钮点击证据，包括点击顺序、点击间隔、React 错误边界文案、浏览器控制台 render stack、事件处理器异常或 `Maximum call stack size exceeded`。
- **当前状态**: 稳定复现的只是 E2E 前置失败，可能是扩展注入、测试页面、浏览器上下文关闭或 service worker 启动问题，不能等同于用户描述的按钮渲染崩溃。
- **详细记录**: 见 `05-测试与验证缺口/E2E运行阻塞问题.md`。

## 建议的补充测试方向

针对上述 7 项缺口，建议补充以下测试用例：

1. **针对缺口1**：新增"用户上拉后流式输出不自动滚动"的组件测试，模拟 `scrollIntoView` 调用并断言用户上拉状态下不被触发，流式结束后恢复跟随。
2. **针对缺口2**：新增 `scrollIntoView` 调用次数统计测试，构造多段 reasoning + 多组视频数组推送的输入，断言调用次数在合理上限内。
3. **针对缺口3**：新增跨搜索批次测试，在 `chat-context.test.ts` 中模拟第二次 `SET_VIDEOS`，断言旧视频数组是否被保留或覆盖。
4. **针对缺口4**：新增旧视频与旧 insight 归属一致性测试，断言两者的批次标识一致，第二次搜索后旧卡片归属不变。
5. **针对缺口5**：新增 rerank 数组端到端顺序测试，串联 background -> content -> MessageList，断言 DOM 顺序与 rerank 输入一致。
6. **针对缺口6**：新增 rerank 与播放量排序冲突测试，断言 rerank 到达后客户端展示顺序的优先级行为，并补充产品需求中的优先级定义。
7. **针对缺口7**：新增视频数组更新后筛选/排序状态测试，断言更新后筛选与排序字段的重置或保留行为符合产品定义。
8. **针对 E2E 阻塞**：优先修复 `extension-harness.ts` 的 content script 注入时机和 service worker 启动状态，恢复 E2E 后再补充按钮点击序列和浏览器崩溃堆栈的端到端验证。
