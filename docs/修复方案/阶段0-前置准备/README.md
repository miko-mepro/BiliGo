# 阶段0 前置准备

## 阶段目标

恢复扩展的运行时验证能力，为后续阶段的修复提供可执行的 E2E 测试基础设施和运行时证据采集通道。本阶段不修复具体问题编号，而是解除测试与验证缺口目录记录的 E2E 运行阻塞，并搭建运行时证据采集环境。

## 包含方案

本阶段包含两类前置工作：

### 方案一：E2E 运行阻塞解除

- 对应问题档案：`docs/问题档案/05-测试与验证缺口/E2E运行阻塞问题.md`
- 目标：消除 `Main/e2e/fixtures/extension-harness.ts:85-87` 等待 `[data-bili-agent-toggle]` 时的前置失败。
- 关键症状：`Error: Channel closed` 和 `Error: page.goto: Target page, context or browser has been closed`。
- 排查方向：扩展注入时机、测试页面可用性、浏览器上下文生命周期、service worker 启动顺序。
- 采集要求：恢复后至少一条目标 smoke 测试能进入面板打开和按钮交互阶段。

### 方案二：运行时证据采集通道搭建

- 对应问题档案：`docs/问题档案/06-待验证假设/` 下的网络层假设清单和搜索结果高风险假设清单。
- 目标：建立 service worker 控制台日志、DevTools Network 请求记录、DOM 录制和 `scrollIntoView` 调用计数的采集能力。
- 采集要求：不记录 API Key、Cookie 或完整请求凭据，只记录发生时间、Provider 类型、Base URL、模型名、错误文案、耗时和非敏感消息时间线。
- 应用范围：阶段1 到阶段3 的运行时补验、阶段4 的 E2E 场景回归和假设验证均依赖本方案建立的采集通道。

## 前置依赖

无硬依赖。本阶段是整个修复工作的起点，可与阶段1 的静态修复并行启动。

## E2E 挂载阻塞的特殊规则

本阶段的核心约束是 E2E 挂载阻塞与静态修复的解耦关系，必须明确区分：

- **E2E 挂载阻塞不阻塞静态修复**：R-1（历史标题类型校验）和 N-2（聊天流总超时）等问题已由静态代码证据确认根因，其修复方案设计、代码实现和单元测试可以在 E2E 能力恢复之前并行推进。这类修复不依赖运行时证据即可完成代码层面工作。
- **E2E 挂载阻塞阻塞最终运行时证据采集**：R-1、R-2、R-3 的渲染崩溃堆栈、S-2 的实际滚动频率、S-4 的最终 DOM 顺序、N-V1 到 N-V6 和 S-V1 到 S-V5 的假设验证，都需要运行时证据支持。这些证据必须等待 E2E 能力恢复后才能采集。

因此，阶段1 到阶段3 的代码修复可以先行推进，但其 `completed` 状态的最终验收需要本阶段提供运行时证据支持。在状态追踪中，这类问题可标记为 `needs_review`，但不能标记为 `completed`，直到本阶段完成。

## 可并行项

- 阶段1 的 R-1 静态修复（代码实现和单元测试）。
- 阶段2 的 N-2 静态修复（总超时阈值设定和 `AbortSignal.timeout` 接入）。
- 阶段2 的 S-3 批次模型设计（协议层和状态层的字段定义，不含运行时验证）。
- 阶段2 的 S-2 滚动保护设计（effect 依赖分析和保护机制设计，不含运行时验证）。

以上并行项的前提是：阶段0 的 E2E 阻塞排查和运行时证据采集通道搭建不被这些并行工作干扰。

## 阶段退出条件

- E2E 测试夹具能稳定等待 content script 挂载，`[data-bili-agent-toggle]` 在限定时间内出现。
- `Channel closed` 和 `page.goto: Target page, context or browser has been closed` 错误已消除或已规避。
- 运行时证据采集通道（service worker 控制台、DevTools Network、DOM 录制、`scrollIntoView` 调用计数）可用。
- 至少一条目标 smoke 测试能进入面板打开和按钮交互阶段。
- 运行时证据采集通道已通过一次最小冒烟验证，能记录非敏感信息（发生时间、Provider 类型、Base URL、模型名、错误文案、耗时）。

## 风险

- **E2E 阻塞根因可能与扩展注入逻辑耦合**：`Channel closed` 错误可能源于 service worker 启动顺序、content script 注入时机或浏览器上下文关闭，排查可能涉及 MV3 生命周期细节，耗时不确定。
- **运行时证据采集可能引入副作用**：在 service worker 注入日志、在 content script 录制 DOM 可能影响流式输出性能或滚动行为，需验证采集通道本身不改变被验证的行为。
- **静态修复先行可能导致返工**：阶段1 到阶段3 的静态修复在运行时证据采集前完成，若运行时证据揭示与静态分析不同的根因，部分修复可能需要返工。建议静态修复保留一定的设计弹性。
- **MV3 service worker 回收风险**：service worker 可能在 `generateText` 返回前被浏览器回收或重启，E2E 测试和运行时日志采集需考虑这一约束（对应假设 N-V3）。
