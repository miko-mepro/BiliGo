## 产品决策记录: A1（延后到 tool_result 之后）

- **决策日期**: 2026-08-03
- **选定方向**: 方案 A1 —— 在 `tool-result` 事件中先推送 `tool_result`，再推送附加 `videos`/`insight` 消息。
- **决策依据**: 延后到 `tool_result` 之后是最小改动方案，无需扩展协议（不引入 `auxiliary` 字段）、不依赖前端占位状态（无需两阶段渲染），即可让完成消息排在辅助内容之前、收窄二者时序窗口。能否在浏览器侧真正消除 understanding/expansion/视频网格/rerank 依次跳变的中间态仍属运行时/E2E 待验证预期，A1 不提供原子 UI 更新。
- **落点选择**: 不选 A3（延后到整段文本结束），因为 A3 延迟最大，长搜索（含 analyze_covers）场景下用户等待感知过强；不选 A2（附带在 tool_result 中），因为需要扩展协议类型并改 content reducer，与本任务「不改变协议或 content reducer」的约束冲突。
- **统一延后范围**: 5 个工具（slang_understand、bilibili_search、video_rerank、ask_clarification、query_expand）全部延后到各自 `tool_result` 之后。`ask_clarification` 不保留即时展示——其 insight 在 `tool_result` 之后紧接着推送，时序间隔可忽略，不阻塞用户交互。
- **tool-call 行为不变**: `tool-call` case 仍只推送 `tool_start`，不附加辅助内容（原代码即如此，A 时机点不存在）。
- **S-3 批次 ID 保留**: `bilibili_search` 的 `batchId` 生成与 `video_rerank` 复用 `session.lastSearchBatchId` 的逻辑不变，仅推送时点从 `tool_result` 之前移到之后。
- **错误/流终止行为不变**: `tool-error`/`error`/`abort` 的处理与 `done` 推送顺序不变。

## S-3 / S-2 / S-4 回查结论

- **S-3（视频批次归属模型）回查**: 成立。S-3 的 `batchId` 由 `bilibili_search` 的 `toolCallId` 派生并记录到 `session.lastSearchBatchId`，`video_rerank` 复用该值。A1 只改变辅助内容相对 `tool_result` 的先后，不改变 `batchId` 的生成时机与复用规则。S-3 的两次 videos 推送仍落在同一批次上（`search_call_s1`），重排更新仍标记 `reranked: true`。回查结论：**S-3 修复前提不变，无需调整**。
- **S-2（自动滚动保护）回查**: 成立。S-2 的滚动 effect 依赖 `[renderItems.length, streamingContent, streamingReasoning, videos, isAtBottom, userScrolled]`。A1 后 `videos`/`insight` 推送仍在 `done` 之前，只是从 `tool_result` 之前移到之后，`videos` 数组引用变化次数不变（一次搜索仍最多 2 次 videos 推送：search + rerank）。`streamingContent`/`streamingReasoning` 的高频滚动触发源不受 A1 影响。回查结论：**S-2 的滚动保护前提不变，无需调整**；A1 不减少 `videos` 更新频率，S-2 仍需独立的 `isAtBottom`/`userScrolled` 保护。
- **S-4（客户端排序覆盖）回查**: 成立。S-4 的排序重置 effect 依赖 `[videos]` 引用变化，A1 不改变 `videos` 推送次数与 `reranked` 标记，仅改变其相对 `tool_result` 的时序。S-4 的「rerank 同批次不重置用户排序」逻辑以 `batchId` 为锚点，A1 不影响 `batchId` 复用。回查结论：**S-4 排序重置逻辑前提不变，无需调整**。
- **阶段2 回查总结**: S-2/S-3/S-4 的修复前提均不依赖「videos 在 tool_result 之前推送」这一时序，A1 仅调整辅助内容与 `tool_result` 的相对顺序，不改变批次 ID、推送次数、引用变化频率，阶段2 修复全部成立。

## 术语澄清:两个被混为一谈的展示时机

在进入方案前必须先把一个被原档案模糊的关键区分讲清楚,否则后续的产品决策会建立错误前提上:

| 时机点 | 修复前基线行为 | 用户报告现象对应此时机点吗 |
| --- | --- | --- |
| **A. 工具调用刚开始就展示** | 否。`stream.ts` 不会在 `tool-call` 事件(第 345-352 行)推送任何视频或 insight。此时 UI 只收到 `tool_start` 消息,视频网格、insight 卡片均未渲染。 | 否。用户说的"调用 Search 工具过程中,搜索内容会立即展示"指的是结果到达后,不是工具刚开始时。 |
| **B. 工具结果到达后立即展示** | 是（修复前基线）。`stream.ts:354-366` 在 `tool-result` 事件中先调用 `postToolAuxiliaryMessages`(第 175-225 行)推送 `videos`/`insight`,再推送 `tool_result`。辅助内容不等待最终 `tool_result` 或整段文本结束就进入 content script。**A1 已将该顺序翻转为 `tool_result` 在前、辅助内容在后**，下文「静态确认的推送链路」第 2 条记录的是修复前链路。 | 是。这正是用户看到的"立即展示"的真实含义。 |

**关键事实校准**:原档案标题"搜索辅助内容即时展示"容易让人误以为"工具刚启动就有内容"。实际代码中,`tool-call` 和 `tool-result` 是 AI SDK 流的两个独立 part 事件,中间存在模型实际执行工具的间隔。辅助内容只在 `tool-result`(工具执行体返回后)才推送,**不是在工具刚开始时**。S-1 修复方案处理的也仅是 B 时机的延后,不涉及 A 时机点不存在的"工具开始就展示"行为。

本区分是产品决策的前提:如果误把 B 当成 A,会去寻找"工具开始时谁在推送视频"的根因,而该根因不存在。

## 静态确认的推送链路

以下链路已通过静态代码审查确认,不需要运行时复现即可作为修复前提:

1. **`tool-call` 事件不推送辅助内容**: `Main/src/background/stream.ts:345-352` 收到 `tool-call` part 时,只推送 `tool_start` 消息(包含 `toolCallId`、`toolName`、`args`),不调用 `postToolAuxiliaryMessages`,不推送 `videos` 或 `insight`。
2. **`tool-result` 事件先推辅助内容再推 `tool_result`（修复前基线，A1 已翻转此顺序）**: `Main/src/background/stream.ts:354-366` 修复前在 `tool-result` part 中先调用 `postToolAuxiliaryMessages` 推送 `videos`/`insight`，再推送 `tool_result`。A1 实施后已改为先推送 `tool_result`、再调用 `postToolAuxiliaryMessages`，顺序变为 `tool_start -> tool_result -> videos/insight`。
3. **辅助内容按工具类型分流**: `postToolAuxiliaryMessages`(`stream.ts:175-225`)按 `toolName` 分发:
   - `bilibili_search` 推送 `{ type: 'videos', videos: ... }`(第 184 行)。
   - `slang_understand` 推送 `insight(understanding)`(第 187-191 行)。
   - `query_expand` 推送 `insight(expansion)`(第 193-198 行)。
   - `video_rerank` 先推送 `insight(rerank)`,再推送重排后的 `videos`(第 200-212 行)。
   - `ask_clarification` 推送 `insight(clarification)`(第 214-219 行)。
4. **协议层允许独立传递**: `Main/src/background/port-protocol.ts:6-17` 的 `SWMessage` 类型中,`videos` 和 `insight` 是独立消息类型,没有强制要求它们与 `tool_result` 绑定或等待工具完成。
5. **前端分三状态消费**: `Main/src/content/chat-context.tsx:389-459` 收到 `videos` 派发 `SET_VIDEOS`(直接替换全局视频数组),收到 `insight` 按类型追加到 understanding/expansion/rerank 数组,`tool_result` 只更新工具步骤完成状态。三类状态没有共同的"搜索输出块"锚点。

因此,"辅助内容在工具结果到达后立即进入 UI"是当前实现的静态确认行为,而非工具刚开始就展示。

## 触发边界

满足以下条件即触发 B 时机点的立即展示:

1. 模型在流中产生 `tool-result` part(AI SDK 在工具执行体返回后产生)。
2. 工具名为 `bilibili_search`、`slang_understand`、`query_expand`、`video_rerank` 或 `ask_clarification` 之一。
3. `postToolAuxiliaryMessages` 推送 `videos` 或 `insight` 消息。
4. content script 收到消息后派发对应 reducer,UI 状态更新。
5. `MessageList` 重新渲染,视频网格、筛选控件或 insight 卡片出现/更新。

不触发的情况:

- 工具名为 `default` 分支(未知工具),只推送 `tool_result`,不附加消息。
- `video_rerank` 的候选视频全部不完整(缺少 `bvid` 或 `title`),`extractVideoCandidates` 返回空数组,不推送第二组 `videos`(`stream.ts:207-211`)。
- 流在 `tool-result` 之前因 `tool-error` 或 `error` part 终止,辅助内容不推送。

## 这是产品决策项,不是纯技术缺陷

S-1 与 R-1(标题类型校验缺失导致 TypeError)不同:R-1 有一个明确的"正确行为"(render 不应抛 TypeError),S-1 没有唯一正确答案。当前 B 时机点的立即展示既有缺点也有优点:

- **缺点**:搜索过程中多个 UI 区域(understanding、expansion、视频网格、rerank)依次出现,造成视觉跳动;与 S-2 的无条件滚动叠加,用户难以稳定阅读上方内容;与 S-3 的全局替换叠加,新搜索覆盖旧视频时视觉变化被滚动掩盖。
- **优点**:用户能更早看到搜索中间结果,感知到"系统在工作";对于长耗时搜索(如包含 cover 分析的 `bilibili_search`),延后展示可能让用户长时间看不到任何反馈,误以为卡住。

因此 S-1 的修复必须先做产品决策,再落地技术实现。本方案曾提供两个可选方向,由产品决策选定后再进入实施（历史上下文：产品决策已于 2026-08-03 选定 A1，见「产品决策结论」一节，当前实施范围以 A1 为准）。

## 修复目标

**使搜索辅助内容的展示时机与"搜索输出块"的语义边界对齐,并缩短工具完成消息与辅助内容之间的时序窗口。**

> A1 只调整 service worker 消息顺序,不把独立的 `tool_result` 与辅助消息合并为一次原子 UI 更新。浏览器侧是否因此减少视觉跳变,仍需运行时/E2E 验证。

具体目标分解（A1 已选定，下方"两阶段展示"为决策前备选方向的历史上下文）:

- A1（已选）:辅助内容在各自 `tool_result` 之后推送,但独立消息仍可能产生短暂中间态；浏览器侧的实际稳定性留待运行时验证。
- 若选定"两阶段展示"（历史备选方向，A1 未选此方向，仅记录排除理由）:保留即时展示,但在 UI 层引入"工具进行中"占位状态,辅助内容以低强调度展示,`tool_result` 完成后切换为正式展示状态。
- 消息锚点建议（历史推演，A1 不引入此结构）:原方案建议两个方向都为视频数组建立消息锚点(与 S-3 批次模型协调),使 UI 能识别"搜索输出块"的边界。A1 不扩展协议、不引入消息锚点，该建议供后续可能的协议扩展参考。

**关于"工具刚开始就展示"的边界声明**:本方案不处理 A 时机点,因为当前代码不存在该行为。若后续运行时证据发现 A 时机点确实出现(例如 service worker 在 `tool-call` 之前推送了 videos),则属于另一个未确认问题,不在 S-1 范围内。

## 与 S-3 批次模型的关系

S-3 的核心问题是 `SET_VIDEOS` 直接替换全局视频数组,没有批次归属和消息锚点。以下条件分支为决策前的协调推演（历史上下文）；选定 A1 后的实测结论见「S-3 / S-2 / S-4 回查结论」一节：

- **若 S-1 选定"延后展示"（历史推演，A1 已选定此方向）**:辅助内容缓存到 `tool_result` 后一并下发。此时 `videos` 消息仍走 `SET_VIDEOS` 替换全局数组,S-3 的覆盖问题不变。S-1 只改变了"何时替换",没改变"替换语义"。S-3 仍需独立引入批次 ID。实测结论：A1 选定此方向，S-3 批次归属模型前提不受影响（见回查结论一节）。
- **若 S-1 选定"两阶段展示"（历史推演，A1 未选此方向，仅记录排除理由）**:`tool_result` 之前的辅助内容以低强调度展示(占位状态),`tool_result` 完成后切换为正式展示。此时 UI 需要区分"占位视频"和"正式视频",S-3 的批次模型需支持该状态切换。A1 未选此方向，该分支不适用。
- **共享数据模型建议（历史推演，A1 不引入此结构）**:无论 S-1 选哪个方向,都建议与 S-3 共享一个"搜索输出块"数据结构,包含 `searchBatchId`、`toolCallId`、`status: 'streaming' | 'completed'`、`videos`、`insights` 字段。S-1 负责控制 `status` 的切换时机,S-3 负责用 `searchBatchId` 区分不同搜索批次。A1 不扩展协议、不引入此结构，该建议供后续可能的协议扩展参考。

## 与 S-2 滚动保护的关系

S-2 的根因是 `MessageList.tsx:93-96` 的 effect 在 `renderItems.length`、`streamingContent`、`streamingReasoning`、`videos` 任一变化时无条件滚动。A1 调整的是辅助内容相对 `tool_result` 的先后顺序，不改变 `videos` 的更新次数与引用变化频率（实测结论见「S-3 / S-2 / S-4 回查结论」一节）:

- **修复前基线(B 时机点立即展示)**:一次包含 `bilibili_search` + `video_rerank` 的搜索会产生至少两次 `videos` 更新(搜索结果 + 重排结果),每次都触发 S-2 的滚动。
- **A1 延后展示后(当前行为)**:`videos` 更新仍保持相同次数,但均发生在对应 `tool_result` 之后；`streamingContent` 和 `streamingReasoning` 仍高频更新,S-2 仍需独立实现用户阅读保护。
- **协同建议**:A1 不应假设"延后展示就能解决 S-2"。S-2 的滚动保护是独立的 `isAtBottom`/`userScrolled` 状态判断,A1 不减少 `videos` 更新频率、不消除视频触发的滚动，没有减少任何滚动触发源。
