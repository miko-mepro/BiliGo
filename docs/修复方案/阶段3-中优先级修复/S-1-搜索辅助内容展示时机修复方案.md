- **所属阶段**: 阶段3 - 中优先级修复
- **修复状态**: pending
- **问题档案**: `docs/问题档案/03-UI渲染与交互/S-1-搜索辅助内容即时展示.md`

## 术语澄清:两个被混为一谈的展示时机

在进入方案前必须先把一个被原档案模糊的关键区分讲清楚,否则后续的产品决策会建立错误前提上:

| 时机点 | 当前实际行为 | 用户报告现象对应此时机点吗 |
| --- | --- | --- |
| **A. 工具调用刚开始就展示** | 否。`stream.ts` 不会在 `tool-call` 事件(第 345-352 行)推送任何视频或 insight。此时 UI 只收到 `tool_start` 消息,视频网格、insight 卡片均未渲染。 | 否。用户说的"调用 Search 工具过程中,搜索内容会立即展示"指的是结果到达后,不是工具刚开始时。 |
| **B. 工具结果到达后立即展示** | 是。`stream.ts:354-366` 在 `tool-result` 事件中先调用 `postToolAuxiliaryMessages`(第 175-225 行)推送 `videos`/`insight`,再推送 `tool_result`。辅助内容不等待最终 `tool_result` 或整段文本结束就进入 content script。 | 是。这正是用户看到的"立即展示"的真实含义。 |

**关键事实校准**:原档案标题"搜索辅助内容即时展示"容易让人误以为"工具刚启动就有内容"。实际代码中,`tool-call` 和 `tool-result` 是 AI SDK 流的两个独立 part 事件,中间存在模型实际执行工具的间隔。辅助内容只在 `tool-result`(工具执行体返回后)才推送,**不是在工具刚开始时**。S-1 修复方案处理的也仅是 B 时机的延后,不涉及 A 时机点不存在的"工具开始就展示"行为。

本区分是产品决策的前提:如果误把 B 当成 A,会去寻找"工具开始时谁在推送视频"的根因,而该根因不存在。

## 静态确认的推送链路

以下链路已通过静态代码审查确认,不需要运行时复现即可作为修复前提:

1. **`tool-call` 事件不推送辅助内容**: `Main/src/background/stream.ts:345-352` 收到 `tool-call` part 时,只推送 `tool_start` 消息(包含 `toolCallId`、`toolName`、`args`),不调用 `postToolAuxiliaryMessages`,不推送 `videos` 或 `insight`。
2. **`tool-result` 事件先推辅助内容再推 `tool_result`**: `Main/src/background/stream.ts:354-366` 收到 `tool-result` part 时,先取出该 `toolCallId` 对应的 `toolInput`(第 356 行),调用 `postToolAuxiliaryMessages`(第 357 行)推送 `videos`/`insight`,删除 `toolInputs` 中的缓存(第 358 行),再推送 `tool_result`(第 360-365 行)。
3. **辅助内容按工具类型分流**: `postToolAuxiliaryMessages`(`stream.ts:175-225`)按 `toolName` 分发:
   - `bilibili_search` 推送 `{ type: 'videos', videos: ... }`(第 184 行)。
   - `slang_understand` 推送 `insight(understanding)`(第 187-191 行)。
   - `query_expand` 推送 `insight(expansion)`(第 193-198 行)。
   - `video_rerank` 先推送 `insight(rerank)`,再推送重排后的 `videos`(第 200-212 行)。
   - `ask_clarification` 推送 `insight(clarification)`(第 214-219 行)。
4. **协议层允许独立传递**: `Main/src/background/port-protocol.ts:6-17` 的 `SWMessage` 类型中,`videos` 和 `insight` 是独立消息类型,没有强制要求它们与 `tool_result` 绑定或等待工具完成。
5. **前端分三状态消费**: `Main/src/content/chat-context.tsx:389-459` 收到 `videos` 派发 `SET_VIDEOS`(直接替换全局视频数组),收到 `insight` 按类型追加到 understanding/expansion/rerank 数组,`tool_result` 只更新工具步骤完成状态。三类状态没有共同的"搜索输出块"锚点。

因此,"辅助内容在工具结果到达后立即进入 UI"是当前实现的静态确认行为,而非工具刚开始就展示。

## 触发边界

满足以下条件即触发 B 时机点的立即展示:

1. 模型在流中产生 `tool-result` part(AI SDK 在工具执行体返回后产生)。
2. 工具名为 `bilibili_search`、`slang_understand`、`query_expand`、`video_rerank` 或 `ask_clarification` 之一。
3. `postToolAuxiliaryMessages` 推送 `videos` 或 `insight` 消息。
4. content script 收到消息后派发对应 reducer,UI 状态更新。
5. `MessageList` 重新渲染,视频网格、筛选控件或 insight 卡片出现/更新。

不触发的情况:

- 工具名为 `default` 分支(未知工具),只推送 `tool_result`,不附加消息。
- `video_rerank` 的候选视频全部不完整(缺少 `bvid` 或 `title`),`extractVideoCandidates` 返回空数组,不推送第二组 `videos`(`stream.ts:207-211`)。
- 流在 `tool-result` 之前因 `tool-error` 或 `error` part 终止,辅助内容不推送。

## 这是产品决策项,不是纯技术缺陷

S-1 与 R-1(标题类型校验缺失导致 TypeError)不同:R-1 有一个明确的"正确行为"(render 不应抛 TypeError),S-1 没有唯一正确答案。当前 B 时机点的立即展示既有缺点也有优点:

- **缺点**:搜索过程中多个 UI 区域(understanding、expansion、视频网格、rerank)依次出现,造成视觉跳动;与 S-2 的无条件滚动叠加,用户难以稳定阅读上方内容;与 S-3 的全局替换叠加,新搜索覆盖旧视频时视觉变化被滚动掩盖。
- **优点**:用户能更早看到搜索中间结果,感知到"系统在工作";对于长耗时搜索(如包含 cover 分析的 `bilibili_search`),延后展示可能让用户长时间看不到任何反馈,误以为卡住。

因此 S-1 的修复必须先做产品决策,再落地技术实现。本方案提供两个可选方向,由产品决策选定后再进入实施。

## 修复目标

**使搜索辅助内容的展示时机与"搜索输出块"的语义边界对齐,消除搜索过程中多个 UI 区域依次跳变的体验问题。**

具体目标分解(取决于产品决策选定的方向):

- 若选定"延后展示":辅助内容在最终 `tool_result`(或整段文本结束)之后统一展示,搜索过程中 UI 不出现视频网格或 insight 卡片的中间态。
- 若选定"两阶段展示":保留即时展示,但在 UI 层引入"工具进行中"占位状态,辅助内容以低强调度展示,`tool_result` 完成后切换为正式展示状态。
- 两个方向都需为视频数组建立消息锚点(与 S-3 批次模型协调),使 UI 能识别"搜索输出块"的边界。

**关于"工具刚开始就展示"的边界声明**:本方案不处理 A 时机点,因为当前代码不存在该行为。若后续运行时证据发现 A 时机点确实出现(例如 service worker 在 `tool-call` 之前推送了 videos),则属于另一个未确认问题,不在 S-1 范围内。

## 依赖关系

- **硬依赖**:无。S-1 的修复方案设计不依赖运行时证据,产品决策和技术方案可在静态确认基础上推进。
- **软依赖**:S-1 的实施与 S-3(视频结果缺少批次归属模型)强耦合。S-1 选定"延后展示"或"两阶段展示"后,视频数组需要消息锚点来标识"搜索输出块"边界,这正是 S-3 的批次模型要解决的。建议 S-1 与 S-3 协同设计,共享"搜索输出块"的数据模型。
- **因果链上游责任**:S-1 是 S-2/S-3/S-4 因果链的最上游(见问题关联图"关联四")。S-1 的展示时机调整会改变下游前提:
  - 对 S-2:若 S-1 延后展示,搜索过程中不再有 `videos` 数组更新触发滚动,S-2 的滚动频率会自然下降,但 `streamingContent`/`streamingReasoning` 仍会触发滚动,S-2 的用户阅读保护仍需独立修复。
  - 对 S-3:若 S-1 引入"搜索输出块",S-3 的批次归属模型可复用该块的锚点 ID,避免重复设计。
  - 对 S-4:若 S-1 延后展示且视频数组只推送一次(最终结果),S-4 的排序覆盖触发条件(数组引用变化重置用户排序)会减少,但 `video_rerank` 的第二组 `videos` 推送仍会产生新引用,S-4 仍需独立修复。
- **与阶段2 的回查关系**:S-1 归入阶段3,但 S-2/S-3/S-4 归入阶段2。若阶段2 已先于阶段3 完成 S-2/S-3/S-4 修复,S-1 实施时必须回查阶段2 修复是否仍成立。具体回查项:
  - S-2 的滚动保护是否假设"搜索过程中有多次 videos 更新"——若 S-1 延后展示,该假设不再成立,S-2 的滚动触发条件需相应调整。
  - S-3 的批次模型是否假设"videos 在 tool-result 时立即推送"——若 S-1 延后展示,S-3 的批次时序需对齐。
  - S-4 的排序重置是否假设"videos 数组引用在搜索过程中多次变化"——若 S-1 延后展示,引用变化次数减少,S-4 的重置逻辑需评估是否仍必要。

## 与 S-3 批次模型的关系

S-3 的核心问题是 `SET_VIDEOS` 直接替换全局视频数组,没有批次归属和消息锚点。S-1 的展示时机调整必须与 S-3 协调:

- **若 S-1 选定"延后展示"**:辅助内容缓存到 `tool_result` 后一并下发。此时 `videos` 消息仍走 `SET_VIDEOS` 替换全局数组,S-3 的覆盖问题不变。S-1 只改变了"何时替换",没改变"替换语义"。S-3 仍需独立引入批次 ID。
- **若 S-1 选定"两阶段展示"**:`tool_result` 之前的辅助内容以低强调度展示(占位状态),`tool_result` 完成后切换为正式展示。此时 UI 需要区分"占位视频"和"正式视频",S-3 的批次模型需支持该状态切换。
- **共享数据模型建议**:无论 S-1 选哪个方向,都建议与 S-3 共享一个"搜索输出块"数据结构,包含 `searchBatchId`、`toolCallId`、`status: 'streaming' | 'completed'`、`videos`、`insights` 字段。S-1 负责控制 `status` 的切换时机,S-3 负责用 `searchBatchId` 区分不同搜索批次。

## 与 S-2 滚动保护的关系

S-2 的根因是 `MessageList.tsx:93-96` 的 effect 在 `renderItems.length`、`streamingContent`、`streamingReasoning`、`videos` 任一变化时无条件滚动。S-1 的展示时机调整会直接影响 `videos` 的更新频率:

- **当前(B 时机点立即展示)**:一次包含 `bilibili_search` + `video_rerank` 的搜索会产生至少两次 `videos` 更新(搜索结果 + 重排结果),每次都触发 S-2 的滚动。
- **S-1 延后展示后**:`videos` 更新集中在 `tool_result` 之后,更新频率降低,但 `streamingContent` 和 `streamingReasoning` 仍高频更新,S-2 仍需独立实现用户阅读保护。
- **协同建议**:S-1 不应假设"延后展示就能解决 S-2"。S-2 的滚动保护是独立的 `isAtBottom`/`userScrolled` 状态判断,S-1 只减少了一个触发源。

## 精确修改范围

> 以下修改范围基于"延后展示"方向描述。若产品决策选定"两阶段展示",修改范围需相应调整,但涉及的文件和函数不变。

### 文件1:`Main/src/background/stream.ts`

**修改位置**:`postToolAuxiliaryMessages` 函数(第 175-225 行)及其调用点(第 354-366 行)。

**当前行为**:`tool-result` 事件中,先调用 `postToolAuxiliaryMessages` 推送 `videos`/`insight`,再推送 `tool_result`。

**修改要点**:将辅助内容推送延迟到 `tool_result` 之后,或在 `tool_result` 时附带辅助内容(通过扩展 `tool_result` 消息或新增 `tool_auxiliary` 消息类型)。具体实现取决于产品决策:

- 方案A1(延后到 tool_result 之后):在 `tool-result` case 中先推送 `tool_result`,再调用 `postToolAuxiliaryMessages`。这改变了消息顺序为 `tool_start -> tool_result -> videos/insight`。
- 方案A2(附带在 tool_result 中):扩展 `tool_result` 消息类型,增加 `auxiliary` 字段携带 videos/insight,content script 一次性派发。
- 方案A3(延后到整段文本结束):缓存所有辅助内容,在流结束(`finally` 块或 `done` 之前)统一推送。该方案延迟最大,用户等待时间最长,需评估长搜索场景的可接受性。

**不在修改范围**:`tool-call` case(第 345-352 行)不修改,因为当前不在工具开始时推送辅助内容,无需调整。

### 文件2:`Main/src/background/port-protocol.ts`

**修改位置**:`SWMessage` 类型定义(第 6-17 行)。

**修改要点**:若选定方案A2,需扩展 `tool_result` 消息类型增加 `auxiliary` 字段;若选定方案A1或A3,协议类型不变,仅推送顺序调整。

### 文件3:`Main/src/content/chat-context.tsx`

**修改位置**:`videos` 和 `insight` 消息的派发逻辑(第 389-459 行)。

**修改要点**:若选定方案A2,content script 需从 `tool_result` 的 `auxiliary` 字段中提取 videos/insight 并派发;若选定方案A1或A3,派发逻辑不变,仅时序变化。

### 文件4:`Main/src/components/MessageList.tsx`

**修改位置**:视频网格和 insight 卡片的渲染逻辑(第 144-195 行)。

**修改要点**:若选定"两阶段展示",需引入"工具进行中"占位状态(如半透明、折叠、骨架屏),在 `tool_result` 完成前以低强调度展示辅助内容,完成后切换为正式展示。该方案对 `MessageList` 的修改最大,需新增状态字段和样式。

### 不在修改范围内的内容

- 不修改 `tool-call` case 的推送逻辑:当前不在工具开始时推送辅助内容,无需调整。
- 不修改 `video_rerank` 的 `reorderVideosByRerank` 逻辑:重排算法本身正确,问题在展示时机。
- 不修改 `FilterSortControls` 和 `VideoCard` 组件:这些组件的渲染逻辑不受展示时机影响。
- 不修改 `AgentInsightCard` 的 `isExpanded` 局部状态:卡片展开/收起不在 S-1 范围内。

## 产品决策待定项

以下决策必须由产品方确认后才能进入实施,本方案不代替产品决策:

1. **展示时机方向**:选择"延后展示"(方案A1/A2/A3 之一)还是"两阶段展示"(方案B)。两者的用户体验差异:
   - 延后展示:搜索过程中 UI 稳定,但用户等待时间增加,长搜索可能误以为卡住。
   - 两阶段展示:搜索过程中有低强调度反馈,但 UI 仍有变化(只是强度降低),实现复杂度更高。
2. **延后到哪个时机点**(若选延后展示):`tool_result` 之后还是整段文本结束(`done` 之前)。前者延迟较小,后者延迟最大但 UI 最稳定。
3. **是否允许部分工具即时展示**:例如 `ask_clarification`(澄清请求)可能需要用户立即看到并回应,不适合延后。是否对部分工具保留即时展示。
4. **占位状态的视觉设计**(若选两阶段展示):骨架屏、半透明、折叠还是其他形式。

## 运行时验证

以下事项不能仅凭静态代码确认,需在阶段0 恢复 E2E 后采集运行时证据:

1. **S-V1 假设**:用户报告的每一次 Search 是否都会同时触发视频网格、筛选控件和某一种 insight 卡片。这取决于模型实际调用了哪些工具,静态代码无法确认。
2. **视觉跳动感知**:浏览器实际是否出现用户看到的特定渲染顺序、闪烁或视觉跳动。需运行时录制屏幕并逐帧分析。
3. **延后展示的等待感知**:延后展示后,用户在搜索过程中是否误以为卡住。需用户测试确认。
4. **占位状态的视觉效果**(若选两阶段展示):占位状态在浏览器中的实际渲染效果是否符合产品预期。
5. **`video_rerank` 的第二组 videos 推送时机**:延后展示后,重排后的 videos 是否仍需在 `tool_result` 之后单独推送,还是与第一组 videos 合并。需运行时确认 rerank 实际触发频率。

**运行时验证边界声明**:在运行时证据采集完成前,本方案不把"延后展示一定能解决视觉跳动"或"两阶段展示一定能提升体验"写成已确认事实。这些是产品决策和技术方案的预期,需运行时验证后才能确认。

## 风险与回滚

### 风险

1. **延后展示增加用户等待感知**:搜索过程中 UI 无变化,用户可能误以为卡住。缓解:对于长耗时搜索,可考虑在 `tool_start` 时推送"正在搜索..."的轻量占位文本,而非完整辅助内容。该占位文本不属于 S-1 的辅助内容范围,是独立的 UX 反馈设计。
2. **两阶段展示的实现复杂度**:占位状态需要 `MessageList` 新增状态字段和样式,且需处理占位期间的状态更新频率,避免占位状态本身高频跳变。缓解:占位状态使用骨架屏或固定文案,不随每次状态更新变化。
3. **与 S-3 协同设计的返工风险**:若 S-3 的批次模型设计与 S-1 的展示时机调整不协调,可能导致数据模型返工。缓解:S-1 和 S-3 的数据模型设计应在同一批次推进,共享"搜索输出块"结构。
4. **阶段2 回查的返工风险**:S-1 修改了 videos 推送时机,可能使阶段2 已完成的 S-2/S-3/S-4 修复前提不再成立。缓解:步骤5 强制回查阶段2 修复,记录回查结论,若需调整则在方案中说明。
5. **部分工具延后展示的合理性**:`ask_clarification`(澄清请求)可能需要用户立即看到并回应,延后展示会阻塞用户交互。缓解:产品决策时评估各工具的即时性需求,对需要即时响应的工具保留即时展示。
6. **协议变更的兼容性**(若选方案A2):扩展 `tool_result` 消息类型可能影响旧版本 content script 的兼容性。缓解:Chrome 扩展的 service worker 和 content script 同版本发布,不存在跨版本兼容问题;但需确认协议变更不破坏现有测试。

### 回滚方案

如果修复引入回归问题,回滚步骤:

1. **回滚 `stream.ts`**:将 `postToolAuxiliaryMessages` 调用恢复为 `tool-result` case 中先调用、再推送 `tool_result` 的原始时序。
2. **回滚 `port-protocol.ts`**(若协议变更):恢复 `tool_result` 消息类型的原始定义,移除 `auxiliary` 字段。
3. **回滚 `chat-context.tsx`**(若派发逻辑变更):恢复原始的 `videos`/`insight` 独立派发逻辑。
4. **回滚 `MessageList.tsx`**(若选两阶段展示):移除占位状态相关代码和样式,恢复原始渲染逻辑。
5. **保留测试**:时序调整的单元测试可保留(标记为 `skip` 或调整断言),便于后续重新接入。

回滚后,辅助内容恢复到 B 时机点立即展示的原始行为,搜索过程中 UI 仍会出现中间态跳变。回滚是纯代码还原操作,不涉及数据迁移。
