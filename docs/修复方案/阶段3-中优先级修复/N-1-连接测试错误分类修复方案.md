## 关键事实校准:inferErrorCode 的真实签名

在进入方案前必须先澄清一个容易被"想当然"误判的事实,它直接决定本方案的技术约束:

**`inferErrorCode` 的入参是 `string`(错误消息文本),不是 `Error` 对象或 `unknown`。**

已通过静态代码验证(`Main/src/background/port-protocol.ts:96-102`):

```ts
export function inferErrorCode(message: string): string {
  const lower = message.toLowerCase()
  if (/\b401\b/.test(message) || /\b403\b/.test(message)
    || lower.includes('api key') || lower.includes('auth')) return '401'
  if (/\b429\b/.test(message) || lower.includes('rate limit')) return '429'
  return 'NETWORK_ERROR'
}
```

调用点也确认这一点(`stream.ts:549-555`):

```ts
const message = err instanceof Error ? err.message : String(err)
const code = inferErrorCode(message)
```

调用方先把 `err` 转成 `message: string`,再传给 `inferErrorCode`。**当前实现只能基于错误消息文本做正则匹配,无法访问 `err.cause`、`err.code`、`err.errno` 等 Node 错误对象字段。**

这意味着本方案不能直接假定"扩展 `inferErrorCode` 读取 `err.code`/`err.errno` 即可区分 DNS/TLS/超时"--因为入口签名是 `string`,错误对象已在调用点被拍平为文本。要区分 Node 错误码,必须先改变调用约定(传入 Error 对象或其结构化字段),再扩展分类逻辑。这一约束是本方案设计步骤的核心起点,不能跳过。

## 根因分析

问题的根因有两层,必须分别处理:

### 第一层:入口签名限制

`inferErrorCode(message: string)` 只接收文本,调用方在传入前已用 `err instanceof Error ? err.message : String(err)` 把错误对象拍平为文本。Node 错误对象的 `code`(`ENOTFOUND`、`ECONNREFUSED`、`ECONNRESET`、`ETIMEDOUT` 等)、`errno`、`cause` 等结构化字段在拍平后丢失,`inferErrorCode` 无法访问它们。

**不能直接假定所有运行时错误都有 Node 错误码。** 以下情况错误对象没有标准 Node `code` 字段:

- Provider SDK 抛出的自定义 Error(如 OpenAI SDK 的 `APIError`、`APIConnectionError`),其 `code` 字段语义与 Node 原生 `code` 不同。
- `AbortSignal.timeout` 触发的 `TimeoutError`(`DOMException`),其 `name` 为 `'TimeoutError'`,但没有 Node `code`。
- `fetch failed` 的底层 `TypeError`(V8 在 fetch 底层网络失败时抛出),`message` 为 `'fetch failed'`,`cause` 中可能携带 `code: 'ECONNREFUSED'` 等,但 `err.message` 只有 `'fetch failed'`。
- 浏览器环境的 `TypeError: NetworkError when attempting to fetch resource`,没有 Node `code`。

因此,错误分类设计不能只依赖 Node `code`,必须结合文本匹配、HTTP 状态码、错误对象结构化字段(若可访问)和 `cause` 链的多维度判断。

### 第二层:分类粒度不足

即使入口签名不变(只基于文本),当前分类也过粗:

- `fetch failed` 是 fetch 底层网络失败的通用文案,可能对应 DNS 解析失败、TCP 连接拒绝、TLS 握手失败、连接重置等多种根因,当前一律归为 `NETWORK_ERROR`。
- `timeout` 文本可能来自 `AbortSignal.timeout`(连接测试 10s 超时)或 Provider SDK 的请求超时,当前不区分。
- Provider 返回的 HTTP 404(模型不存在)、500(服务端错误)等状态码,若 message 中不含 401/403/429,也归为 `NETWORK_ERROR`,用户看到"网络连接失败"但实际是模型不存在或服务端错误。

## 修复目标

**使连接测试和聊天流的错误分类能区分网络层失败、HTTP 状态码错误、超时、Provider 配置错误和鉴权/限流,为每个分类提供差异化用户文案。**

具体目标分解:

1. **扩展入口签名**:使 `inferErrorCode` 能访问错误对象的结构化字段(`code`、`cause`、`name`),而非仅文本。不破坏现有 `string` 入参的调用方(保持向后兼容)。
2. **细化错误分类**:在 HTTP 401/403/429 之外,新增 DNS 错误、连接拒绝/重置、TLS 错误、超时、HTTP 4xx(非 401/403/429)、HTTP 5xx、Provider 配置错误等分类。
3. **差异化文案**:为每个新增分类提供独立的用户文案,使用户能从文案推断应检查网络、API Key、Base URL、模型名还是服务端状态。
4. **统一分类出口**:所有错误路径(连接测试内部 catch、路由层兜底、聊天流 tool-error/error/catch)都经过 `inferErrorCode`,消除 `test_connection` 路由层兜底绕过分类的缺口。
5. **不假定所有运行时错误都有 Node 错误码**:分类逻辑对无 `code` 字段的错误对象,回退到文本匹配和 HTTP 状态码判断。

## 依赖关系

- **硬依赖**:无。N-1 的错误分类设计不依赖运行时证据,可在静态确认基础上推进。

## HTTP 边界定义

错误分类需明确 HTTP 状态码的边界,避免类似 `14012`(B站业务码)被误判为 401 的问题(原始记录已确认当前 `inferErrorCode` 用 `\b401\b` 正则避免了该问题):

| HTTP 状态码范围 | 分类 code | 文案方向 | 当前是否区分 |
| --- | --- | --- | --- |
| 401 | `AUTH_ERROR`(或沿用 `'401'`) | API Key 无效,请检查设置 | 是 |
| 403 | `AUTH_ERROR`(或沿用 `'403'`) | API Key 无效或无权限,请检查设置 | 是 |
| 404 | `NOT_FOUND_ERROR`(新增) | 模型或接口不存在,请检查模型名或 Base URL | 否(当前归 NETWORK_ERROR) |
| 408 | `TIMEOUT_ERROR`(新增) | 请求超时,请稍后重试 | 否 |
| 429 | `RATE_LIMIT`(或沿用 `'429'`) | 请求太频繁,请稍后重试 | 是 |
| 其他 4xx | `CLIENT_ERROR`(新增) | 请求错误(HTTP {status}),请检查配置 | 否 |
| 5xx | `SERVER_ERROR`(新增) | 服务端异常(HTTP {status}),请稍后重试 | 否 |

**HTTP 状态码提取规则**:从错误消息文本中提取 HTTP 状态码时,使用 `/\bHTTP\s*(\d{3})\b/i` 或类似正则,只匹配 "HTTP" 前缀后的状态码,避免误匹配业务码(如 B站的 `-352`、`14012` 等数字)。当前 `inferErrorCode` 用 `\b401\b` 匹配裸数字已有该风险(例如消息中若出现 "14012" 不会误匹配 401,因为 `\b401\b` 要求词边界,但 "14012" 中 401 前后是数字,不构成词边界)。新增分类需保持该严谨性。

## 错误分类设计步骤

### 步骤1:扩展入口签名(向后兼容)

当前:`inferErrorCode(message: string): string`

扩展为两个重载或新函数:

```ts
// 方案示意,非最终实现代码
// 保留原 string 入参的兼容入口
export function inferErrorCode(message: string): string
// 新增 Error/unknown 入参的扩展入口,可访问结构化字段
export function inferErrorCode(error: unknown): string
```

或新增独立函数 `inferErrorCodeFromError(error: unknown): string`,调用方逐步迁移。

**调用方迁移**:各调用点从 `inferErrorCode(err instanceof Error ? err.message : String(err))` 改为 `inferErrorCode(err)`(传入原始错误对象),使分类逻辑能访问 `err.code`、`err.cause`、`err.name`。

**向后兼容约束**:现有 `inferErrorCode(message: string)` 入参必须保留,因为已有测试和潜在的外部调用方依赖该签名。新增 `unknown` 入参不应破坏 `string` 入参的行为。

### 步骤2:定义错误分类层级

分类按优先级从高到低判断(先判断结构化字段,再回退到文本匹配):

**第一优先级:Abort/取消错误**

- `AbortError`(err.name === 'AbortError' 或 isAbortError(err) 为 true):用户主动取消或 `AbortSignal.timeout` 触发。
- 当前 `handleTestConnection` 的 `AbortSignal.timeout(10_000)` 触发的超时属于此类。
- 分类 code: `TIMEOUT_ERROR` 或 `ABORTED`(区分用户取消和超时取消需进一步判断 cause)。
- 文案: 连接超时,请检查网络或稍后重试。

**第二优先级:Node 原生网络错误码(若 err.code 存在)**

仅当 `err.code` 是字符串且匹配 Node 原生网络错误码时,归入对应分类。**不能假定所有运行时错误都有 Node 错误码**(见"根因分析"第一层)。

| Node code | 分类 code | 文案 |
| --- | --- | --- |
| `ENOTFOUND` | `DNS_ERROR` | 域名解析失败,请检查 Base URL 或网络 |
| `ECONNREFUSED` | `CONNECTION_REFUSED` | 连接被拒绝,请检查 Base URL 或服务状态 |
| `ECONNRESET` | `CONNECTION_RESET` | 连接被重置,请检查网络稳定性 |
| `ETIMEDOUT` | `TIMEOUT_ERROR` | 连接超时,请检查网络或稍后重试 |
| `EPROTO` | `TLS_ERROR` | TLS 握手失败,请检查 Base URL 协议或证书 |
| `EAI_AGAIN` | `DNS_ERROR` | 域名解析临时失败,请稍后重试 |

**第三优先级:cause 链中的 Node 错误码(若 err.cause 存在)**

fetch 底层失败时,`err.message` 可能只有 `'fetch failed'`,但 `err.cause` 携带 `code: 'ECONNREFUSED'` 等结构化字段。需递归检查 `err.cause`(最多 2 层,避免无限递归)。

**第四优先级:HTTP 状态码(从 message 或 err 中提取)**

按"HTTP 边界定义"章节提取状态码并分类。

**第五优先级:文本关键字匹配(当前已有逻辑)**

- `api key`、`auth`、`unauthorized`、`forbidden` -> `AUTH_ERROR`。
- `rate limit`、`too many requests` -> `RATE_LIMIT`。
- `timeout`、`timed out` -> `TIMEOUT_ERROR`。
- `fetch failed`、`network`、`dns`、`connect`、`socket` -> `NETWORK_ERROR`(保留作为文本回退)。

**第六优先级:兜底**

无法识别的错误 -> `UNKNOWN_ERROR`(文案:请求失败,请稍后重试)。**不再一律归为 `NETWORK_ERROR`**,避免把非网络错误误判为网络问题。

### 步骤3:文案映射扩展

在 `friendlyMessage` 中为新增分类添加文案:

| code | 文案 |
| --- | --- |
| `DNS_ERROR` | 域名解析失败,请检查 Base URL 或网络 |
| `CONNECTION_REFUSED` | 连接被拒绝,请检查 Base URL 或服务状态 |
| `CONNECTION_RESET` | 连接被重置,请检查网络稳定性 |
| `TLS_ERROR` | TLS 握手失败,请检查 Base URL 协议或证书 |
| `TIMEOUT_ERROR` | 连接超时,请检查网络或稍后重试 |
| `NOT_FOUND_ERROR` | 模型或接口不存在,请检查模型名或 Base URL |
| `CLIENT_ERROR` | 请求错误,请检查配置 |
| `SERVER_ERROR` | 服务端异常,请稍后重试 |
| `UNKNOWN_ERROR` | 请求失败,请稍后重试 |

### 步骤4:统一分类出口(消除路由层兜底缺口)

修改 `stream.ts:591-596` 的 `test_connection` 路由层兜底,使其经过 `inferErrorCode` + `friendlyMessage`:

## 验收标准

1. **入口签名扩展且向后兼容**:`inferErrorCode` 新增 `unknown` 入参,原 `string` 入参仍能正常分类,现有测试不破坏。
2. **错误分类细化**:DNS 错误、连接拒绝/重置、TLS 错误、超时、HTTP 4xx(非 401/403/429)、HTTP 5xx、Provider 配置错误等分类均有对应 code 和文案。
3. **不假定所有运行时错误都有 Node 错误码**:无 `code` 字段的错误对象回退到文本匹配和 HTTP 状态码判断,兜底为 `UNKNOWN_ERROR` 而非 `NETWORK_ERROR`。
4. **HTTP 状态码提取严谨**:业务码(如 14012、-352)不误匹配为 HTTP 401/429。
5. **统一分类出口**:`test_connection` 路由层兜底接入 `inferErrorCode` + `friendlyMessage`,不再直接返回原始 message。
6. **文案差异化**:不同根因的网络异常显示不同文案,用户能从文案推断应检查网络、API Key、Base URL、模型名还是服务端状态。
7. **cause 链递归安全**:cause 链检查最多 2 层,循环引用不无限递归。
8. **单元测试覆盖**:所有新增分类、文案、cause 链递归、HTTP 状态码提取严谨性、入口签名向后兼容均有单元测试覆盖。
9. **N-4 可接入**:N-1 定义的错误分类基础设施可被 N-4 复用,Bilibili 网络失败能映射到对应网络错误分类。

## 运行时验证

以下事项不能仅凭静态代码确认,需在阶段0 恢复 E2E 后采集运行时证据:

1. **N-V2 假设**:错误实际发生在 DNS、TLS、代理、CORS/权限、HTTP 状态码还是请求超时。需采集 DevTools Network 中的请求 URL、HTTP 状态或是否根本没有发出请求。
2. **实际触发的错误类型分布**:用户报告中"偶发网络连接失败"实际包含哪些根因。需在 service worker 控制台记录 `inferErrorCode` 实际命中的分类。
3. **Provider SDK 抛出的 Error 结构**:OpenAI/Anthropic/Ollama 等 SDK 的 Error 子类是否有 `code`、`cause` 字段,字段语义如何。需抓取实际错误对象的结构。
4. **fetch failed 的 cause 链**:V8 fetch 底层失败的 cause 链实际携带哪些字段。需在浏览器中触发网络失败并检查 Error 对象。
5. **`createModel` 在 try 外抛出的实际场景**:该路径的原始错误对象结构。需复现配置错误场景。

**运行时验证边界声明**:在运行时证据采集完成前,本方案不把"所有网络错误都能精确分类"写成已确认事实。分类逻辑的设计基于 Node 错误码和文本匹配的组合策略,但实际错误对象的字段结构需运行时确认。对于无法分类的错误,兜底为 `UNKNOWN_ERROR`,文案为"请求失败,请稍后重试"。

## 风险与回滚

### 风险

1. **分类逻辑过于细化增加维护成本**:新增分类越多,文案维护和测试覆盖成本越高。缓解:分类按"用户可据此推断检查方向"的粒度设计,不追求穷举所有错误码。例如 `ECONNREFUSED` 和 `ECONNRESET` 可合并为 `CONNECTION_ERROR`,只要文案能提示"检查网络稳定性"即可。
2. **Node 错误码的版本差异**:不同 Node 版本(或浏览器 V8 版本)的错误码可能不完全一致。缓解:分类逻辑对未识别的 code 回退到文本匹配,不硬依赖特定 code 存在。
3. **Provider SDK 的 Error 结构差异**:不同 SDK 的 Error 子类字段语义不同,可能需要 SDK 特定适配。缓解:分类逻辑优先检查通用字段(`code`、`cause`、`name`、`message`),SDK 特定字段作为可选增强,不硬依赖。
4. **入口签名扩展的调用方迁移遗漏**:若部分调用点未迁移到 `unknown` 入参,仍传 `string`,分类逻辑只能基于文本,无法访问结构化字段。缓解:步骤4 明确列出所有调用点,迁移完成后通过代码搜索确认无遗漏。
5. **文案变更影响用户认知**:现有用户已习惯"网络连接失败"文案,新增差异化文案可能让用户困惑。缓解:文案保持简洁明确,指向具体检查方向;对于无法分类的错误,兜底文案与原"网络连接失败"语义接近。
6. **cause 链递归的性能开销**:递归检查 cause 链在极端情况下可能有性能开销。缓解:限制最多 2 层递归,且 cause 链通常不超过 2 层。
7. **HTTP 状态码提取的误匹配**:若 Provider SDK 的错误 message 中包含裸数字(如 "Error 404 in model config"),可能被误匹配为 HTTP 404。缓解:HTTP 状态码提取使用 "HTTP" 前缀正则,不匹配裸数字。

### 回滚方案

如果修复引入回归问题,回滚步骤:

1. **回滚 `port-protocol.ts`**:将 `inferErrorCode` 恢复为原始的 `string` 入参和三类分类逻辑,移除新增分类。将 `friendlyMessage` 恢复为原始文案映射。
2. **回滚 `stream.ts`**:将四个调用点恢复为 `inferErrorCode(err instanceof Error ? err.message : String(err))`。将 `test_connection` 路由层兜底恢复为直接返回原始 message。
3. **保留测试**:新增分类的单元测试可保留(标记为 `skip`),便于后续重新接入。

回滚后,错误分类恢复到原始的三类粗粒度,`test_connection` 路由层兜底恢复到直接返回原始 message。回滚是纯代码还原操作,不涉及数据迁移。
