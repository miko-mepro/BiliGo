## 静态确认的过期覆盖窗口

本修复方案针对的过期覆盖窗口已通过静态代码审查完全确认，不需要运行时复现即可落地代码层修复。缺陷链路如下：

1. **Promise.race 无法被取消**：`Main/src/components/model-settings/TestConnectionButton.tsx:115-189` 的 `handleClick` 使用 `Promise.race([connectionPromise, timeoutPromise])` 等待 SW 回复或 12 秒超时。JavaScript 的 `Promise` 本身不可取消，`Promise.race` 返回的 Promise 会持续 pending 直到其中一个输入 Promise resolve。
2. **cleanup 只清理同步资源**：`:79-88` 的 `cleanup` 函数只移除 `onMessage` listener（`:81-83`）和超时 timer（`:84-87`），没有取消已经创建的 `Promise.race`。当 Provider 变化或组件卸载触发 cleanup 时，listener 和 timer 被移除，但 `connectionPromise` 和 `timeoutPromise` 仍可能 pending。
3. **Provider 变化触发 cleanup**：`:100-104` 的 `useEffect` 在 `[provider, cleanup]` 变化时执行 cleanup（effect 的 cleanup 函数在下次执行前调用）。切换 Provider 时旧 listener/timer 被清理，但旧 `Promise.race` 仍 pending。
4. **卸载触发 cleanup**：`:91-95` 的 `useEffect` 在组件卸载时执行 cleanup。同样只清理 listener/timer，不取消 Promise。
5. **过期结果覆盖新状态**：旧 `Promise.race` 在 SW 端返回 `connection_result` 后 resolve（若 listener 未被移除则 `connectionPromise` resolve；若 listener 已被移除则 `connectionPromise` 永不 resolve，但 SW 端请求仍在执行）。待旧请求 resolve 后，`:175-185` 的 `await` 返回，旧闭包继续调用 `setStatus`、`setErrorMessage`、`setIsTimeout`，可能覆盖新 Provider 的 UI 状态或在卸载后产生无效状态更新。

需要严格区分的关键点（来自问题档案 R-3 第 40 行）：

- **listener 已移除时 connectionPromise 不 resolve**：若 cleanup 已移除 `onMessage` listener，SW 后续返回的 `connection_result` 不会触发 `connectionPromise` resolve。此时 `connectionPromise` 永远 pending，`Promise.race` 只能等 `timeoutPromise` 在 12 秒后 resolve。但 `timeoutPromise` 的 timer 也可能已被 cleanup 清除（`clearTimeout` 后 timer 不再触发），导致两个 Promise 都永不 resolve，`await` 永远阻塞。
- **实际风险场景**：当 cleanup 移除了 listener 和 timer 后，`Promise.race` 的两个输入都永不 resolve，`handleClick` 的 `await` 永远阻塞，`setStatus` 等不会被调用。但若 cleanup 在 `connectionPromise` 已 resolve 之后、`await` 返回之前执行（时序窗口），旧闭包仍会在 `await` 返回后调用 `setStatus`。
- **React 闭包问题**：`handleClick` 是 `useCallback`，依赖 `[provider, port, status, cleanup]`。Provider 变化后 `handleClick` 重新创建，但旧 `handleClick` 的 `await` 仍在执行旧闭包。旧闭包持有的 `setStatus`/`setErrorMessage`/`setIsTimeout` 是 React 的 setState 函数，对同一组件实例始终有效（React 的 setState 不会因闭包过期而失效）。

### 尚未证实的崩溃

需要严格区分"静态确认的过期覆盖窗口"与"尚未证实的渲染崩溃"：

- **静态确认**：`Promise.race` 缺少取消机制，cleanup 只清理同步资源（listener、timer），未覆盖异步资源（Promise），形成半截子清理。Provider 变化或卸载后，旧请求的结果可能覆盖新状态或产生无效状态更新。
- **尚未证实**：当前没有运行时堆栈证明该路径直接导致 render crash。来源文档渲染崩溃问题记录第 76 行明确指出"当前可确认的影响是：旧 Provider 的结果可能覆盖新 Provider 的 UI 状态，或者在视图切换后产生无效状态更新。尚无运行时堆栈证明该路径直接导致 render crash"。

因此，本修复方案的目标是**引入请求代次/取消机制，使 Provider 变化或组件卸载时旧请求不再覆盖新状态或产生无效状态更新**，而非"修复已证实的渲染崩溃"。

## 触发边界

满足以下全部条件即触发"过期结果覆盖"：

### 场景1：Provider 切换覆盖

1. 用户在设置页对 Provider A 发起连接测试，`handleClick` 执行，`Promise.race` 开始等待。
2. 在 SW 返回 `connection_result` 之前（`connectionPromise` 未 resolve），用户切换到 Provider B。
3. `:100-104` 的 `useEffect` cleanup 触发，移除旧 `onMessage` listener 和旧 timer。
4. 新 Provider B 的 `handleClick` 执行，新的 `connectionPromise` 和 `timeoutPromise` 创建。
5. **关键时序窗口**：若旧 `connectionPromise` 在 listener 被移除前已收到 `connection_result` 并 resolve（SW 在 cleanup 前已发送回复），旧 `handleClick` 的 `await` 返回旧 Provider A 的结果，旧闭包调用 `setStatus`/`setErrorMessage`/`setIsTimeout`，覆盖新 Provider B 的 UI 状态。

### 场景2：组件卸载后无效状态更新

1. 用户在设置页发起连接测试，`Promise.race` 开始等待。
2. 在 SW 返回前，用户离开设置页（`Panel` 切换到聊天视图），`TestConnectionButton` 卸载。
3. `:91-95` 的 `useEffect` cleanup 触发，移除 listener 和 timer。
4. **关键时序窗口**：若旧 `connectionPromise` 在 listener 被移除前已 resolve，旧 `handleClick` 的 `await` 返回，旧闭包调用 `setStatus`/`setErrorMessage`/`setIsTimeout`，对已卸载组件执行状态更新（React 会忽略但输出警告）。

不触发的情况：

- SW 在 cleanup 前未返回 `connection_result`：listener 被移除后 `connectionPromise` 不 resolve，若 timer 也被清除则 `Promise.race` 永远阻塞，`await` 不返回，不覆盖。
- SW 在 cleanup 后返回 `connection_result`：listener 已移除，`connectionPromise` 不 resolve，不覆盖。
- 用户未切换 Provider 或未卸载组件：`handleClick` 正常执行，无过期覆盖。

## 修复目标

**为连接测试 `Promise.race` 引入请求代次/取消机制，使 Provider 变化或组件卸载时旧请求不再在 `:175-185` 完成并调用 `setStatus`、`setErrorMessage`、`setIsTimeout`。**

具体目标分解：

1. 为每次连接测试分配请求代次（generation）或取消标志，在 `handleClick` 开始时递增代次。
2. `await Promise.race` 返回后检查代次/取消标志，若已过期（Provider 变化或卸载）则跳过 `setStatus`/`setErrorMessage`/`setIsTimeout`。
3. 设计请求代次/取消/Provider 变化/组件卸载的过期结果保护，注意 React 闭包问题：旧 `handleClick` 闭包持有的 setState 函数对同一组件实例始终有效，需通过代次检查而非闭包失效来阻止过期写入。
4. 注意 cleanup：`cleanup` 移除 listener/timer 后，`Promise.race` 的两个输入可能都永不 resolve，`await` 永远阻塞。需确保代次检查在 `await` 返回后才生效，或引入使 `Promise.race` 主动 resolve 的机制（如 `AbortController` 触发 reject）。
5. 不规定未经代码确认的具体 API：本方案描述设计思路和代次/取消机制的方向，不规定 `AbortController`、`AbortSignal` 或 `controller.abort()` 的具体调用方式（这些需在代码实现时确认 React 闭包和 cleanup 的实际行为后确定）。

## 请求代次/取消机制设计

### 方向一：请求代次（generation）检查

采用递增的代次标记，每次 `handleClick` 开始时递增并记录当前代次，`await` 返回后检查代次是否仍为当前。

| 时机 | `generationRef.current` | 局部代次 | 说明 |
| --- | --- | --- | --- |
| `handleClick` 开始 | 递增后值（如 1） | 1 | 新请求发起，记录当前代次 |
| `await Promise.race` 期间 | 1（无新请求时） | 1 | Promise pending |
| Provider 变化 cleanup | 递增后值（如 2） | 1（旧闭包仍持有） | 新请求将使用代次 2，旧闭包代次 1 已过期 |
| 重新点击 `handleClick` | 递增后值（如 3） | 1（旧闭包）或 3（新闭包） | 新请求代次 3，旧闭包代次 1 已过期 |
| 组件卸载 cleanup | 递增后值（如 4） | 1（旧闭包） | 组件已卸载，旧闭包代次 1 已过期 |
| `await` 返回后 | 检查：局部代次（1）=== `generationRef.current`（4）? 否 | 1 | 代次过期，跳过状态更新 |

**优点**：简单、无外部依赖、与 R-2 的 `cancelled` 标志模式一致。

**缺点**：`await Promise.race` 可能永远阻塞（listener 和 timer 都被 cleanup 后两个 Promise 都不 resolve），代次检查永不执行。但此情况下也不会覆盖新状态（`await` 不返回则不调用 `setStatus`），只是 `handleClick` 的 Promise 永远 pending，属于资源泄漏而非状态覆盖。

### 方向二：AbortController 主动 reject

采用 `AbortController`，在 cleanup 时 `controller.abort()`，使 `Promise.race` 主动 reject 或 resolve 取消结果。

| 时机 | `controller.signal.aborted` | `Promise.race` 行为 | 说明 |
| --- | --- | --- | --- |
| `handleClick` 开始 | `false` | 正常 pending | 新请求发起 |
| `connectionPromise` 内监听 abort | `false` | 正常等待 onMessage | 监听 signal.abort 事件 |
| cleanup 调用 `controller.abort()` | `true` | `connectionPromise` resolve/reject 取消结果 | 主动结束 pending |
| `await` 返回后 | 检查：结果是否为取消结果 | 跳过状态更新 | 代次检查或结果检查 |

**优点**：`Promise.race` 主动结束，不留下永远 pending 的 Promise。

**缺点**：需在 `connectionPromise` 和 `timeoutPromise` 内监听 `signal.abort` 事件，实现复杂度较高。需确认 `AbortController` 在 React 闭包和 cleanup 中的实际行为。

### 设计决策

本方案描述两个方向的设计思路，**不规定具体采用哪个方向**。代码实现时需：

1. 确认 React 闭包中 `generationRef` 的读写时机是否正确（`useRef` 的 `.current` 在闭包中始终指向最新值，适合代次比较）。
2. 确认 `AbortController` 在 `connectionPromise` executor 内监听 `signal.abort` 的可行性（executor 内可访问 `signal`，`addEventListener` 在 cleanup 时需移除）。
3. 确认 cleanup 移除 listener/timer 后 `Promise.race` 的实际行为（两个 Promise 都不 resolve 则 `await` 永远阻塞）。
4. 评估是否需要使 `Promise.race` 主动结束（方向二）还是接受永远 pending 的 Promise 并依赖代次检查（方向一）。

无论采用哪个方向，核心验收标准是：**Provider 变化或组件卸载后，旧请求的结果不再覆盖新状态或产生无效状态更新**。

## React 闭包与 cleanup 注意事项

### React 闭包问题

`handleClick` 是 `useCallback`，依赖 `[provider, port, status, cleanup]`。Provider 变化后：

1. `handleClick` 重新创建（新闭包持有新 `provider`）。
2. 旧 `handleClick` 的 `await` 仍在执行（旧闭包持有的 `provider` 是旧值）。
3. 旧闭包持有的 `setStatus`/`setErrorMessage`/`setIsTimeout` 是 React 的 setState 函数，对同一组件实例始终有效（React 的 setState 不会因闭包过期而失效）。

因此，**不能依赖闭包失效来阻止过期写入**。必须通过代次检查（`generationRef.current` 在闭包中始终指向最新值）或取消标志来阻止。

### cleanup 与 await 的时序

`cleanup` 移除 listener 和 timer 后：

1. `connectionPromise`：若 listener 已移除，SW 后续返回的 `connection_result` 不触发 resolve，`connectionPromise` 永远 pending。
2. `timeoutPromise`：若 timer 已 `clearTimeout`，timer 不再触发，`timeoutPromise` 永远 pending。
3. `Promise.race`：两个输入都 pending，`await` 永远阻塞。

此情况下 `await` 不返回，`setStatus` 不被调用，不覆盖新状态。但 `handleClick` 的 Promise 永远 pending，属于资源泄漏（Promise 和闭包不被 GC）。

**关键时序窗口**：若 `connectionPromise` 在 cleanup 移除 listener 之前已 resolve（SW 在 cleanup 前已发送回复），但 `await` 尚未返回（事件循环尚未处理 microtask），此时 cleanup 执行移除 listener 和 timer。随后 `await` 返回已 resolve 的结果，旧闭包调用 `setStatus`。**代次检查在此窗口生效**：cleanup 时递增 `generationRef.current`，`await` 返回后检查代次过期，跳过 `setStatus`。

### cleanup 的幂等性

cleanup 需幂等：多次调用不抛错。代次递增也需幂等：多次递增只是使代次更大，旧闭包的代次检查仍失败。N-3 新增的 `onDisconnect` listener 移除也需在 cleanup 中幂等处理。

- 具体实现需确认 React 闭包和 cleanup 的实际行为后确定，本方案不规定未经代码确认的具体 API。

## 验收标准

1. **Provider 切换后旧结果不覆盖**：对 Provider A 发起测试后切换到 Provider B，Provider A 的结果返回时不覆盖 Provider B 的 UI 状态。
2. **卸载后旧结果不更新**：发起测试后卸载组件，旧请求结果返回时不调用 `setStatus`/`setErrorMessage`/`setIsTimeout`。
3. **代次检查正确**：`generationRef` 在每次 `handleClick` 开始时递增，Provider 变化 cleanup 和卸载 cleanup 中递增。`await` 返回后检查代次，过期则跳过状态更新。
4. **正常路径不受影响**：无 Provider 切换和卸载时，`connection_result` 返回后代次检查通过，`setStatus`/`setErrorMessage`/`setIsTimeout` 正常执行。
5. **React 闭包正确处理**：不依赖闭包失效阻止过期写入，通过代次检查（`generationRef.current` 在闭包中始终指向最新值）阻止。
6. **cleanup 幂等**：多次调用 cleanup（卸载 + Provider 变化）不抛错，代次递增幂等，listener/timer/onDisconnect listener（N-3 协同）不重复移除。
7. **不规定未经代码确认的具体 API**：本方案描述代次检查和 `AbortController` 两个方向的设计思路，不规定具体采用哪个方向。代码实现时确认 React 闭包和 cleanup 的实际行为后确定。
8. **不声称修复已证实崩溃**：本方案文档及实现不包含"R-3 修复了已证实的渲染崩溃"的表述，修复目标明确为"引入请求代次/取消机制，使 Provider 变化或组件卸载时旧请求不再覆盖新状态或产生无效状态更新"。
9. **单元测试覆盖**：Provider 切换、卸载、重新点击、正常路径、多次切换代次递增、cleanup 幂等路径均有单元测试覆盖。

## 风险与回滚

### 风险

1. **代次检查遗漏点**：`handleClick` 有三个状态更新点（`setStatus`、`setErrorMessage`、`setIsTimeout`），若代次检查遗漏或位置错误，过期保护不完整。缓解：代次检查统一放在 `await` 返回后、所有状态更新之前，一次检查覆盖三个写入点。
2. **Promise.race 永远 pending 的资源泄漏**：采用方向一（代次检查）时，cleanup 移除 listener/timer 后 `Promise.race` 两个输入都不 resolve，`await` 永远阻塞，`handleClick` 的 Promise 永远 pending。缓解：评估是否引入方向二（`AbortController`）使 `Promise.race` 主动结束。若不引入，需确认 pending Promise 的资源泄漏影响（闭包持有 `provider`、`port` 引用，组件卸载后 Port 被 disconnect，引用可被 GC）。
3. **代次递增时序问题**：Provider 变化 cleanup 和卸载 cleanup 都递增 `generationRef.current`。若两者时序与 `connectionPromise` resolve 的时序交叉，需确认代次检查仍能正确拦截。缓解：`generationRef.current` 只递增不重置，任何 cleanup 后旧闭包的代次都小于当前值，检查必定失败。
4. **与 N-3 共用 cleanup 的冲突**：N-3 在 cleanup 中增加 `onDisconnect` listener 移除，R-3 在 cleanup 中增加代次递增。两者共同修改 cleanup 时需保证执行顺序和幂等性。缓解：N-3 与 R-3 联合审查，统一 cleanup 的资源管理顺序（代次递增 -> 移除 onMessage listener -> 移除 onDisconnect listener -> 清除 timer）。
5. **React 18 严格模式双调用**：`useEffect` cleanup 在严格模式下双调用，代次递增会被双执行（递增两次）。缓解：代次递增幂等，双调用只是使代次更大，旧闭包检查仍失败。
6. **AbortController 的 React 闭包问题**（若采用方向二）：`AbortController` 需在 `handleClick` 内创建并通过 ref 保存，cleanup 时 `controller.abort()`。需确认 `controller` 在闭包中的引用正确，且 `signal.abort` 事件的 listener 在 cleanup 时被移除（避免 `addEventListener` 泄漏）。具体实现需确认 React 闭包和 cleanup 的实际行为后确定。

### 回滚方案

如果修复引入回归问题，回滚步骤：

1. **回滚 `TestConnectionButton.tsx`**：移除 `generationRef`，移除 `handleClick` 中的代次检查，移除 Provider 变化 cleanup 和卸载 cleanup 中的代次递增。
2. **回滚 `AbortController` 相关代码**（若采用了方向二）：移除 `AbortController` 创建、`signal.abort` 监听、`controller.abort()` 调用。
3. **回滚测试**：移除因代次/取消机制新增的单元测试。

回滚后，`Promise.race` 恢复为修复前的逻辑（cleanup 只清理 listener/timer，不取消 Promise，旧请求可能覆盖新状态），过期覆盖窗口恢复存在，但不会引入新的功能问题。回滚是纯代码还原操作，不涉及数据迁移。
