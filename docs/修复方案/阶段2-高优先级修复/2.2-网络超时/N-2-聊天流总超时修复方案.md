## 1. 问题定位

### 1.1 现象

`streamText` 调用创建了手动 `AbortController` 并传给 `streamText` 作为 `abortSignal`，但该调用没有像连接测试（10 秒）和标题生成（10 秒）那样设置 `AbortSignal.timeout(...)`。这意味着如果上游 AI 请求既不返回数据也不主动抛错，聊天会长期保持等待状态，用户表现为"发出去就转圈不回来"，无任何错误提示，也无法判断应该重试还是继续等待。

### 1.2 当前代码确认

**文件**：`Main/src/background/stream.ts:315-329`

当前 `handleChatMessage` 在创建聊天流时，手动构造 `AbortController` 用于中断控制：

```ts
// stream.ts:315-329 当前实现
const abortController = new AbortController()
session.abortController = abortController

// ... toolInputs 映射初始化 ...

const result = streamText({
  model,
  system: SYSTEM_PROMPT,
  messages: modelMessages,
  tools,
  stopWhen: isStepCount(5),
  abortSignal: abortController.signal,  // 仅传入手动 controller，未结合 timeout
})
```

该 `abortController` 用于两处外部取消：
- **用户主动停止**：`handleStop`（stream.ts:426-430）调用 `session.abortController.abort()`
- **Port 断开**：`setupPortListener`（stream.ts:564-569）的 `onDisconnect` 回调调用 `session.abortController.abort()`

但两个取消路径都没有设置独立的总超时。

### 1.3 对比：仓库中其他请求路径的超时配置

经审计，仓库中 `AbortSignal.timeout` 的调用位置包含：

| 请求路径 | 文件位置 | 超时阈值 |
| --- | --- | --- |
| 标题生成 | `stream.ts:478` | 10 秒 |
| 连接测试 | `stream.ts:541` | 10 秒 |
| Bilibili 请求（wbi/hot/tags/suggest） | `lib/bilibili-client/*.ts` | 10 秒 |
| 工具 / 视觉请求（analyze-covers / llm-json） | `tools/analyze-covers.ts:200,314`、`tools/llm-json.ts:131,150` | 30 秒 |

聊天 `streamText` 是仓库中唯一未接入总超时的 AI 请求路径。

### 1.4 根因边界

**已确认（静态代码审查）**：

1. `handleChatMessage` 创建的 `AbortController` 仅用于手动取消，未与 `AbortSignal.timeout(...)` 合并。
2. 现有 catch 块（stream.ts:398-407）通过 `isAbortError(err)` 判断 abort 错误并静默跳过。如果引入超时信号，超时触发的 abort 也会被 `isAbortError` 拦截而静默跳过，导致超时后不向用户发送任何反馈。
3. Port 心跳（ping/pong，60 秒 pong 超时）只检测 content script 与 service worker 通道是否存活，不能证明上游 AI 请求仍在推进。即便心跳正常，上游也可能已经卡死，而前端没有总超时兜底。

**待验证（需运行时证据，不作为本次代码修复的前置条件）**：

- 假设1：用户所述"偶发网络连接失败""连接超时"实际由聊天流卡死引起，但因无超时兜底，最终由其他机制触发反馈。
- 假设2：上游 AI 请求在部分网络条件下会静默挂起而非抛错，导致 `streamText` 永不 resolve。

以上假设的验证依赖运行时日志采集，不阻塞本方案的代码层修复。

## 2. 修复目标

为聊天流式请求添加独立的总超时，超时后终止流并向 UI 发送错误反馈，同时保持用户主动取消和 Port 断开的现有行为不变。

**关于超时阈值的边界声明**：本方案不臆定具体的超时数值（如 45 秒）。聊天流式场景的合理阈值需要综合考虑以下因素后由产品侧确定：

- 流式 chunk 之间的合理间隔上限（超过该间隔视为卡死）
- 推理模型（如 thinking 模式）的首 token 延迟
- 工具调用多轮（`stopWhen: isStepCount(5)`）的累计耗时
- 长回复场景的总耗时容忍度

本方案在代码中定义常量 `CHAT_STREAM_TIMEOUT_MS`，其具体数值在实施步骤1中通过产品调研确定后填入。方案给出调研维度和建议区间，但不预设固定值。

## 5. 超时与取消区分设计

### 5.1 问题：超时 abort 会被 isAbortError 静默吞掉

当前 catch 块（stream.ts:398-407）逻辑：

```ts
} catch (err) {
  if (!isAbortError(err)) {
    // 只有非 abort 错误才发送 error
    const message = err instanceof Error ? err.message : String(err)
    const code = inferErrorCode(message)
    postToPort(port, session, { type: 'error', message: friendlyMessage(code, message), code })
  }
}
```

如果直接用 `AbortSignal.any([abortController.signal, AbortSignal.timeout(N)])` 合并信号，超时触发后 `streamText` 会抛出 `AbortError`，被 `isAbortError` 拦截而静默跳过——用户看不到任何超时反馈，与现状无异。

### 5.2 方案：在 session 上记录 abort 原因

在 `PortSession` 接口上增加 `abortReason` 字段，标记 abort 的来源：

```ts
// stream.ts 修改后的 PortSession 接口
export interface PortSession extends PortState {
  abortController: AbortController | null
  // 新增：记录 abort 的来源，用于 catch 块区分超时与用户取消
  // 'timeout' = 总超时触发；'user' = 用户主动停止；'disconnect' = Port 断开
  abortReason: 'timeout' | 'user' | 'disconnect' | null
}
```

三类 abort 来源的处理策略：

| abort 来源 | 触发位置 | abortReason 设置 | catch 块行为 |
| --- | --- | --- | --- |
| 用户主动停止 | `handleStop`（stream.ts:426-430） | `'user'` | 静默跳过（保持现有行为，不发 error） |
| Port 断开 | `onDisconnect` 回调（stream.ts:564-569） | `'disconnect'` | `session.disconnected` 已为 true，`postToPort` 不发送（保持现有行为） |
| 总超时 | 超时信号回调（新增） | `'timeout'` | 发送 `{ type: 'error', message: '连接超时...', code: 'TIMEOUT' }` |

### 5.3 信号合并方式

使用 `AbortSignal.any([...])` 将手动 `abortController.signal` 与 `AbortSignal.timeout(CHAT_STREAM_TIMEOUT_MS)` 合并，传给 `streamText`：

```ts
// stream.ts handleChatMessage 内修改示意（非最终实现代码，仅说明结构）
const abortController = new AbortController()
session.abortController = abortController
session.abortReason = null

// 创建总超时信号
const timeoutSignal = AbortSignal.timeout(CHAT_STREAM_TIMEOUT_MS)

// 超时回调：标记原因并记录卡死时长
timeoutSignal.addEventListener('abort', () => {
  // 仅在尚未被其他原因 abort 时标记为超时
  if (session.abortReason === null) {
    session.abortReason = 'timeout'
    // 触发手动 controller，使 streamText 抛出 AbortError
    abortController.abort()
    // 记录上游卡死时长，便于后续与用户偶发反馈对齐（建议写入诊断日志）
    console.warn(`[N-2] 聊天流总超时触发，阈值=${CHAT_STREAM_TIMEOUT_MS}ms`)
  }
}, { once: true })

const result = streamText({
  model,
  system: SYSTEM_PROMPT,
  messages: modelMessages,
  tools,
  stopWhen: isStepCount(5),
  // 合并手动取消信号与总超时信号
  abortSignal: AbortSignal.any([abortController.signal, timeoutSignal]),
})
```

### 5.4 catch 块修改

catch 块增加对 `abortReason === 'timeout'` 的判断：

```ts
// stream.ts catch 块修改示意
} catch (err) {
  if (session.abortReason === 'timeout') {
    // 总超时触发的 abort：向用户发送超时反馈
    postToPort(port, session, {
      type: 'error',
      message: friendlyMessage('TIMEOUT', `聊天流总超时 (${CHAT_STREAM_TIMEOUT_MS}ms)`),
      code: 'TIMEOUT',
    })
  } else if (!isAbortError(err)) {
    // 非 abort 错误：保持现有行为
    const message = err instanceof Error ? err.message : String(err)
    const code = inferErrorCode(message)
    postToPort(port, session, {
      type: 'error',
      message: friendlyMessage(code, message),
      code,
    })
  }
  // abortReason === 'user' 或 'disconnect' 时：静默跳过（保持现有行为）
}
```

### 5.5 handleStop 修改

`handleStop` 在调用 `abort()` 前设置 `abortReason`：

```ts
// stream.ts handleStop 修改示意
export function handleStop(session: PortSession): void {
  if (session.abortController) {
    session.abortReason = 'user'
    session.abortController.abort()
  }
}
```

### 5.6 onDisconnect 修改

`setupPortListener` 的 `onDisconnect` 回调设置 `abortReason`：

```ts
// stream.ts setupPortListener 修改示意
port.onDisconnect.addListener(() => {
  session.disconnected = true
  session.abortReason = 'disconnect'
  if (session.abortController) {
    session.abortController.abort()
  }
})
```

### 5.7 超时参数定义

在 `stream.ts` 顶部（`SYSTEM_PROMPT` 附近）新增聊天流总超时参数。实施时必须使用阶段 1 的产品决策结果，不在本方案中预设未经确认的数值。

产品决策必须记录以下内容后，才能进入代码实现：

| 决策维度 | 需要确认的内容 |
| --- | --- |
| 流式 chunk 间隔 | 多久没有新 chunk 才视为上游无进展 |
| 首 token 延迟 | thinking 模式和慢速 Provider 是否需要额外容忍时间 |
| 工具循环 | `stopWhen: isStepCount(5)` 等多轮调用的累计耗时上限 |
| 长回复 | 长文本和连续工具调用允许的总耗时 |
| 错误呈现 | 超时是否映射到独立的错误码和用户文案 |

实施完成后，参数名称、最终数值、单位和来源必须写入对应代码注释，并在测试中使用同一参数，避免测试自行设定不同阈值。

### 5.8 friendlyMessage 对 TIMEOUT 码的处理

需要确认 `friendlyMessage('TIMEOUT', ...)` 是否返回合理文案。检查 `port-protocol.ts:104` 的 `friendlyMessage` 实现：

- 如果 `friendlyMessage` 对未知 code 返回 fallback 文案，则 `TIMEOUT` 码会回退到传入的 fallback 文本，行为正确。
- 如果 `friendlyMessage` 对未知 code 返回固定占位文案，则需在 `friendlyMessage` 的映射表中增加 `TIMEOUT` 的友好文案。

实施时需验证 `friendlyMessage` 对 `TIMEOUT` 的处理，必要时在映射表中补充。此修改属于 `port-protocol.ts` 的范围，已在"修改文件"中隐含覆盖。

### 7.2 测试实现注意事项

- **超时时间控制**：单元测试中不应等待真实的 `CHAT_STREAM_TIMEOUT_MS`（可能是 60-120 秒）。使用 `vi.useFakeTimers()` 和 `vi.advanceTimersByTime()` 控制时间，或通过依赖注入将超时阈值作为参数传入测试。
- **AbortSignal.any 兼容性**：`AbortSignal.any` 在 Node.js 20+ 和现代浏览器中可用。如果测试环境不支持，需 polyfill 或使用 `AbortSignal.any` 的替代实现。实施前需确认测试环境（vitest + jsdom / Node.js 版本）支持 `AbortSignal.any`。
- **async iterable mock**：mock `streamText` 返回的永不结束的 async iterable 需正确实现 `Symbol.asyncIterator`，避免触发 stream.ts:333-335 的"模型未返回可迭代流"防御。

## 9. 风险与回滚

### 9.1 风险

| 风险编号 | 风险 | 概率 | 影响 | 缓解措施 |
| --- | --- | --- | --- | --- |
| RK1 | 超时阈值设置过短，导致正常长回复被误判为超时 | 中 | 高 | 步骤1 产品调研综合考量推理模型和工具循环耗时；阈值取建议区间上限定 |
| RK2 | `AbortSignal.any` 在目标环境（Chrome MV3 service worker）中不可用 | 低 | 高 | Chrome 116+ 支持 `AbortSignal.any`，MV3 要求 Chrome 88+，需确认最低支持版本；如不可用则手动实现 signal 合并 |
| RK3 | 超时 abort 和用户 abort 竞争：用户在超时触发前一刻点击停止，两个 abort 同时发生 | 低 | 低 | `abortReason` 采用"先到先记"策略，`timeoutSignal.addEventListener` 中检查 `session.abortReason === null` 才标记为 timeout |
| RK4 | `friendlyMessage('TIMEOUT', ...)` 返回不合理文案 | 低 | 低 | 步骤4.2 验证并补充映射；超时 fallback 文本已包含可读信息 |
| RK5 | 超时后 `WorkingMemoryStore.release(traceId)` 未执行 | 低 | 中 | finally 块（stream.ts:408-416）保持不变，无论 abort 原因都会执行 release |
| RK6 | 超时触发时 stream 循环正在处理 tool-call，超时中断导致 tool 状态不一致 | 中 | 中 | 超时 abort 会中断 `for await` 循环，tool-call 未完成的部分不会发送 tool_result，UI 侧已有 `isLoading` 状态兜底 |

### 9.2 回滚方案

如果修复引入回归问题，回滚步骤：

1. **回滚 stream.ts**：将 `handleChatMessage` 中的 `abortSignal` 恢复为 `abortController.signal`（移除 `AbortSignal.any` 合并），移除 `timeoutSignal` 创建和回调。
2. **回滚 catch 块**：移除 `session.abortReason === 'timeout'` 分支，恢复为原始的 `if (!isAbortError(err))` 单分支。
3. **回滚 handleStop / onDisconnect**：移除 `session.abortReason` 设置语句。
4. **回滚 PortSession 接口**：移除 `abortReason` 字段。
5. **保留超时常量定义**：`CHAT_STREAM_TIMEOUT_MS` 常量本身无副作用，可保留不影响功能，便于后续重新接入。
6. **回滚测试**：移除因超时逻辑新增的单元测试。

回滚后，聊天流恢复到修复前的状态（无总超时，上游卡死时长期等待），但不会引入新的功能问题。回滚是纯代码还原操作，不涉及数据迁移。
