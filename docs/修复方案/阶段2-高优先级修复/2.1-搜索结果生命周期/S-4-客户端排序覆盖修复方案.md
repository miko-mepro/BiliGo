## 依赖声明

**S-4 强依赖 S-3 完成。** S-3 建立 `videoBatches` 批次归属模型（协议层 `batchId`/`reranked`、状态层 `UPSERT_VIDEO_BATCH`、渲染层按批次锚点内联）后，S-4 才能定义最终排序行为：

- S-4 的"rerank 标记跳过默认排序"需要读取 S-3 协议层的 `reranked` 字段。

## 问题定位

后端 `video_rerank` 重排已确认存在并推送重排后数组，但客户端默认排序在 DOM 渲染前覆盖重排顺序，且视频数组引用变化时无条件重置用户手动排序选择。问题由两个独立但叠加的路径构成：

### 路径一：客户端默认排序覆盖重排顺序

1. **`MessageList.tsx:44-47`**：默认 `sortField` 为 `'play'`。
2. **`MessageList.tsx:58-61`**：对视频调用 `applySortAndFilter(videos, sortField, dateFilter, durationFilter)`。
3. **`sort-filter.ts:32-57`**：`sortVideos` 复制数组并按所选字段降序排序。
4. **`sort-filter.ts:110-117`**：`applySortAndFilter` 先过滤、再排序。
5. **`MessageList.tsx:172-177`**：渲染的是 `processedVideos`（排序后），不是 `state.videos`（原始顺序）。

当重排顺序与播放量降序不一致时，后端送来的重排顺序在 DOM 渲染前被播放量排序覆盖。只有两种顺序恰好一致时，用户才会看到看似生效的重排。

### 路径二：排序重置覆盖用户手动选择

1. **`MessageList.tsx:49-56`**：`useEffect` 依赖 `[videos]`，`videos` 数组引用变化时执行 `setSortField('play')`、`setDateFilter('all')`、`setDurationFilter('all')`。
2. **`stream.ts:200-212`**：`video_rerank` 的双重推送会产生第二次 `{ type: 'videos', videos: reordered }`，产生新的数组引用。
3. 因此 rerank 触发时不仅覆盖重排顺序，还会把用户此前手动选择的排序（如"按最新"）重置为默认播放量排序。

### 后端重排已确认存在

- **`stream.ts:203`**：先推送 `insight(rerank)`。
- **`stream.ts:207`**：从 tool input 提取原始候选视频。
- **`stream.ts:209`**：调用 `reorderVideosByRerank(candidates, rerankResult.items)`。
- **`stream.ts:210`**：推送 `{ type: 'videos', videos: reordered }`。
- **`stream.ts:257-288`**：`reorderVideosByRerank` 按 rerankItems 的 bvid 顺序取卡片，未涉及的候选按原序追加。
- **`stream.test.ts:557-620`**：已验证输入 `[BV1, BV2, BV3]`、重排结果 `BV2, BV1, BV3` 时，推送的视频消息顺序也是 `BV2, BV1, BV3`。

### AgentInsightCard 不参与顺序

`AgentInsightCard.tsx:142-147` 的 rerank body 只展示策略、裁剪数量和保留结果数量，不读取 bvid 顺序，不参与 `processedVideos` 计算。insight 卡片对实际视频顺序没有约束作用。

## 产品排序优先级定义

**实施前必须确认的产品决策**。S-4 的修复方向取决于产品对以下优先级的定义：

### 候选优先级策略（设计选择，实施前需确认）

| 策略 | 优先级顺序 | 用户手动排序行为 | rerank 触发时行为 |
| --- | --- | --- | --- |
| A. rerank 最高优先 | rerank 顺序 > 用户手动排序 > 默认播放量 | rerank 存在时禁用或忽略用户手动排序 | 自动切换为"智能排序"，保留 rerank 顺序 |
| B. 用户手动排序最高优先 | 用户手动排序 > rerank 顺序 > 默认播放量 | 用户选择后始终生效，rerank 不覆盖 | 保留用户当前选择，rerank 顺序仅在用户未手动选择时生效 |
| C. 优先级可切换 | 用户可选择"智能排序"或"手动排序" | 用户显式选择优先级模式 | 根据用户当前模式决定是否应用 rerank 顺序 |

**推荐策略C**（优先级可切换）：在 `SortField` 中增加 `'rerank'` 选项（UI 文案"智能排序"），rerank 触发时自动切换到此选项；用户可手动切换到其他排序选项覆盖 rerank 顺序。理由：既尊重后端重排结果，又保留用户控制权。此策略与问题档案 S-4 的方案B一致。

**若产品确认策略A**（rerank 最高优先）：rerank 存在时强制使用 rerank 顺序，`SortField` 不增加选项，`MessageList` 检测 `reranked=true` 时跳过排序直接渲染原序。
**若产品确认策略B**（用户手动排序最高优先）：rerank 不改变 `sortField`，仅在 `sortField` 为默认 `'play'` 时保留 rerank 顺序（需引入"默认原序"状态）。

以下方案设计以推荐策略C为基础，标注策略A/B的差异点。

## 排序策略设计

### SortField 类型扩展

当前 `sort-filter.ts:3`：

```ts
export type SortField = 'play' | 'pubdate' | 'duration' | 'favorites';
```

**修复后（策略C推荐，设计选择，实施前确认）**：

```ts
// 修复后示意（设计选择，实施前确认）
export type SortField = 'play' | 'pubdate' | 'duration' | 'favorites' | 'rerank';
```

新增 `'rerank'` 选项，语义为"保持后端重排顺序（智能排序）"。`sortVideos` 对 `'rerank'` 不执行排序，返回原序：

```ts
// 修复后 sortVideos 示意（非最终实现代码）
export function sortVideos(videos: BilibiliVideoCard[], sortField: SortField): BilibiliVideoCard[] {
  if (sortField === 'rerank') {
    return [...videos];   // 保持原序，仅复制数组避免突变
  }
  const sorted = [...videos];
  sorted.sort((a, b) => {
    switch (sortField) {
      case 'play': return b.play - a.play;
      case 'favorites': return b.favorites - a.favorites;
      case 'pubdate': return b.pubdate - a.pubdate;
      case 'duration': {
        const durationA = parseDurationToSeconds(a.duration);
        const durationB = parseDurationToSeconds(b.duration);
        return durationB - durationA;
      }
      default: return 0;
    }
  });
  return sorted;
}
```

**策略A差异**：不增加 `'rerank'` 选项，`MessageList` 检测 `reranked=true` 时跳过 `applySortAndFilter` 的排序步骤，直接用过滤后的数组。

### 默认 sortField

**当前**：`MessageList.tsx:45` 默认 `useState<SortField>('play')`。

**修复后（策略C推荐，设计选择，实施前确认）**：

- 新批次首次到达（`bilibili_search` 推送，`reranked=false`）：默认 `sortField='play'`（保持旧行为，用户习惯按播放量看）。
- rerank 更新同批次（`video_rerank` 推送，`reranked=true`）：自动切换 `sortField='rerank'`，保留后端重排顺序。

**策略B差异**：rerank 不自动切换 `sortField`，仅在 `sortField` 仍为默认 `'play'` 时保留 rerank 顺序（需引入"是否为用户主动选择"的状态标记）。

## 保持原序策略

### 当前重置 effect

`MessageList.tsx:49-56`：

```ts
useEffect(() => {
  setSortField('play');
  setDateFilter('all');
  setDurationFilter('all');
}, [videos]);
```

问题：`videos` 引用变化（包括 rerank 的第二次推送）触发重置，覆盖用户手动选择。

### 修复后重置 effect（依赖 S-3 批次）

**设计选择（实施前需确认）**：重置 effect 的依赖从 `[videos]` 改为 `[currentBatchId]`（仅新批次时重置），rerank 更新同批次（batchId 不变）时不重置。

```ts
// 修复后示意（非最终实现代码，依赖 S-3 的批次结构）
// currentBatchId = state.videoBatches 中最新批次的 batchId
const currentBatchId = state.videoBatches.at(-1)?.batchId;

useEffect(() => {
  // 新批次到达时重置筛选为默认值
  setSortField('play');
  setDateFilter('all');
  setDurationFilter('all');
}, [currentBatchId]);
```

rerank 更新同批次时 `currentBatchId` 不变，effect 不触发，用户手动排序选择保留。

### rerank 自动切换 sortField

rerank 推送到达时（`reranked=true`），自动切换 `sortField` 为 `'rerank'`（策略C）：

```ts
// 修复后示意（非最终实现代码，依赖 S-3 的批次结构）
// 检测最新批次是否经过 rerank
const currentBatch = state.videoBatches.at(-1);

useEffect(() => {
  if (currentBatch?.reranked === true) {
    // rerank 更新到达时自动切换为智能排序，保留后端重排顺序
    setSortField('rerank');
  }
}, [currentBatch?.reranked, currentBatch?.batchId]);
```

**注意**：此 effect 与重置 effect 协作。新批次首次到达（`reranked=false`）时重置 effect 触发（`currentBatchId` 变化），设为 `'play'`；rerank 更新同批次时（`currentBatchId` 不变，`currentBatch.reranked` 变为 `true`）此 effect 触发，设为 `'rerank'`。两个 effect 依赖不同，不会冲突。

## 用户手动排序策略

### 当前用户排序

`FilterSortControls.tsx:69-80` 将排序选择回调到 `MessageList.tsx:162-168`，之后 `applySortAndFilter` 按用户选择排序。

### 修复后用户排序（依赖 S-3 批次渲染）

**设计选择（实施前需确认）**：用户排序状态按批次独立维护还是全局共享？

| 策略 | 方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 全局共享 | 单个 `sortField` 状态应用于所有批次 | 实现简单，与当前行为一致 | 旧批次的排序选择影响新批次 |
| 按批次独立 | `Map<batchId, { sortField, dateFilter, durationFilter }>` | 各批次排序互不影响 | 实现复杂，需要 S-3 的 `VideoBatchBlock` 组件持有独立状态 |

**推荐按批次独立**（依赖 S-3 的批次渲染结构）：S-3 将视频网格改为按批次内联渲染（`VideoBatchBlock` 组件），每个 `VideoBatchBlock` 持有独立的 `sortField`/`dateFilter`/`durationFilter` 状态。用户对旧批次的排序不影响新批次。

**若 S-3 采用全局渲染**（非按批次独立）：保持全局 `sortField` 状态，但重置 effect 依赖 `currentBatchId` 而非 `videos` 引用，保证 rerank 更新同批次时不重置。

**设计选择（实施前需确认）**：`'rerank'` 选项是否始终可见，还是仅在 `reranked=true` 时可见？推荐始终可见（用户可随时切换回智能排序），但如果当前批次未经过 rerank，选择 `'rerank'` 时等同于保持原搜索顺序。

## 验收标准

1. **rerank 标记到达协议层**：`video_rerank` 推送的重排数组携带 `reranked: true`，`bilibili_search` 推送时 `reranked` 为 `false` 或省略。
2. **DOM 最终顺序为重排顺序**：当后端已重排（`reranked=true`）时，DOM 中视频卡片的渲染顺序为 rerank 重排顺序，而非播放量降序。验收方式：构造 rerank 顺序与播放量降序不一致的场景，断言 DOM 顺序。
3. **用户手动排序可覆盖 rerank**：用户手动选择"播放量"/"发布时间"等排序后，DOM 顺序按用户选择，rerank 顺序被覆盖（策略C，实施前确认）。
4. **rerank 自动切换智能排序**：rerank 推送到达时 `sortField` 自动切换为 `'rerank'`（策略C），保留后端重排顺序。
5. **视频数组引用变化时保留用户排序**：rerank 的第二次推送（同批次 `batchId` 不变）不触发 `sortField` 重置，用户手动排序选择保留。验收方式：用户选择"按最新"后触发 rerank，断言 `sortField` 未被重置为 `'play'`。
6. **新批次时重置排序**：新搜索产生新批次（`batchId` 变化）时，`sortField` 重置为默认值 `'play'`。
7. **`SortField` 增加 `'rerank'` 选项**：`SortField` 类型包含 `'rerank'`，`sortVideos` 对 `'rerank'` 保持原序，`FilterSortControls` 下拉包含"智能排序"选项。
8. **用户排序状态**：若 S-3 采用按批次独立渲染，各批次 `sortField` 独立维护，互不影响。若全局共享，rerank 同批次更新时不重置。
9. **单元测试覆盖**：`sortVideos` 的 `'rerank'` 场景、`stream.ts` rerank 推送标记、`isSWMessage` reranked 校验均有单元测试。
10. **组件测试覆盖**：`MessageList` 的 rerank DOM 顺序、用户手动排序覆盖、同批次不重置、新批次重置均有组件测试。
11. **E2E 冒烟**（依赖阶段0）：rerank 后 DOM 顺序为重排顺序，用户排序行为符合产品确认策略。
12. **依赖 S-3**：本方案所有验收标准以 S-3 完成（协议层 `batchId`/`reranked`、状态层 `videoBatches`、渲染层批次锚点）为前提。

## 风险与回滚

### 风险

1. **产品优先级未确认导致返工**：S-4 的修复方向（策略A/B/C）取决于产品决策。若未确认就实施，可能需要返工。缓解：步骤1 为前置决策确认，确认前不进入步骤2-6。
2. **`'rerank'` 选项语义歧义**：用户可能不理解"智能排序"的含义。缓解：UI 文案明确（如"智能排序（按相关性）"），并在 rerank 未触发时禁用或灰显此选项（设计选择，实施前确认）。
3. **rerank 自动切换与用户预期冲突**：用户手动选择"播放量"后，rerank 推送自动切换为"智能排序"可能不符合预期（用户可能希望保持播放量排序）。缓解：策略C 的自动切换仅在用户未手动选择时触发；若用户已手动选择，保留用户选择（引入"是否为用户主动选择"标记）。实施前确认此边界。
4. **按批次独立排序状态增加复杂度**：若 S-3 采用 `VideoBatchBlock` 按批次独立渲染，每个批次持有独立 `sortField` 状态，状态管理复杂度增加。缓解：状态封装在 `VideoBatchBlock` 内部，`MessageList` 不感知。
5. **S-3 批次渲染结构变更影响**：S-3 将全局视频网格改为按批次内联渲染，S-4 的 `sortField` 状态位置随之变化。若 S-3 方案变更，S-4 需同步调整。缓解：S-4 步骤4 明确依赖 S-3 步骤6。
6. **rerank 未触发时选择"智能排序"**：用户在未经 rerank 的批次上选择"智能排序"时，`sortVideos` 保持原搜索顺序（非重排顺序）。这可能让用户困惑。缓解：UI 提示"智能排序在 AI 重排后生效"，或未经 rerank 时灰显此选项（设计选择，实施前确认）。
7. **S-1 因果链上游影响**：S-1（即时展示）修复可能改变 rerank 推送时机，影响 S-4 的 `reranked` 标记消费时序。缓解：阶段2 完成后修复 S-1 时回查 S-4 的标记消费是否仍成立。

### 回滚方案

如果修复引入回归问题，回滚步骤：

1. **回滚 `sort-filter.ts`**：将 `SortField` 恢复为 `'play' | 'pubdate' | 'duration' | 'favorites'`，移除 `'rerank'` 选项，`sortVideos` 恢复原逻辑。
2. **回滚 `FilterSortControls.tsx`**：将 `SORT_OPTIONS` 恢复原四项，移除"智能排序"。
3. **回滚 `MessageList.tsx`**：
   - 重置 effect 依赖恢复为 `[videos]`。
   - 移除 rerank 自动切换 effect。
   - `sortField` 默认值恢复为 `'play'`。
4. **回滚 `stream.ts`**：`video_rerank` 推送移除 `reranked: true` 标记（若 S-3 未回滚协议层，`reranked` 字段保留但不被消费）。
5. **回滚 `port-protocol.ts`**：`videos` 分支的 `reranked` 字段若 S-3 未回滚则保留（可选字段，不影响功能）。
6. **回滚测试**：移除因 rerank 排序逻辑新增的单元测试和组件测试。

回滚后，客户端默认播放量排序覆盖 rerank 顺序的问题恢复到修复前状态，但不会引入新的功能问题。回滚是纯代码还原操作，不涉及数据迁移。若 S-3 同时回滚，则 `videoBatches` 恢复为扁平 `videos`，S-4 的批次依赖随之消失。
