# S-3 视频结果缺少批次归属模型 - 修复方案

## 问题标识

- **问题编号**: S-3
- **严重程度**: HIGH
- **问题类型**: 状态管理 / 数据生命周期
- **所属阶段**: 阶段2 - 高优先级修复
- **修复状态**: completed
- **问题档案**: `docs/问题档案/02-状态管理与数据生命周期/S-3-视频结果缺少批次归属模型.md`
- **调查依据**: `docs/搜索结果展示与重排问题记录.md`
- **发现日期**: 2026-08-01
- **关联问题**: S-1（即时展示）、S-4（客户端排序覆盖，强依赖本方案）、R-1（状态数据字段校验）

## 问题定位

视频结果在协议层、状态层和渲染层均缺少批次归属信息，表现为一条"直接替换"链路：

1. **协议层无批次字段**：`Main/src/background/port-protocol.ts:6-17` 的 `SWMessage` 联合类型中，`videos` 分支仅为 `{ type: 'videos'; videos: BilibiliVideoCard[] }`（第 11 行），没有批次标识、消息锚点或来源标记。`isSWMessage`（第 43-44 行）只校验 `Array.isArray(record.videos)`，不校验批次字段。

2. **service worker 无批次生成**：`Main/src/background/stream.ts:175-225` 的 `postToolAuxiliaryMessages` 在 `bilibili_search`（第 182-185 行）和 `video_rerank`（第 200-212 行）两个分支推送 `{ type: 'videos', videos: ... }` 时，均不携带任何批次标识。`video_rerank` 分支（第 207-211 行）先调用 `extractVideoCandidates(toolInput)` 提取候选，再调用 `reorderVideosByRerank`（第 257-288 行）重排，最后推送重排后数组——但这第二次推送与第一次推送之间没有任何关联字段，content script 无法区分"同一批搜索的重排更新"与"新搜索的结果"。

3. **状态层直接替换**：`Main/src/content/chat-context.tsx:177-178` 的 `SET_VIDEOS` reducer 执行 `return { ...state, videos: action.payload }`，直接替换全局 `state.videos`。`ChatState`（第 94-108 行）只有 `videos: BilibiliVideoCard[]`，没有 `searchId`/`batchId`/`messageId`/`anchorId`。而 understanding、expansion、rerank（第 283-308 行）采用追加策略并记录 `receivedAt`，二者生命周期不一致。

4. **渲染层无锚点**：`Main/src/components/MessageList.tsx:19-23` 的 `RenderItem` 只包含 `message` 和三种 `insight`，不包含视频批次项。第 144-195 行的渲染结构中，视频筛选控件（第 161-170 行）和视频网格（第 172-177 行）位于 `renderItems.map()` 之后统一输出，独立于具体消息——没有"某条 assistant 消息下面挂一组视频"的渲染模型。

5. **持久化层为扁平数组**：`Main/src/content/chat-context.tsx:83-92` 的 `PersistedConversation`（version 1）和 `Main/src/lib/shared-types/index.ts:116-126` 的 `ConversationData`（version 2）均保存 `videos: BilibiliVideoCard[]` 扁平数组，无批次结构。

**确认结论**：`SET_VIDEOS` 直接替换全局数组是已静态确认的行为，新搜索会顶掉旧视频卡片，用户期望的"旧卡片留在旧输出下、新卡片留在新输出下"无法实现。旧 insight 追加保留而视频替换，产生语义错配。

## 依赖关系

- **硬依赖**：无。S-3 的根因（协议/状态/渲染三层缺少批次归属）已由静态代码证据完全确认，不依赖运行时证据即可完成设计。
- **软依赖**：S-3 的 E2E 冒烟验证（验证旧视频挂在旧输出下）依赖阶段0 恢复 content script 挂载能力。阶段0 已完成，S-3 的该项运行时依赖已解除。
- **下游强依赖**：**S-4（客户端排序覆盖）强依赖 S-3**。S-3 完成协议、状态和渲染层的批次归属模型后，S-4 才能定义最终排序行为——排序重置和覆盖需要以批次为锚点。若先修 S-4，排序逻辑没有批次锚点可挂载。
- **关联问题**：
  - S-1（即时展示）是 S-3 的因果链上游，归入阶段3。S-1 修复可能改变 S-3 的前提假设，阶段2 完成后修复 S-1 时需回查。
  - R-1（历史标题类型校验）共享"状态数据缺少字段级校验"风险。S-3 引入批次字段时必须同步加入字段校验（参考 R-1 的 `sanitizeHistoryIndex` 模式），避免新字段再次出现类型缺失导致的 render crash。

## 协议层设计

### 当前协议

```ts
// port-protocol.ts:6-17（当前）
export type SWMessage =
  | { type: 'videos'; videos: BilibiliVideoCard[] }
  | ...
```

### 设计方案

`videos` 消息增加批次归属字段，使 content script 能重建"这组视频属于哪一次搜索"的归属关系。

**候选字段名（设计选择，实施前需确认）**：

| 候选字段 | 类型 | 用途 | 备选方案 |
| --- | --- | --- | --- |
| `batchId` | `string` | 搜索批次唯一标识，同一搜索的 rerank 更新复用此值 | `searchId`、`batchSeq` |
| `reranked` | `boolean` | 标记本次推送是否为 rerank 重排结果（供 S-4 使用） | `source: 'search' \| 'rerank'`、`isRerank: true` |
| `anchorMessageTimestamp` | `number`（可选） | 视频批次在消息流中的渲染锚点时间戳 | `anchorMessageId`、`anchorIndex` |

**推荐方案（设计选择，实施前需确认）**：

```ts
// 修复后协议示意（非最终实现代码，字段名为设计选择）
| { type: 'videos'; videos: BilibiliVideoCard[]; batchId: string; reranked?: boolean }
```

- `batchId`：必填，SW 在 `bilibili_search` 推送时生成（如 `search_<toolCallId>` 或 `search_<Date.now()>_<random>`），`video_rerank` 推送时复用同一值。
- `reranked`：可选，默认 `false`。`bilibili_search` 推送时不携带或为 `false`，`video_rerank` 推送时为 `true`。此字段供 S-4 使用，S-3 本身不依赖它改变渲染行为。
- **不采用 `anchorMessageTimestamp`**：渲染锚点由 content state 按视频批次到达时间自行推导（取批次创建时的最后一条 assistant 消息时间戳），不需要协议层传递。如果实施时发现时间推导不稳定，再考虑协议层显式传递锚点。

### `isSWMessage` 校验扩展

`isSWMessage`（第 43-44 行）的 `videos` case 当前只校验 `Array.isArray(record.videos)`。修复后增加 `batchId` 字段校验：

```ts
// 修复后校验示意（非最终实现代码）
case 'videos':
  return Array.isArray(record.videos)
    && typeof record.batchId === 'string'
    && record.batchId.length > 0
    && (record.reranked === undefined || typeof record.reranked === 'boolean')
```

**旧消息兼容**：如果 `batchId` 缺失（旧版本 SW 推送的消息），`isSWMessage` 应拒绝还是降级？设计选择（实施前需确认）：
- **方案A（拒绝）**：`batchId` 缺失时 `isSWMessage` 返回 `false`，消息被丢弃。风险：SW/CS 版本不一致时视频不显示。
- **方案B（降级）**：`batchId` 缺失时 `isSWMessage` 仍返回 `true`，`consumeSWMessage` 内部生成临时 `batchId`（如 `legacy_<Date.now()>`）。推荐此方案，保证向后兼容。

## service worker 批次生成/复用

### 当前推送路径

```
bilibili_search tool-result
  → postToolAuxiliaryMessages(port, session, 'bilibili_search', output, toolInput)
    → postToPort(port, session, { type: 'videos', videos: output })     // 第 184 行

video_rerank tool-result
  → postToolAuxiliaryMessages(port, session, 'video_rerank', output, toolInput)
    → postToPort(port, session, { type: 'insight', kind: 'rerank', data })  // 第 203 行
    → candidates = extractVideoCandidates(toolInput)                        // 第 207 行
    → reordered = reorderVideosByRerank(candidates, rerankResult.items)    // 第 209 行
    → postToPort(port, session, { type: 'videos', videos: reordered })     // 第 210 行
```

### 批次标识生成

**候选生成策略（设计选择，实施前需确认）**：

| 策略 | 生成时机 | 生成方式 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| A. toolCallId 派生 | `bilibili_search` tool-result 时 | `batchId = 'search_' + toolCallId` | 与工具调用一一对应，可追溯 | 需要 `postToolAuxiliaryMessages` 接收 `toolCallId` 参数 |
| B. 时间戳+随机 | `bilibili_search` tool-result 时 | `batchId = 'search_' + Date.now() + '_' + Math.random()` | 不依赖 toolCallId，改动小 | 无法从 batchId 反查工具调用 |
| C. 会话级计数器 | `bilibili_search` tool-result 时 | `session.searchBatchCount += 1; batchId = 'search_' + session.searchBatchCount` | 简洁，会话内有序 | 需要 `PortSession` 增加计数器字段 |

**推荐策略A**：`batchId` 由 `bilibili_search` 的 `toolCallId` 派生，因为 `toolCallId` 在 tool-result 事件中可用（`part.toolCallId`，第 354-358 行），且天然唯一。需要将 `postToolAuxiliaryMessages` 的签名增加 `toolCallId` 参数。

### rerank 批次复用

`video_rerank` 推送重排后视频时，需要复用对应 `bilibili_search` 的 `batchId`，使 content state 将其识别为"同一批次的更新"而非"新批次"。

**候选复用策略（设计选择，实施前需确认）**：

| 策略 | 复用方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 会话级 lastSearchBatchId | `PortSession` 增加 `lastSearchBatchId?: string`；`bilibili_search` 推送时设置；`video_rerank` 推送时读取 | 实现简单，适配标准工作流（先搜索后重排） | 多次搜索后才重排时可能误关联到最新搜索 |
| B. bvid 集合匹配 | `video_rerank` 推送时，将候选 bvid 集合与所有已推送批次的 bvid 集合比对，取匹配批次 | 鲁棒，不依赖时序 | 实现复杂；候选被模型修改时匹配失败 |
| C. toolInput 注入 | 在 `bilibili_search` tool-result 时将 `batchId` 写入 WorkingMemory，`video_rerank` 工具执行时从 WorkingMemory 读取 | 解耦推送层 | 需要修改 `video_rerank` 工具实现，超出 S-3 范围 |

**推荐策略A**：会话级 `lastSearchBatchId`。理由：SYSTEM_PROMPT（`stream.ts:32-44`）规定工作流为"搜索 → 重排"，标准流程中 rerank 紧跟 search。`stopWhen: isStepCount(5)` 限制了单次会话工具调用轮数，多次搜索后才重排的场景极少。若实施时确认存在多次搜索场景，再升级为策略B。

### Action 变更

```ts
// 当前（第 114 行）
| { type: 'SET_VIDEOS'; payload: BilibiliVideoCard[] }

// 修复后示意（设计选择，实施前需确认）

  // insight
  understandings.forEach((data) => { items.push({ type: 'understanding', data }) })
  // 视频批次（新增）
  state.videoBatches.forEach((batch) => { items.push({ type: 'video-batch', batch }) })
  // 按时间排序
  items.sort((a, b) => getRenderItemTime(a) - getRenderItemTime(b))
  return items
}, [state.messages, state.videoBatches, understandings, ...])
```

`getRenderItemTime` 增加 `video-batch` 分支，返回 `batch.anchorTimestamp`。

渲染时，`video-batch` 项内联渲染该批次的 `FilterSortControls` + `bili-agent-video-grid`：

```tsx
// 修复后渲染示意（非最终实现代码）
{renderItems.map((item, idx) => {
  if (item.type === 'video-batch') {
    return (
      <VideoBatchBlock key={`batch-${item.batch.batchId}`} batch={item.batch} />
    )
  }
  // ... 其余分支不变

```

`VideoBatchBlock` 是新组件（或在 MessageList 内联），负责渲染该批次的筛选控件和视频网格。**设计选择（实施前需确认）**：每个批次独立维护筛选/排序状态，还是共享全局状态？推荐每个批次独立（用户对旧批次的排序不应影响新批次），但实现成本更高。实施时需确认。

### 全局视频网格移除

当前第 161-178 行的全局 `FilterSortControls` 和 `bili-agent-video-grid` 移除，改为内联到 `video-batch` 渲染项中。`processedVideos` 的 `useMemo`（第 58-61 行）移到 `VideoBatchBlock` 内部，按批次独立计算。

## 批次生命周期

| 事件 | 批次操作 | 说明 |
| --- | --- | --- |
| `bilibili_search` 推送 videos | 创建新批次（`UPSERT_VIDEO_BATCH`，batchId 不存在时追加） | 新搜索产生新批次 |
| `video_rerank` 推送 videos | 更新同批次（`UPSERT_VIDEO_BATCH`，batchId 已存在时更新 videos + reranked=true） | rerank 是同一搜索的重排更新 |
| 用户发起新消息（`send`） | 不主动清除批次 | 旧批次保留在历史中 |
| `CLEAR_MESSAGES`（清空对话） | 清除所有批次（`CLEAR_VIDEO_BATCHES`） | 新对话从空开始 |
| `HYDRATE` / `REHYDRATE` | 从持久化数据恢复批次 | 加载历史会话时恢复旧批次 |
| 组件卸载 | 批次随 ChatState 销毁 | 无特殊清理 |

### 批次上限

**设计选择（实施前需确认）**：是否限制单会话最大批次数？推荐不限制（批次随消息流自然累积，且 `MAX_PERSISTED_MESSAGES=200` 已限制消息数量），但实施时需确认大量批次对渲染性能的影响（见"性能风险"）。

## 旧数据兼容边界

### 持久化结构兼容

当前持久化结构（`PersistedConversation` version 1、`ConversationData` version 2）保存扁平 `videos: BilibiliVideoCard[]`。

**兼容策略（设计选择，实施前需确认）**：

| 策略 | 方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 版本号升级 | `PersistedConversation` 升至 version 2，`ConversationData` 升至 version 3，新增 `videoBatches` 字段 | 结构清晰，旧版本可拒绝 | 需要处理版本迁移 |
| B. 向后兼容字段 | 保持 version 不变，新增 `videoBatches?` 可选字段；读取时若 `videoBatches` 缺失但 `videos` 存在，迁移为单批次 | 无版本迁移风险 | 两个字段并存增加复杂度 |

**推荐策略B**：向后兼容字段。`store.ts` 的 `loadConversation`（第 139-153 行）和 `loadLocalCache`（第 204-218 行）读取后，若 `videoBatches` 缺失但 `videos` 为非空数组，构造单批次 `{ batchId: 'legacy_<conversationId>', videos, anchorTimestamp: 0, receivedAt: 0, reranked: false }`。`HYDRATE`/`REHYDRATE` reducer 接收迁移后的批次结构。

### 迁移边界

- **存储中已有的旧数据**：通过上述降级迁移处理，不需要主动回写清理（与 R-1 的静默降级策略一致）。
- **跨标签页同步**：`sync.ts` 的 listener 同样需要处理旧结构数据（若未来接入视频批次同步）。
- **SW/CS 版本不一致**：如果旧版本 SW 推送无 `batchId` 的 `videos` 消息，`consumeSWMessage` 生成临时 `batchId`（见"协议层设计"的降级方案B）。
- **字段校验（参考 R-1）**：批次字段引入时必须加入运行时校验，`batchId` 非字符串时降级为临时值，`videos` 非数组时丢弃整条消息。避免 R-1 类的 render crash。

## 验收标准

1. **批次归属模型建立**：`ChatState` 包含 `videoBatches: VideoBatch[]`，每个批次携带 `batchId`、`videos`、`anchorTimestamp`、`receivedAt`、`reranked`。
2. **协议层携带批次字段**：`videos` 消息包含 `batchId`（必填）和 `reranked`（可选），`isSWMessage` 校验 `batchId` 为非空字符串。
3. **SW 批次生成/复用**：`bilibili_search` 推送时生成 `batchId`，`video_rerank` 推送时复用同一 `batchId`，两次推送的 `batchId` 相同。
4. **状态层 upsert**：`UPSERT_VIDEO_BATCH` 按 `batchId` 更新而非替换全局数组，rerank 的第二次推送更新同一批次。
5. **渲染层批次锚点**：视频网格按批次 `anchorTimestamp` 插入消息流，旧视频留在旧输出下，新视频在新输出下。
6. **旧数据兼容**：持久化中扁平 `videos` 数组在加载时迁移为单批次，不丢失数据，不崩溃。
7. **字段校验**：批次字段（`batchId`、`videos`）有运行时校验，非法数据降级或丢弃，不产生 render crash（参考 R-1 教训）。
8. **insight 与视频归属一致**：旧 insight 与旧视频按时间锚点对齐，不再出现"旧 insight 留在消息流中而视频网格已替换"的语义错配。
9. **单元测试覆盖**：`UPSERT_VIDEO_BATCH` reducer、`consumeSWMessage` videos 消费者、`postToolAuxiliaryMessages` 批次生成/复用、旧数据迁移均有单元测试。
10. **组件测试覆盖**：`MessageList` 批次渲染、两批次保留、rerank 更新同批次均有组件测试。
11. **save-orchestrator 兼容**：`hasAiActivity`、`buildStoredConversationPayload`、`buildMigrationPayload` 正确读取批次结构，保存时写入 `videoBatches`。
12. **E2E 冒烟**（依赖阶段0）：两次搜索的旧视频保留在旧输出下，未被顶掉。

## 性能风险

1. **多批次渲染开销**：单会话多次搜索时，`videoBatches` 可能累积多个批次，每个批次独立渲染 `FilterSortControls` + `bili-agent-video-grid`。在极端场景（如 10 次搜索 × 20 条视频/批）下，DOM 节点数增加。缓解：批次内视频网格可设最大渲染数（如 50 条），超出部分折叠。实施时需确认实际搜索频次和批次累积上限。
2. **renderItems 排序开销**：`renderItems` 的 `useMemo`（第 63-91 行）合并消息 + insight + 视频批次后排序，批次增加时排序数组变长。缓解：批次数量远小于消息数量（典型场景 < 5 批 vs 200 条消息），排序开销可忽略。
3. **持久化体积**：保存全部批次会增加 `chrome.storage.local` 写入体积。缓解：`MAX_PERSISTED_MESSAGES=200` 已限制消息数量，批次数量与之同量级，存储配额（10MB）充裕。实施时需确认。
4. **派生选择器调用频率**：`selectCurrentVideos` 每次 render 调用，遍历 `videoBatches` 取最后一项。缓解：`Array.prototype.at(-1)` 为 O(1)，无性能问题。

## 风险与回滚

### 风险

1. **三层改动回归面广**：S-3 涉及协议层（`port-protocol.ts`）、状态层（`chat-context.tsx`）、渲染层（`MessageList.tsx`）和持久化层（`store.ts`、`save-orchestrator.ts`）四层改动。缓解：分步实施——先协议层加字段（步骤2），再状态层 upsert（步骤4-5），再渲染层锚点（步骤6），最后持久化兼容（步骤7）。每步完成后运行已有测试确认无回归。
2. **`postToolAuxiliaryMessages` 签名变更**：增加 `toolCallId` 参数会影响所有调用处。当前仅第 357 行一处调用。缓解：签名变更后立即更新调用处，编译检查。
