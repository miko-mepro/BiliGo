## 1. 问题定位

### 1.1 现象

`MessageList` 组件使用 `useEffect` 监听流式文本、推理文本、render item 数量和视频数组，这些依赖任一变化都会无条件调用 `scrollIntoView({ behavior: 'smooth' })`。用户在流式输出期间手动上拉阅读历史内容时，下一个 chunk、reasoning 或视频数组更新会再次触发滚动，把视图强行拉回底部，打断阅读。

### 1.2 当前代码确认

**文件**：`Main/src/components/MessageList.tsx:93-96`

当前自动滚动 effect：

```tsx
// MessageList.tsx:93-96 当前实现
// Auto-scroll to bottom when new messages arrive
useEffect(() => {
  messagesEndRef.current?.scrollIntoView({ behavior: 'smooth' });
}, [renderItems.length, state.streamingContent, state.streamingReasoning, videos]);
```

四类 effect 依赖触发时机：

| 依赖项 | 触发时机 | 触发频率 | 派发路径 |
| --- | --- | --- | --- |
| `renderItems.length` | 新消息或新 insight 进入合并列表 | 低频 | renderItems useMemo 重新计算 |
| `state.streamingContent` | 每个流式文本 chunk 更新 | 高频 | chat-context.tsx:395-397 派发 `APPEND_STREAMING` |
| `state.streamingReasoning` | 推理文本更新 | 高频 | chat-context.tsx:400-402 派发 `APPEND_REASONING` |
| `videos` | Search 或 rerank 推送新数组 | 中频 | chat-context.tsx:428-431 派发 `SET_VIDEOS` |

### 1.3 根因分析

问题的核心在于自动滚动 effect 缺少"用户正在阅读"的保护条件，且依赖项覆盖了所有高频更新源。

**缺失的保护机制**（经静态确认 MessageList.tsx 中不存在）：

- 监听滚动容器并判断用户是否接近底部
- `isAtBottom`、`userScrolled` 或类似状态
- 用户主动上拉后暂停自动滚动的标记
- 仅在新消息到达且用户已经位于底部时滚动的条件判断

**派发路径证据**：

- `chat-context.tsx:395-397`：chunk 到达时派发 `APPEND_STREAMING`，更新 `state.streamingContent`
- `chat-context.tsx:400-402`：reasoning 到达时派发 `APPEND_REASONING`，更新 `state.streamingReasoning`
- `chat-context.tsx:428-431`：视频消息到达时派发 `SET_VIDEOS`，更新 `state.videos`

因此，用户在流式输出期间手动上拉时，只要继续收到 chunk、reasoning 或视频数组更新，就会再次触发滚动到底部。

**insight 卡片的局部状态**：`AgentInsightCard` 的 `isExpanded` 是局部状态，展开/收起本身不在 effect 依赖中。但如果展开期间又有流式状态更新（chunk、reasoning），后续依赖变化仍会把视图拉到底部，打断用户的展开阅读。

### 1.4 滚动容器结构确认

**文件**：`Main/src/components/MessageList.tsx:122-195`

```tsx
// MessageList.tsx:122 滚动容器
<div ref={containerRef} className="bili-agent-message-list">
  {/* ... messages 渲染 ... */}
  {/* MessageList.tsx:194 滚动锚点 */}

```

- `containerRef`（line 42）：指向滚动容器 `<div className="bili-agent-message-list">`
- `messagesEndRef`（line 41）：指向容器底部的锚点 `<div>`
- 当前 `scrollIntoView` 在 `messagesEndRef` 上调用，滚动的是整个 `bili-agent-message-list` 容器

> **注意**：`scrollIntoView` 滚动的是最近的可滚动祖先元素。需在实施时确认 `bili-agent-message-list` 本身是否设置了 `overflow: auto/scroll`，还是其更外层祖先滚动。这影响 onScroll 监听目标的位置。

### 1.5 与 S-1 的关联

S-1（搜索辅助内容即时展示）中描述的"搜索辅助内容即时展示"会产生多次 videos 和 insight 更新，每一次更新都会触发本问题的自动滚动。两者叠加会显著放大交互干扰。S-2 修复后，S-1 的滚动干扰会自然缓解，但 S-1 本身的即时展示逻辑仍需独立修复。

## 2. 修复目标

实现"用户正在阅读"保护机制，使用户在流式输出期间手动上拉时不会被自动滚动打断，同时保持用户位于底部时的自动跟随滚动。

具体目标分解：

1. 引入 `isAtBottom` 状态，基于滚动容器位置判断用户是否接近底部。
2. 引入 `userScrolled` 标记，用户主动上拉超过阈值时暂停自动滚动。
3. 条件化滚动触发：effect 中仅当 `isAtBottom === true` 时才调用 `scrollIntoView`。
4. 恢复机制：用户重新滚动到底部时清除 `userScrolled`，恢复自动跟随。
5. 高频依赖优化：将 `state.streamingContent` 和 `state.streamingReasoning` 从 effect 依赖中移除或降频，改为基于 `isAtBottom` 的内部节流滚动。
6. 流结束行为：流式输出结束后，视情况恢复自动滚动或保持用户位置。

## 5. 滚动保护设计

### 5.1 状态引入

在 `MessageList` 组件中新增两个状态：

```tsx
// MessageList.tsx 修改示意（非最终实现代码，仅说明结构）
const [isAtBottom, setIsAtBottom] = useState(true);
const [userScrolled, setUserScrolled] = useState(false);
```

- `isAtBottom`：用户当前是否接近滚动容器底部（距离底部 < 阈值像素）。
- `userScrolled`：用户是否主动上拉导致自动滚动被暂停。两者关系：`userScrolled` 为 true 时自动滚动暂停；`userScrolled` 为 false 时（即 `isAtBottom` 为 true）自动滚动恢复。

### 5.2 接近底部判断阈值

定义接近底部的阈值常量：

```tsx
// MessageList.tsx 常量定义示意
/**
 * 判断用户是否"接近底部"的阈值（像素）。
 * 距离底部小于该值视为"在底部"，允许自动滚动。
 * 取值考量：太小则用户稍微滚动就被判定为离开底部，太大则在长内容时滚回不够灵敏。
 * 80px 覆盖大多数设备的滚动惯性余量。
 */
const SCROLL_BOTTOM_THRESHOLD = 80;

/**
 * 自动滚动节流间隔（毫秒）。
 * 流式 chunk 高频更新时，限制 scrollIntoView 的调用频率，避免动画队列堆积。
 */
const SCROLL_THROTTLE_MS = 100;
```

### 5.3 滚动容器 onScroll 监听

在滚动容器上添加 `onScroll` 事件处理：

```tsx
// MessageList.tsx onScroll 处理示意
const handleScroll = useCallback(() => {
  const container = scrollContainerRef.current;
  if (!container) return;

  // 计算距离底部的距离
  const { scrollTop, scrollHeight, clientHeight } = container;
  const distanceFromBottom = scrollHeight - scrollTop - clientHeight;
  const atBottom = distanceFromBottom < SCROLL_BOTTOM_THRESHOLD;

  setIsAtBottom(atBottom);

  if (atBottom) {
    // 用户滚动到底部，清除上拉标记，恢复自动滚动
    setUserScrolled(false);
  } else {
    // 用户上拉离开底部，标记暂停自动滚动
    setUserScrolled(true);
  }
}, []);
```

> **注意**：`scrollContainerRef` 应指向实际的可滚动元素。实施时需确认 `containerRef`（现有 line 42）指向的 `bili-agent-message-list` div 是否设置了 `overflow: auto/scroll`。如果是其外层祖先滚动，则 onScroll 需绑定到外层祖先，或通过 `getScrollParent` 工具查找。实施步骤1需先确认滚动容器。

### 5.4 条件化自动滚动 effect

修改自动滚动 effect，增加 `isAtBottom` 和 `userScrolled` 条件：

```tsx
// MessageList.tsx effect 修改示意
useEffect(() => {
  // 用户已上拉离开底部时，不自动滚动
  if (userScrolled || !isAtBottom) return;
  messagesEndRef.current?.scrollIntoView({ behavior: 'smooth' });
}, [renderItems.length, state.streamingContent, state.streamingReasoning, videos, isAtBottom, userScrolled]);
```

### 5.5 高频更新降频策略

`state.streamingContent` 和 `state.streamingReasoning` 每个 chunk 都变化，直接作为 effect 依赖会导致高频滚动。采用节流策略：

**方案：内部节流，保留依赖但限制 scrollIntoView 调用频率**

```tsx
// MessageList.tsx 节流滚动示意
const lastScrollRef = useRef(0);

useEffect(() => {
  if (userScrolled || !isAtBottom) return;

  const now = Date.now();
  if (now - lastScrollRef.current < SCROLL_THROTTLE_MS) return;
  lastScrollRef.current = now;

  messagesEndRef.current?.scrollIntoView({ behavior: 'smooth' });
}, [renderItems.length, state.streamingContent, state.streamingReasoning, videos, isAtBottom, userScrolled]);
```

**为什么保留依赖而不移除**：如果完全移除 `state.streamingContent` 和 `state.streamingReasoning` 依赖，effect 不会在 chunk 到达时触发，用户在底部时无法跟随流式输出滚动。保留依赖但节流，既保证跟随效果又限制频率。

### 5.6 流结束行为

流式输出结束后（`state.isLoading` 从 true 变为 false）的行为：

**方案：不主动滚回，保持用户当前位置**

```tsx
// MessageList.tsx 流结束 effect 示意
useEffect(() => {
  if (!state.isLoading) {
    // 流结束：不强制滚回底部，保持用户当前位置
    // 如果用户当前在底部（userScrolled === false），上一帧的节流滚动已将其保持在底部
    // 如果用户已上拉（userScrolled === true），保持上拉位置，不强制打断阅读
    // 可选：重置节流时间戳，避免下次流开始时立即触发遗留的节流
    lastScrollRef.current = 0;
  }
}, [state.isLoading]);
```

> **设计决策**：流结束后不强制滚回底部。理由：流结束时用户可能正在阅读流式输出的末尾内容，强制滚回会打断。如果用户在底部，最后一帧的滚动已保持位置；如果用户已上拉，尊重其阅读位置。

### 5.7 真正新消息的特殊处理

对于 `renderItems.length` 增加（真正的新消息到达），原问题档案建议5提到可给予未读提示而非强行拉回。本方案当前不实现未读提示（超出范围），但对新消息的处理策略：

**当前策略：新消息到达时，如果用户在底部则滚动，如果已上拉则不滚动（与流式 chunk 一致）**

这与现有行为的区别：现有逻辑无论用户位置都滚动；修复后尊重用户位置。如果未来需要"新消息到达时即使上拉也轻微滚动提示"，可在后续优化中实现。

### 5.8 滚动容器 JSX 修改

在滚动容器上添加 onScroll：

```tsx
// MessageList.tsx JSX 修改示意
return (
  <div
    ref={scrollContainerRef}
    className="bili-agent-message-list"
    onScroll={handleScroll}
  >
    {/* ... 现有内容不变 ... */}
  </div>
);
```

### 7.2 测试实现注意事项

- **jsdom 不实现滚动**：现有测试文件（MessageList.test.tsx:7）已 mock `Element.prototype.scrollIntoView = vi.fn()`。新增测试沿用此 mock，通过断言 mock 被调用与否判断滚动行为。
- **onScroll 模拟**：jsdom 不模拟真实滚动，需通过手动调用 onScroll 回调并传入模拟的 `Event` 对象来模拟滚动。构造 mock event 时需包含 `scrollTop`、`scrollHeight`、`clientHeight` 属性（通过 `Object.defineProperty` 设置到容器元素上）。
- **distanceFromBottom 计算**：`handleScroll` 内部读取 `container.scrollTop`、`container.scrollHeight`、`container.clientHeight`。测试中需通过 `Object.defineProperty` 设置这些值，因为 jsdom 不自动计算布局。
- **节流测试**：使用 `vi.useFakeTimers()` 和 `vi.advanceTimersByTime()` 控制时间，验证节流窗口内的调用次数。

## 9. 风险与回滚

### 9.1 风险

| 风险编号 | 风险 | 概率 | 影响 | 缓解措施 |
| --- | --- | --- | --- | --- |
| RK1 | 滚动容器判断错误：onScroll 绑定的元素不是实际可滚动元素 | 中 | 高 | 步骤1 确认滚动容器；测试中验证 onScroll 回调能正确读取 scrollTop/scrollHeight/clientHeight |
| RK2 | `SCROLL_BOTTOM_THRESHOLD` 设置不当，太小导致用户稍微滚动就被判定离开底部，太大导致长内容滚回不灵敏 | 中 | 中 | 80px 覆盖大多数设备惯性余量；可在实施后通过 E2E 调整 |
| RK3 | 节流导致用户在底部时跟随滚动有 100ms 延迟，视觉上"跳"而非"平滑跟随" | 低 | 低 | 100ms 间隔对 smooth 滚动动画影响小；如 E2E 反馈不佳可降低至 50ms |
| RK4 | `behavior: 'smooth'` 的动画与高频 chunk 更新叠加产生动画队列堆积 | 低 | 中 | 节流限制调用频率；原问题档案待验证假设1需运行时确认 |
| RK5 | rerank 的二次 videos 推送与首次推送的滚动动画叠加导致跳动 | 低 | 中 | 节流限制频率；原问题档案待验证假设2需运行时确认 |
| RK6 | onScroll 高频触发导致 React 状态更新风暴 | 中 | 中 | onScroll 回调内不做重计算；`setIsAtBottom`/`setUserScrolled` 在值未变时 React 会自动跳过 re-render（React 18+ 的 bailout 机制） |
| RK7 | 现有测试因 `scrollIntoView` 调用条件改变而失败 | 中 | 中 | 步骤6.2 验证现有测试；如有失败需更新测试 mock 的初始状态（确保 isAtBottom 初始为 true） |
