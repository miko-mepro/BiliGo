## 根因

`--load-extension` 需**同时**满足两个条件才生效，缺一则扩展完全不加载：

1. **持久化上下文**（`launchPersistentContext`）：非持久化上下文是 incognito 语义，扩展默认不在其中启用，因此 content script 不注入、扩展 service worker 也不启动；
2. **完整 Chromium 二进制**（`channel: "chromium"`）：Playwright 默认 headless 使用的 `chromium_headless_shell` 不支持扩展加载。

代码注释中留有四种启动组合的实测对照表（`Main/e2e/fixtures/extension-fixture.ts:8-16`）：

| 启动方式 | 扩展 service worker | `#bili-agent-host` |
| --- | --- | --- |
| `launch` + `newContext`（原配置） | 无 | 未注入 |
| `launchPersistentContext`（无 channel） | 无 | 未注入 |
| `launch` + `newContext` + `channel=chromium` | 无 | 未注入 |
| `launchPersistentContext` + `channel=chromium` | 已启动 | 已注入 |

该结论与 Playwright 官方 Chrome extensions 指南的要求一致。原先所有 spec 直接 `import { test } from "@playwright/test"`，用的正是表中第一种组合--**扩展从未被加载过**，所以等待 `[data-bili-agent-toggle]` 必然超时。

**三段探针**的价值在于可诊断性。原实现只等 `[data-bili-agent-toggle]` 一个选择器，失败时无法区分三种情况；拆开后每层给出定向错误：

1. 扩展 SW 已启动 -> 失败指向 E0-A2 / E0-A4
2. `#bili-agent-host` 已 attached -> 失败指向 E0-A3（`host` 元素由 `mountPanel` 创建，不依赖 storage 读取）
3. `[data-bili-agent-toggle]` 可见 -> 失败指向 E0-A5（`toggle` 依赖 `isReady`，即 storage 读取完成）

每用例独立临时 profile 目录（`fs.mkdtemp`）解决两个问题：避免用例间 `chrome.storage.local` 数据串味（`seedSettingsToStorage` 写真实存储），以及复用同一目录时的 Chromium profile 锁冲突。
