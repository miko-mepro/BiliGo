# 修复开发日志（Devlogs）

## 目录用途

本目录记录**已实际落地**的修复工作：改了什么、为什么这么改、验证结果如何、与原修复方案有何出入。

与同级目录的分工：

| 目录/文件 | 内容性质 | 时态 |
| --- | --- | --- |
| `docs/问题档案/` | 问题调查结论与代码证据 | 问题被发现时 |
| `docs/修复方案/阶段N-*/` | 实施计划、测试策略、验收标准 | 修复开始前 |
| `docs/修复方案/Devlogs/`（本目录） | 实际改动、验证结果、方案偏离与新发现 | 修复完成后 |
| `docs/修复方案/修复状态追踪.md` | 各问题当前状态（唯一状态源） | 持续更新 |

修复方案描述"打算怎么做"，本目录记录"实际做了什么、发现了什么"。当实现与方案不一致时，**以本目录记录的实际改动为准**，并在对应条目中说明偏离理由。

## 命名约定

- 单个问题：`<问题编号>-<简述>.md`，如 `R-1-历史标题类型校验.md`
- 阶段性汇总：`阶段N-<名称>-小结.md`
- 文件名使用问题档案中的编号，便于与 `docs/问题档案/` 和阶段方案交叉检索

## 每篇日志应包含

1. **改了什么**：文件清单 + 每处改动的意图（不复制代码全文）
2. **验证结果**：测试数量变化、typecheck/lint 实际输出，失败就如实写失败
3. **与方案的偏离**：方案要求 A、实际做了 B、理由是什么
4. **过程中的新发现**：方案未预见的问题、踩到的坑
5. **遗留缺口**：未完成的部分、被阻塞的验证项

不记录：逐行代码解释、git 已能查到的信息、未经验证的推测结论。
