### 缺口6：rerank 顺序与默认播放量排序冲突时，产品应优先哪一种

**关联修复**：S-4（客户端排序覆盖后端重排）
**关联假设**：S-V4（某次具体搜索中 video_rerank 是否因为候选字段不完整而跳过了重排视频推送）
**代码位置**：`Main/src/components/MessageList.tsx:44-47`（默认 sortField = 'play'）、`Main/src/utils/sort-filter.ts:32-57`（sortVideos 按字段降序）

**缺口描述**：当前 `sort-filter.test.ts:48-80` 覆盖了播放量排序，但没有任何测试覆盖"rerank 顺序与客户端默认播放量排序冲突"时的产品优先级。

**产品决策依赖**：此缺口需要产品决策确认"rerank 到达后客户端应展示 rerank 顺序还是播放量顺序"。

**测试文件**：`Main/test/utils/sort-filter.test.ts` 和 `Main/test/components/MessageList.test.tsx`

**测试用例设计**：

```
describe('缺口6：rerank 顺序与播放量排序冲突时的优先级', () => {
  // 场景A：rerank 到达后客户端立即覆盖默认排序
  it('rerank 到达后客户端展示 rerank 顺序而非默认播放量顺序', () => {
    // 1. 构造视频数据：
    //    BV1: 播放量 10000
    //    BV2: 播放量 5000
    //    BV3: 播放量 8000
    // 2. rerank 顺序：[BV2, BV1, BV3]（与播放量降序 [BV1, BV3, BV2] 不同）
    // 3. 派发 SET_VIDEOS，payload 为 rerank 顺序
    // 4. 根据 S-4 修复后的产品决策断言 DOM 顺序
    //    若 rerank 优先：DOM 顺序 === [BV2, BV1, BV3]
    //    若播放量优先：DOM 顺序 === [BV1, BV3, BV2]
  });

  // 场景B：用户手动切换排序后 rerank 顺序是否被保留
  it('用户手动切换到其他排序后 rerank 顺序被覆盖', () => {
    // 1. 派发 rerank 顺序的 SET_VIDEOS
    // 2. 若 S-4 修复后 rerank 优先，此时 DOM 显示 rerank 顺序
    // 3. 用户手动切换 sortField 为 'play'（播放量）
    // 4. 断言：DOM 顺序变为播放量降序 [BV1, BV3, BV2]
    //    即用户手动排序优先于 rerank
  });

  // 场景C：rerank 到达时用户已手动选择其他排序
  it('用户已手动选择排序后 rerank 到达时不覆盖用户选择', () => {
    // 1. 派发第一次 SET_VIDEOS
    // 2. 用户手动切换 sortField 为 'danmaku'（弹幕数）
    // 3. 派发 rerank 的 SET_VIDEOS（第二次推送）
    // 4. 断言：DOM 顺序按弹幕数排序，rerank 不覆盖用户手动选择
    //    （验证 S-4 修复后视频数组引用变化时保留用户手动选择）
  });
});
```

**断言要点**：
- 当前 `MessageList.tsx:49-56` 在 `videos` 数组引用变化时重置 `sortField` 为默认值 `'play'`，这会覆盖用户手动选择
- S-4 修复后应定义"视频数组更新时是否重置用户手动选择"的行为（对应缺口7）
- 产品决策需明确：rerank 到达后默认展示顺序、用户手动排序与 rerank 的优先级

**验收标准**：
- 产品决策明确后，测试断言与决策一致
- rerank 与播放量排序冲突时，客户端展示顺序有明确的优先级定义
- 用户手动排序与 rerank 的优先级有明确的优先级定义
