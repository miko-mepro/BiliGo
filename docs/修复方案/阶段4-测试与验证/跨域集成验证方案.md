## 1. 方案目标

覆盖问题关联图中记录的四类跨文档关联，确保不同问题域的修复在集成点不产生冲突。跨域集成验证针对的是"多个修复方案完成后，在共用代码或集成点上是否协调一致"，而非单个修复方案的独立正确性。

本方案不修改 `Main/` 源码，只描述跨域集成验证的前置条件、步骤、预期结果、失败分类、证据留存和退出标准。

## 2. 前置依赖

| 依赖项 | 说明 | 阻塞关系 |
| --- | --- | --- |
| 阶段0 E2E 能力恢复 | 跨域集成验证需要运行时证据支持 | 强阻塞 |

**阶段4 执行时机声明**：阶段4 只能在阶段1、阶段2、阶段3 的修复方案完成后执行。跨域集成验证需要所有相关修复已完成，否则集成点无法验证协调一致性。

| 网络层错误分类与工具调用集成 | N-1、N-4 | N-2/N-3 连接链路 + S-1~S-4 搜索链路 | 连接测试和 Bilibili 工具调用面对相似网络异常时显示一致文案 |

## 4. 网络层连接链路验证（N-2/N-3/R-3）

### 4.1 链路 N-2：聊天流总超时回归

**关联问题**：N-2（聊天流缺少总超时）
**集成点**：`Main/src/background/stream.ts:315-329`（streamText 调用未设置 AbortSignal.timeout）

**前置条件**：
- 阶段0 E2E 能力恢复
- N-2 修复已完成：streamText 已设置独立总超时
- 已配置可用的 Provider（Base URL、模型名，不记录 API Key）

**步骤**：
1. 导航到 bilibili，打开面板，进入聊天视图
2. 发送一条消息触发流式输出
3. 模拟上游请求不返回数据（如配置一个不响应的 Base URL 或 mock 拦截 streamText 请求）
4. 观察从发送到错误显示的耗时
5. 观察错误文案和 Port 状态

**预期结果**：
- 上游请求不返回时，聊天流在总超时阈值后中断（参考连接测试 10 秒和工具请求 30 秒设定合理阈值）
- 中断后给出可读错误文案
- Port 心跳不替代流请求超时（Port 心跳检测的是 content script 与 service worker 通道存活）
- 不长期保持等待状态

**失败分类**：
- 若聊天流长期等待无超时：N-2 修复未生效
- 若超时阈值不合理（过短导致正常请求被中断，过长导致用户长期等待）：阈值需调整
- 若错误文案不可读：N-2 错误映射缺失

**证据留存**：
- 从发送到错误显示的耗时（用于区分约10秒模型请求超时、约12秒前端兜底、约60秒聊天 Port pong 超时）
- 错误文案截图
- service worker 控制台的 chat 消息收到时间和异常类型
- 不记录 API Key、Cookie 或完整请求凭据

**退出标准**：
- 聊天流在总超时后中断并给出可读错误
- 耗时在预期阈值范围内

### 4.2 链路 N-3：设置 Port 断线检测回归

**关联问题**：N-3（设置 Port 无断线检测）
**集成点**：`Main/src/components/Panel.tsx:425-445`（设置 Port 建立和销毁）、`Main/src/components/model-settings/TestConnectionButton.tsx:132-148`（只注册 onMessage）

**前置条件**：
- 阶段0 E2E 能力恢复
- N-3 修复已完成：设置 Port 已注册 onDisconnect 处理，统一两条 Port 链路的断线检测能力

**步骤**：
1. 导航到 bilibili，打开面板，切换到设置视图
2. 确认设置 Port 已建立（Panel.tsx:425-445）
3. 在 service worker 控制台模拟 Port 断开（或通过 chrome.runtime.disconnect 手动触发）
4. 观察前端是否及时感知断开并给出反馈
5. 对比聊天 Port 的断线检测行为（ping/pong + onDisconnect + 60 秒 pong 超时）

**预期结果**：
- 设置 Port 断开时前端及时感知（onDisconnect 触发）
- 断线反馈及时（不等 12 秒前端兜底超时）
- 设置 Port 与聊天 Port 的断线检测能力一致（均注册 onDisconnect）

**失败分类**：
- 若断线反馈延迟到 12 秒：N-3 onDisconnect 未注册或未触发
- 若两条 Port 链路断线检测能力仍不一致：N-3 修复未统一

**证据留存**：
- Port 建立时间戳
- Port onDisconnect 时间戳
- 断线反馈显示时间戳
- 对比设置 Port 与聊天 Port 的断线检测行为

**退出标准**：
- 设置 Port 断开时前端及时感知
- 两条 Port 链路断线检测能力一致

### 4.3 链路 R-3：连接测试结果过期覆盖回归

**退出标准**：

- 组件卸载后不执行状态更新

## 10. 风险与回滚

### 风险

| 风险 | 概率 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| 跨域集成验证覆盖面广，可能存在未被原始文档记录的隐式依赖 | 高 | 中 | 集成验证前先梳理问题关联图的完整依赖路径 |
| 运行时证据采集可能影响测试行为 | 中 | 中 | 验证采集通道本身不改变被验证行为 |
| 假设验证可能揭示新根因，导致阶段1~3 部分修复需返工 | 中 | 高 | 假设验证优先于其他运行时验证推进 |
| 产品决策未明确导致 S-3、S-4 集成点预期行为无法定义 | 高 | 高 | 在阶段2 实施期间同步推进产品需求确认 |
| MV3 service worker 回收影响长耗时验证 | 中 | 中 | `--disable-background-timer-throttling` 缓解 |

### 回滚

若跨域集成验证发现修复冲突或新问题：
1. 记录冲突点和涉及的修复方案
2. 将相关修复方案状态回退为 `in_progress`
3. 不影响其他已通过验证的集成点
4. 冲突修复后重新执行对应集成点验证

## 11. 完成状态

**当前状态**：completed

状态变更条件：
- `pending` -> `in_progress`：阶段0~3 修复完成后，开始执行跨域集成验证
- `in_progress` -> `needs_review`：所有链路和集成点至少执行一次，采集到运行时证据
- `needs_review` -> `completed`：验收标准 CD-AC1 至 CD-AC17 全部满足
