- **所属阶段**: 阶段1 - 致命问题修复
- **修复状态**: completed

## 静态确认的崩溃链路

本修复方案针对的崩溃入口已通过静态代码审查完全确认，不需要运行时复现即可落地代码层修复。崩溃链路如下：

1. **存储读取层缺校验**：`Main/src/lib/history/store.ts:59-65` 的 `getHistoryIndex()` 仅判断 `Array.isArray(value)`，随后通过 `value as ConversationRecord[]` 强制类型断言把存储值返回。存储中的数组元素即使 `title` 为 `null`、数字、对象或字段缺失，也会原样进入下游状态。
2. **跨标签页同步层同样缺校验**：`Main/src/lib/history/sync.ts:52-56` 监听 `chrome.storage.onChanged`，对 `newValue` 同样只判断 `Array.isArray(raw)`，随后强转为 `ConversationRecord[]` 并回调给组件。外部标签页写入的脏数据可通过该路径无校验进入本地状态。
3. **渲染层直接调用字符串方法**：`Main/src/components/HistoryDropdown.tsx:214-219` 在 render 阶段执行搜索过滤，调用 `r.title.toLowerCase()`。当 `r.title` 不是字符串时，JavaScript 抛出 `TypeError`（如 `Cannot read properties of null (reading 'toLowerCase')`）。
4. **错误边界只能降级不能修复**：`Main/src/content/error-boundary.tsx:36-68` 的 `getDerivedStateFromError` 可捕获该 render 异常并显示"BiliAgent 渲染异常"降级 UI，但 `ErrorBoundary` 不会清理底层脏数据。用户每次在搜索框输入非空字符都会重新触发 render，重新抛出 `TypeError`，除非清除历史索引。

`ConversationRecord` 的契约类型定义（`Main/src/lib/shared-types/index.ts:107-114`）要求 `title: string`，但运行时存储值并不保证满足该类型，这是 TypeScript 类型断言掩盖的数据信任债务。

## 触发边界

满足以下全部条件即稳定触发 render crash：

1. `bili-agent-history-index` 存储的数组中，至少一条记录的 `title` 字段不是字符串（取值为 `null`、`undefined`、数字、布尔值、对象或字段缺失）。
2. 面板已打开且历史下拉已展开（`HistoryDropdown` 已挂载）。
3. 用户在"搜索历史记录"输入框中输入至少一个非空字符，使 `searchQuery.trim()` 为真值，进入 `records.filter(...)` 分支。
4. render 阶段执行 `r.title.toLowerCase()` 时命中非字符串 `title` 的记录。

不触发的情况：

- `title` 为字符串（含空字符串 `""`）时不抛错，`"".toLowerCase()` 合法。
- 搜索框为空（`searchQuery.trim()` 为假）时走 `: records` 分支，不调用 `toLowerCase`，不抛错（但脏数据仍存在于状态中，后续操作仍可能触发）。
- 历史下拉未展开时 `HistoryDropdown` 卸载，不执行 render 过滤。

## 修复目标

**保证异常 `title` 不会在 render 阶段调用 `toLowerCase` 导致 `TypeError`。**

具体目标分解：

1. 消除 render 阶段因非字符串 `title` 抛出 `TypeError` 的崩溃入口。
2. 在数据入口（存储读取 + 跨标签页同步）建立统一的结构完整性校验，阻止非字符串 `title` 等异常数据进入组件状态。
3. 对已存在于存储中的历史遗留脏数据，在加载时进行降级或过滤，避免脏数据持续触发防御逻辑。
4. 在渲染层增加防御性类型保护作为最终兜底，确保即使上游校验遗漏也不会导致 render crash。

**关于触发来源的边界声明**：当前没有证据证明"高频点击不同按钮"会制造异常 `title` 数据。正常写入路径 `store.ts:97-104` 的 `saveConversation` 使用字符串 `tempTitle` 或已有字符串标题，`updateTitle` 也接收 `string` 类型。脏数据的实际来源尚未确认（可能是旧版本写入、外部扩展同步或存储损坏）。本修复方案不声称快速点击是该问题的根因，只针对已静态确认的"异常 title 在 render 阶段调用 toLowerCase 导致 TypeError"这一崩溃链路进行修复。

## 精确修改范围

### 文件1：`Main/src/lib/history/store.ts`

**修改位置**：`getHistoryIndex()` 函数，第 59-65 行。

**当前代码**：

```ts
export async function getHistoryIndex(): Promise<ConversationRecord[]> {
  const result = await chrome.storage.local.get(INDEX_KEY);
  const value = result[INDEX_KEY];
  if (Array.isArray(value)) {
    return value as ConversationRecord[];
  }
  return [];
}
```

**修改要点**：在 `Array.isArray(value)` 判断通过后，不再直接强转返回，而是对数组逐条执行字段级校验，过滤掉不满足 `ConversationRecord` 契约的条目，或对可降级字段做安全降级。

**当前代码**：

const raw = changes[INDEX_KEY].newValue;
const newIndex: ConversationRecord[] = Array.isArray(raw)

this.callback?.(newIndex);

**修改要点**：在 `Array.isArray(raw)` 判断通过后，调用与 `store.ts` 相同的逐条字段校验函数，保证跨标签页同步数据与本地读取数据经过一致的校验。

### 文件3：`Main/src/components/HistoryDropdown.tsx`

**修改位置**：搜索过滤逻辑，第 214-219 行。

**修改要点**：在 `r.title.toLowerCase()` 调用前增加类型保护，作为 render 层的防御性兜底。即使上游校验遗漏，也不会在 render 阶段抛出 `TypeError`。

## 数据校验策略

### 校验函数设计

在 `Main/src/lib/history/` 下新增一个独立的校验工具模块（例如 `validate.ts`），导出 `sanitizeHistoryIndex(raw: unknown): ConversationRecord[]` 函数。该函数被 `store.ts` 和 `sync.ts` 共同复用，保证两条数据入口的校验逻辑完全一致。

校验规则按 `ConversationRecord` 契约逐字段定义：

| 字段 | 类型契约 | 校验规则 | 失败处理 |
| --- | --- | --- | --- |
| `id` | `string` | `typeof id === 'string' && id.length > 0` | 丢弃整条记录（无 `id` 无法加载或删除对话） |
| `title` | `string` | `typeof title === 'string'` | 降级为空字符串 `''`（保留记录可加载，搜索不匹配但不崩溃） |
| `titleFinal` | `boolean` | `typeof titleFinal === 'boolean'` | 降级为 `false`（视为标题未最终生成，允许后续重命名覆盖） |
| `createdAt` | `number` | `typeof createdAt === 'number' && Number.isFinite(createdAt) && createdAt >= 0` | 降级为 `0` |
| `lastActiveAt` | `number` | `typeof lastActiveAt === 'number' && Number.isFinite(lastActiveAt) && lastActiveAt >= 0` | 降级为 `0` |
| `messageCount` | `number` | `typeof messageCount === 'number' && Number.isFinite(messageCount) && messageCount >= 0` | 降级为 `0` |

### 校验失败分级

- **致命失败（丢弃整条记录）**：`id` 非字符串或为空。没有 `id` 的记录无法关联到单条对话数据，也无法被删除或加载，保留只会造成索引与数据 key 不一致。
- **可降级失败（保留记录，修正字段）**：`title`、`titleFinal`、`createdAt`、`lastActiveAt`、`messageCount` 任一非预期类型。这些字段缺失或类型错误不影响记录的可加载性，降级后记录仍可正常使用。
- **非对象元素（丢弃）**：数组元素不是对象（如 `null`、`number`、`string`），直接丢弃。

### 校验函数的纯净性约束

校验函数模块必须遵守与 `store.ts`、`sync.ts` 相同的纯净性约束：

- 禁止 import React 或 React hooks。
- 禁止访问 `chrome.storage` 或其他浏览器 API（校验函数是纯函数，只接收输入返回输出）。
- 禁止产生副作用（不修改输入数组，返回新数组）。

## 脏数据降级与过滤策略

### 加载时清理策略

`getHistoryIndex()` 调用 `sanitizeHistoryIndex()` 后，如果检测到脏数据被降级或丢弃，需要决定是否回写清理后的索引。

**采用策略：静默降级，不主动回写。** 理由：

1. 回写清理后的索引会产生 `chrome.storage.local.set` 副作用，可能与其他标签页的并发写入冲突。
2. 降级后的记录仍可正常使用（`title` 降级为空字符串，`id` 完整保留），用户无感知。
3. 下次 `saveConversation` 或 `updateTitle` 写入时，该记录的 `title` 会被正常字符串覆盖，脏数据自然消失。
4. 只有 `id` 缺失的记录被丢弃，但这类记录本就无法加载或删除，丢弃不影响用户体验。

**替代策略（不采用）：主动回写清理。** 主动回写虽然能持久化清理脏数据，但引入写放大和并发风险。若未来确认需要持久化清理，可在 `sanitizeHistoryIndex` 返回时附带"是否发生降级"的标志，由调用方决定是否回写，但本阶段不实现。

### 渲染层兜底策略

`HistoryDropdown.tsx:214-219` 的搜索过滤增加类型保护：

```ts
// 修复后的逻辑示意（非最终实现代码）
const normalizedQuery = searchQuery.trim().toLowerCase();
const filtered = searchQuery.trim()
  ? records.filter((r) => {
      const title = typeof r.title === 'string' ? r.title : '';
      return title.toLowerCase().includes(normalizedQuery);
    })
  : records;
```

该兜底保证：即使上游 `sanitizeHistoryIndex` 因任何原因未生效（例如未来新增的数据入口忘记接入校验），render 阶段也不会因 `r.title.toLowerCase()` 抛出 `TypeError`。

### 跨标签页同步策略

`sync.ts` 的 listener 回调在 `Array.isArray(raw)` 判断后，调用 `sanitizeHistoryIndex(raw)` 对同步数据进行校验。校验后的干净数据再回调给组件。这样跨标签页写入的脏数据在进入本地状态前已被过滤。

## 验收标准

1. **render 不抛 TypeError**：当 `bili-agent-history-index` 存在 `title` 为 `null`、数字、对象或缺失的记录时，在搜索框输入非空字符，`HistoryDropdown` 的 render 阶段不再抛出 `TypeError`。
2. **数据入口校验生效**：`getHistoryIndex()` 和 `HistorySync` listener 返回的数据均经过 `sanitizeHistoryIndex` 校验，非字符串 `title` 被降级为空字符串，`id` 非法的记录被丢弃。
3. **渲染层兜底生效**：`HistoryDropdown.tsx:214-219` 的搜索过滤在 `r.title.toLowerCase()` 前有 `typeof r.title === 'string'` 类型保护，即使上游校验遗漏也不抛错。
4. **正常数据不受影响**：`title` 为正常字符串（含空字符串）的记录在搜索过滤、加载、重命名、删除等操作中行为不变。
5. **校验逻辑一致**：`store.ts` 和 `sync.ts` 使用同一个 `sanitizeHistoryIndex` 函数，两条数据入口的校验规则完全一致。
6. **单元测试覆盖**：`sanitizeHistoryIndex` 的所有字段降级和丢弃路径均有单元测试覆盖，`getHistoryIndex` 和 `HistorySync` listener 的脏数据处理路径均有单元测试覆盖。
7. **组件测试覆盖**：`HistoryDropdown` 在 `records` 包含非字符串 `title` 时的搜索过滤有组件测试覆盖，验证 render 不抛错。
8. **校验函数纯净**：`sanitizeHistoryIndex` 为纯函数，不 import React，不访问浏览器 API，不修改输入数组。
9. **不声称快速点击为根因**：本方案文档及实现不包含"快速点击是 R-1 根因"的表述，修复目标明确为"保证异常 title 不会在 render 阶段调用 toLowerCase 导致 TypeError"。

## 风险与回滚

### 风险

1. **校验性能开销**：逐条校验 `id`、`title`、`titleFinal`、`createdAt`、`lastActiveAt`、`messageCount` 六个字段，在 `MAX_HISTORY=50` 条记录场景下开销可忽略。但如果未来历史记录上限大幅增加，校验可能增加读取延迟。缓解：校验是同步纯函数操作，无 IO，50 条记录的校验在微秒级完成。
2. **降级导致数据"消失"**：`title` 降级为空字符串后，该记录在搜索框中输入任何关键词都不会匹配，用户可能感觉"历史记录消失了"。缓解：空 `title` 的记录在搜索框为空时仍会显示（走 `: records` 分支），用户清空搜索即可看到全部记录。未来可考虑在 `title` 为空时显示占位文案"未命名对话"。
3. **`id` 丢弃导致索引与数据 key 不一致**：丢弃 `id` 非法的记录后，对应的单条对话数据 key（`bili-agent-history:{id}`）仍残留在存储中，造成存储泄漏。缓解：`id` 非法的记录本就无法通过 `loadConversation(id)` 加载（`loadConversation` 要求 `id` 为 string），丢弃后不影响功能。存储泄漏的清理留待后续优化，不在本次修复范围。
4. **跨标签页并发写入覆盖校验结果**：`sanitizeHistoryIndex` 只校验读取时的数据，不回写清理。如果两个标签页同时读取脏数据并各自降级，不会冲突（降级结果一致）。但如果一个标签页在降级后触发 `saveConversation` 回写，另一个标签页的同步事件会收到干净数据，无风险。
5. **未来新增数据入口忘记接入校验**：如果未来新增第三条数据入口（如从云端同步历史），忘记调用 `sanitizeHistoryIndex` 会导致脏数据绕过校验。缓解：渲染层 `HistoryDropdown` 的类型保护作为最终兜底，即使上游遗漏也不会 render crash。但应在代码审查中强制要求新数据入口接入校验。

### 回滚方案

如果修复引入回归问题，回滚步骤：

1. **回滚 `store.ts`**：将 `getHistoryIndex()` 恢复为原始的 `Array.isArray(value) ? value as ConversationRecord[] : []` 逻辑。
2. **回滚 `sync.ts`**：将 listener 回调恢复为原始的 `Array.isArray(raw) ? raw as ConversationRecord[] : []` 逻辑。
3. **回滚 `HistoryDropdown.tsx`**：将搜索过滤恢复为原始的 `r.title.toLowerCase()` 调用（移除类型保护）。
4. **保留 `validate.ts`**：校验工具模块本身无副作用，可保留不影响功能，便于后续重新接入。
5. **回滚测试**：移除因校验逻辑新增的单元测试和组件测试。

回滚后，render crash 问题恢复到修复前的状态（异常 `title` 在搜索时仍会触发 `TypeError`），但不会引入新的功能问题。回滚是纯代码还原操作，不涉及数据迁移。
