# 修复状态追踪

本文件统一追踪 11 个已确认问题和 5 个阶段工作的修复状态。状态定义、当前状态、阻塞关系和每阶段退出条件均在本文维护，阶段 README 不重复维护状态字段。

## 状态定义

| 状态 | 含义 | 是否阻塞后续 |
| --- | --- | --- |
| pending | 未开始，等待前置依赖完成或等待派工 | 阻塞依赖本项的后续任务 |
| in_progress | 正在实施修复或采集运行时证据 | 不视为完成，依赖本项的后续任务仍阻塞 |
| blocked | 遇到阻塞条件，无法继续推进 | 阻塞依赖本项的后续任务 |
| needs_review | 修复代码已提交，等待审查和测试 | 不阻塞独立后续任务，但阶段退出条件未满足 |
| completed | 修复已合并、测试通过、验收标准已达成 | 不阻塞任何后续任务 |

初始状态下，所有问题和阶段工作统一为 `pending`。本文档只记录计划状态，不记录已完成的修复结论。

## 阻塞关系

### 强阻塞（硬依赖）

以下依赖关系中，前置任务必须达到 `completed` 状态，后续任务才能从 `pending` 转为 `in_progress`：

1. **S-4 依赖 S-3 的代码模型**：S-4 的排序行为定义需要 S-3 建立的批次归属模型（`searchId`/`batchId`/`messageId`）作为锚点。S-3 的代码模型已落地；两项仍需阶段0提供运行时批次和最终顺序证据后才能正式关闭。
2. **N-4 阻塞于 N-1**：N-4 需要把 Bilibili 工具网络失败接入 N-1 定义的统一网络错误分类语义层。N-1 未完成时启动 N-4 会缺少统一分类基础，工具调用路径与连接测试文案仍会不一致。
3. **阶段4 阻塞于阶段0**：阶段4 的运行时验证、E2E 场景回归和跨域集成验证依赖阶段0 恢复的 E2E 挂载能力。阶段0 未完成时阶段4 无法采集运行时证据。

### 协调关系（非硬阻塞）

以下关系不是硬阻塞，但相关问题的修复必须协调进行，避免分别修改共用代码造成二次竞态或不一致：

1. **N-3 与 R-3 共用 TestConnectionButton 状态管理**：两者共同涉及 `Main/src/components/model-settings/TestConnectionButton.tsx:115-189`。N-3 关注 Port 断线检测能力，R-3 关注异步 Promise 完成时机。修复时应统一检查 listener、timer、取消和过期结果，避免分别修改造成状态管理冲突。
2. **S-1 到 S-4 因果链**：搜索结果展示的四个问题形成逐级传导的因果链。S-1（即时展示）是上游，S-2（无条件滚动）、S-3（全局替换）、S-4（排序覆盖）逐级放大。S-1 归入阶段3，S-2/S-3/S-4 归入阶段2，修复 S-1 时需回查 S-2/S-3/S-4 的修复是否仍成立。
3. **R-2 与 R-3 同属异步竞态类**：两者触发场景独立（历史重命名 vs 连接测试），但修复模式相似（引入取消机制）。建议共享取消机制的设计经验，但不必互相等待。

### E2E 阻塞的特殊规则

阶段0 的 E2E 挂载阻塞遵循以下规则：

- E2E 挂载阻塞**不阻塞** R-1、N-2 等可由静态证据确认的修复。这类修复可以与阶段0 并行启动。
- E2E 挂载阻塞**阻塞** 最终运行时证据采集。R-1、R-2、R-3 的渲染崩溃堆栈、S-2 的实际滚动频率、S-4 的最终 DOM 顺序等运行时验证必须等待阶段0 恢复 E2E 能力后才能采集。
- 因此，阶段1 到阶段3 的代码修复可以先行推进，但其 `completed` 状态的最终验收需要阶段0 提供运行时证据支持。

- 状态变更时必须同步更新本文件的"当前状态表"。

- 状态从 `needs_review` 转 `completed` 时，必须满足对应阶段的退出条件。
