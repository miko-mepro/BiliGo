# 网络连接错误问题记录

## 记录范围

本记录只描述当前代码中已经确认的网络错误链路、已覆盖的边界和仍需复现的问题，不修改应用代码，也不把待验证假设写成已确认根因。

调查对象为 `Main/` 的 Chrome 扩展实现，重点关注：

- 对话开始前的连接测试；
- 对话开始后的 AI 流式请求；
- content script 与 service worker 之间的 `chrome.runtime.Port`；
- 网络错误、超时和断线状态在 UI 中的呈现。

## 用户现象对应的初步结论

如果用户所说的“对话开始前偶尔进入网络连接错误状态”发生在设置页点击“测试连接”之后，那么它对应的是设置页的独立连接测试链路，而不是聊天流本身。仅凭当前描述，还不能证明每次现象都来自这一条链路：

1. 设置页打开时，`Panel` 建立设置专用 Port。
2. 点击“测试连接”后，前端发送 `test_connection`。
3. service worker 使用待测 Provider 调用 `generateText`。
4. `generateText` 模型请求使用 10 秒超时；前端再等待 12 秒作为结果未返回时的兜底。
5. 鉴权失败、限流、模型请求异常或超时会根据不同路径显示失败、网络错误、原始错误或连接超时。

因此，这个现象至少可能与以下条件有关：Provider 配置错误、上游 API 不可达、网络切换、模型请求超时、service worker/Port 在结果返回前断开。当前实现的错误文案不总能区分这些原因，仍需运行时证据确认具体触发点。

## 已确认的连接测试链路

### 调用路径

| 环节 | 代码位置 | 行为 |
| --- | --- | --- |
| 设置 Port 建立 | `Main/src/components/Panel.tsx:394-445` | 设置视图打开时调用 `chrome.runtime.connect({ name: "bili-agent-chat" })`，关闭时断开 |
| 前端请求与等待 | `Main/src/components/model-settings/TestConnectionButton.tsx:115-189` | 监听 `connection_result`，同时启动 12 秒前端超时 |
| 后台路由 | `Main/src/background/stream.ts:559-597` | 收到 `test_connection` 后异步调用 `handleTestConnection`，异常时补发失败结果 |
| 实际探测 | `Main/src/background/stream.ts:514-557` | 校验 Provider，调用 `generateText("hi")`；模型请求使用 10 秒 `AbortSignal.timeout` |
| 错误映射 | `Main/src/background/port-protocol.ts:96-132` | 401/403、429、鉴权词和其他错误分别归类 |

### 已有保护

- Provider 校验失败会返回 `connection_result { ok: false }`，不会继续调用模型。
- 后台连接测试的模型请求有 10 秒超时。
- 前端有 12 秒超时兜底，避免结果永远等待。
- `postMessage` 同步抛错时，前端会进入失败态并清理 listener/timer。
- 后台 `handleTestConnection` 和 `setupPortListener` 都有失败回传路径。
- `inferErrorCode` 使用 HTTP 状态码边界匹配，已避免将类似 `14012` 的数字误判为 401。

## 对话开始后的链路

### 调用路径

1. `Main/src/content/chat-context.tsx:798-843` 在发送前检查 Port 状态，然后设置 `isLoading` 并发送 `chat`。
2. `Main/src/background/stream.ts:290-329` 读取设置、创建模型和 `AbortController`，随后调用 `streamText`。
3. `Main/src/background/stream.ts:331-420` 消费流式结果，处理文本、工具事件、流错误和迭代异常。
4. `Main/src/content/chat-context.tsx:461-493` 收到 `done` 或 `error` 时清理 loading、activity 和 streaming 缓冲。
5. `Main/src/content/port-connection.ts:58-115` 通过 ping/pong 和 `onDisconnect` 检测 Port 断开。
6. `Main/src/content/chat-context.tsx:594-609` 断线时显示“连接已断开，请重试”，清理流式状态并安排指数退避重连。

### 已确认的对话后错误处理

- `streamText` 在流开始前抛出异常时，外层 `catch` 会发出 `error`。
- 流式迭代过程中抛出网络异常时，外层 `catch` 会将其归类为 `NETWORK_ERROR`，并在最后发送 `done`。
- AI SDK 的 `error` 和 `tool-error` part 都有对应的错误消息路径。
- Port 在流期间断开时，后台停止继续推送；前端通过 `onDisconnect` 结束 loading 并清空半截回答。
- 现有单测已覆盖 `fetch failed`、AbortError、流 error part、工具错误和断线后的静默丢弃。

## 已确认的问题与风险

### 问题 1：连接测试的“网络错误”文案无法区分根因

**证据：** `Main/src/background/port-protocol.ts:96-132`。

由 `generateText` 抛出的、未被识别为 401/403 或 429 的异常，会经过 `inferErrorCode` 归类为 `NETWORK_ERROR`，UI 通常显示“网络连接失败”。但配置校验失败直接返回校验错误，`createModel` 在 `try` 外抛出时由路由层返回原始错误，Port 发送成功后没有结果则由前端显示“连接超时”。因此，Provider 地址错误、模型不存在等情况只有在 Provider SDK 的异常文本未命中现有规则时，才可能与普通网络异常得到相同分类。

**影响：** 部分用户只能看到“网络连接失败”，无法判断应该检查网络、API Key、Base URL 或模型名；而另一些路径显示“连接超时”“连接已断开”或原始错误。错误文案不足以单独确定根因，这是当前无法从现象直接确定单一原因的主要限制。

**当前状态：** 已确认是错误分类粒度不足；具体触发原因仍需运行时日志或可复现请求信息确认。

### 问题 2：聊天流没有独立的总超时

**证据：** `Main/src/background/stream.ts:315-329` 创建了手动 `AbortController` 并将其传给 `streamText`，但该调用没有像连接测试和标题生成那样设置 `AbortSignal.timeout(...)`。仓库中 `AbortSignal.timeout` 的调用位置包含标题 10 秒、连接测试 10 秒、Bilibili 请求 10 秒和工具/视觉请求 30 秒，但没有聊天 `streamText` 的总超时。

**影响：** 如果上游请求既不返回数据也不主动抛错，聊天可能长期保持等待状态。Port 心跳只检测 content script 与 service worker 通道是否存活，不能证明上游 AI 请求仍在推进；因此它不能替代流请求的超时。

**当前状态：** 已由代码静态确认“聊天流缺少独立总超时”。尚未确认用户所述的偶发错误是否由该场景触发，因为当前没有运行时复现日志。

### 问题 3：设置页独立 Port 未注册断线处理，也没有聊天链路同等的心跳机制

**证据：** 原生 Port 本身提供 `onDisconnect`，但 `Main/src/components/Panel.tsx:425-445` 只建立和销毁设置 Port；`TestConnectionButton` 在 `Main/src/components/model-settings/TestConnectionButton.tsx:132-148` 只注册 `onMessage`，没有注册 `port.onDisconnect`。相比之下，聊天 Port 使用 `connectChatPort`，包含 ping/pong、60 秒 pong 超时和 `onDisconnect` 状态通知。

**影响：** 只有在请求已经成功发送、随后设置 Port 断开且没有收到 `connection_result` 时，前端才会继续等待并在 12 秒后显示“连接超时”。如果断开发生在发送时并导致 `postMessage` 同步抛错，前端会立即显示“连接已断开”。因此，缺少 `onDisconnect` 处理会延迟部分断线反馈，但不是所有断开场景都会等待 12 秒；缺少心跳也不是该 12 秒等待的直接原因，聊天心跳的 60 秒阈值反而更长。

**当前状态：** 已确认两条 Port 链路的断线检测能力不一致；未确认这是否就是用户当前观察到的每一次偶发错误。

### 问题 4：工具内 Bilibili 网络失败可能被用户理解为搜索无结果

**证据：** `Main/src/lib/bilibili-client/search.ts:94-112` 会抛出 `BilibiliNetworkError`，`Main/src/tools/bilibili-search.ts:90-127` 不转换该异常；它会回到 AI SDK 的 `tool-error` 路径，由 `Main/src/background/stream.ts:368-380` 统一显示“工具 bilibili_search 执行失败”，随后终止当前流并发送 `done`。

**影响：** 该路径不会直接展示“网络连接失败”分类，而是展示工具执行失败并终止本次流；用户可能把网络失败理解成普通工具问题。当前代码不能证明模型会继续生成解释或一定被理解为“没有搜索结果”，这需要运行时或 UI 证据确认。该问题与对话前连接测试是不同链路，不应混为同一个根因。

**当前状态：** 已确认错误语义在 Bilibili 请求和 Provider 连接测试之间不一致；需要运行时复现确认实际 UI 呈现。

## 当前未能从代码确认的事项

以下内容不能仅凭当前静态代码判定，后续复现时需要采集时间、Provider、Base URL、浏览器网络状态、service worker 生命周期和 Port 事件：

- 具体是哪个 Provider、哪个 URL 或哪个模型请求失败；
- 错误发生在 DNS、TLS、代理、CORS/权限、HTTP 状态码还是请求超时；
- service worker 是否在 `generateText` 返回前被浏览器回收或重启；
- 用户点击“测试连接”时设置 Port 是否已经断开；
- 对话开始后是否也出现同类错误，还是只有设置页连接测试报错；
- 网络恢复后，原聊天流是否需要用户手动重试（当前代码的设计是断开原流并重连 Port，不自动恢复原请求）。

## 后续复现所需最小证据

本次不修改代码，因此这里只记录调查所需证据，不实现日志：

1. 记录发生时间和当前页面 URL，区分设置页连接测试与聊天发送。
2. 记录 Provider 类型、Base URL、模型名和错误展示文案；不要记录 API Key。
3. 在浏览器 DevTools 的 Network 中确认请求 URL、HTTP 状态或是否根本没有发出请求。
4. 在 service worker 控制台记录 `test_connection`/`chat` 收到时间、异常类型和 Port `onDisconnect` 时间。
5. 记录从点击到错误显示的耗时：约 10 秒通常对应连接测试的模型请求超时，约 12 秒通常对应前端兜底，约 60 秒可能对应聊天 Port 的 pong 超时。
6. 若对话开始后发生问题，同时记录是否收到过 `chunk`、`error` 或 `done`，以区分上游流异常、消息链路断开和 UI 状态问题。

## 结论

当前最明确的结论是：对话前的连接测试有超时和失败回传，但错误分类过于粗粒度；对话后的流式请求有异常捕获和 Port 断线清理，但没有独立的聊天总超时。用户描述的偶发“网络连接错误”不能在没有运行时证据的情况下归因于单一网络故障。本文件将这些已确认的代码问题和待验证边界保留为后续修复与复现依据。
