### 2.1 全局实现边界

实施边界按“阶段所有权”判定，而不是按“顺手能否完成”判定。某项工作只有同时满足以下条件，才能进入当前阶段：

1. 直接服务当前阶段的一句话目标；
2. 位于下表允许的层级或适配点内；
3. 不提前实现后续阶段的完整能力；
4. 能由当前阶段的验收清单独立证明完成。

| 阶段 | 主责层级/能力 | 允许的跨层适配 | 明确不进入本阶段 | 阶段出口冻结项 |
|------|---------------|----------------|------------------|----------------|
| P1 | L1、L2 核心、L4 最小管道、测试骨架 | L0 的 manifest；L5 的纯文本最小 UI；临时 Provider 配置入口 | Agent 工具、正式组件体系、历史系统、正式设置 UI、E2E | Port 协议、Provider 工厂、基础消息类型、流结束语义 |
| P2 | L3 全部工具、L1 B站客户端补全、L4 工具编排 | L5 仅消费并展示已有 `videos/insight/tool_*` 消息，不做视觉建设 | 拖拽/主题/完整组件、历史、正式设置、E2E | 工具输入输出、工具事件顺序、WorkingMemory 会话边界 |
| P3 | L5 UI 内容、L6 UI 外壳与样式 | L4/L5 仅做消息到状态/组件的接线；保留临时设置入口可用 | 历史持久化、标题生成、正式 Provider 管理、权限申请、业务工具改造 | ChatState/Action 行为、组件 props、Shadow DOM 与样式注入方案 |
| P4 | L7 历史、同步、保存编排、标题生成 | L5 接入 hydrate/rehydrate 与 HistoryDropdown；L2 只复用活动模型配置 | Provider 表单、权限授权、主题设置、测试体系扩建、工具/UI 重构 | ConversationData v2、存储 key、同步与保存触发语义 |
| P5 | L8 正式设置、迁移、权限授权、全项目质量门禁 | L0 manifest 权限；L2 设置迁移；为可测性做必要注入点 | 新业务工具、新 UI 产品能力、历史协议改版、无验收依据的重构 | 发布包、配置兼容契约、最终测试/CI 基线 |

### 2.2 跨阶段变更规则

- 后续阶段发现已冻结契约必须变更时，先回写契约所属阶段文档，写明根因、兼容方案和回归范围，再改代码；不得静默改签名。
- P4 与 P5 只并行开发无共享入口的模块；共享文件实行单一所有者：`chat-context.tsx`/历史组件归 P4，`settings.ts`/设置组件/manifest 权限归 P5；`App.tsx`、`styles.ts`、`package.json` 的接线按提交顺序串行合并，P5 最终测试在 P4 阶段提交之后执行。
- 临时实现必须标注删除阶段和替代物。未写明退出条件的临时代码不得进入阶段提交。
- 阶段外问题只记录为后续任务；除非阻塞当前验收，否则不在当前阶段修复。

## 3. 子对话（Subagent）执行模型

### 3.1 分工原则

- **主对话**：读设计文档 → 拆任务 → 派发子对话 → 审查产出 → 跑验收 → git 提交
- **子对话**：单一职责，每个子对话领取一个明确模块（输入：设计文档章节 + 旧仓库参照路径；输出：可编译代码 + 自测通过）
- **并行规则**：无依赖的模块并行派发（如 P1 中 L1 类型 / L2 配置 / L4 协议三个子对话可同时启动）；有依赖的串行
- **对接验证**：子对话产出合并后，由主对话按 3.6 §8 对接检查表验证，不通过则打回

### 3.2 子对话任务卡模板

每个子对话任务必须包含：

```
【任务】实现 <模块路径>
【设计依据】Docs/详细设计/3.x §y（必读章节）
【旧仓库参照】Backend/BiliAgent/packages/<路径>（如适用）
【硬性契约】（列出 AI SDK 7.0.22 契约、类型签名、错误码等不可违反项）
【自测要求】tsc -b 通过 + <单测文件>（P1 起）
【禁止】修改任务范围外的文件；引入设计外的依赖
```

### 3.3 全局硬性契约（所有子对话必须遵守）

来自 3.6 §6.3 / 3.7 §1，已核对本地 `ai@7.0.22` 类型：

1. 遍历 `result.stream`（不用 deprecated 的 `fullStream`）
2. `stopWhen: isStepCount(5)`（不用 deprecated 的 `stepCountIs`）；5 是模型 step 上限，不等于每次请求固定调用 5 个工具
3. 流事件字段：`text-delta`/`reasoning-delta` 读 `part.text`；`tool-call` 读 `part.toolCallId/toolName/input`；`tool-result` 读 `part.output`
4. `tool()` 用 `inputSchema`（zod 4，不是旧版 `parameters`）
5. WBI 签名代码原样移植，**不可**用 `URLSearchParams.toString()` 重写（编码敏感）
6. Shadow DOM `mode: 'open'`；CS 内禁止 eval/动态 import
7. 单 Port `bili-agent-chat`；消息类型以 3.2 §3/§4 为唯一契约
8. 系统提示只经 `streamText({ system })` 传入一次

## 4. 渐进式流程（每阶段内部循环）

```
┌─> ① 主对话精读本阶段设计章节，产出任务卡
│   ② 并行派发子对话（无依赖模块）
│   ③ 子对话产出 → 主对话代码审查（契约符合性）
│   ④ 合并 → tsc -b && vite build 构建门禁
│   ⑤ 单测门禁（vitest run，P1 起）
│   ⑥ 手动验收（加载 dist/ 到 Chrome，按验收清单逐项）
│   ⑦ 全过 → git 提交；有未过项 → 回到 ②（针对性修复子对话）
└── ⑧ 阶段风险验证点复核（见各阶段文档）
```

## 5. 验收方式（三级门禁）

| 级别 | 手段 | 频率 |
|------|------|------|
| **L1 静态门禁** | `tsc -b` + `vite build` + `eslint` 零错误 | 每次子对话产出合并后 |
| **L2 自动测试** | `vitest run`（P1 引入）+ typecheck；P5 加 Playwright E2E | 每阶段结束 + 每次触碰已测模块 |
| **L3 手动验收** | Chrome 加载 `dist/`，按各阶段"手动测试步骤"逐项走查 | 每阶段结束 |

**通过标准**：三级全绿才算阶段完成。L3 由用户或主对话（借助 Playwright 驱动 Chrome）执行。

## 6. Git 提交策略

- 每完成一个可验证功能块提交一次（遵循全局规范：中文、写方案与根因）
- 阶段结束必有一次里程碑提交，格式：`feat(P1): 管道打通——<摘要>`
- 提交前必须 L1 门禁通过；阶段提交前必须三级门禁通过
- 分支策略：直接在 master 开发（单人项目）；若某阶段有高风险实验（如 R3 样式验证），可开临时分支验证后合并

## 7. 风险闸口（阻塞性检查点）

| 闸口 | 所在阶段 | 检查内容 | 失败预案 |
|------|---------|---------|---------|
| **G1: AI SDK SW 兼容**（R4） | P1 最早期 | 最小 `streamText` 在 SW 里跑通 | 查报错→polyfill；官方已有扩展案例，概率低 |
| **G2: host_permissions**（R2） | P1 | manifest 补全 9 域名 + optional_host_permissions | 无（纯配置） |
| **G3: SW 休眠**（R1） | P1 | 25s 心跳 + 断连检测 + 60s 超时可用 | 前端超时兜底 |
| **G4: 样式注入**（R3） | P3 最早期 | 1 个组件的 CSS 经 adoptedStyleSheets 生效 | 降级 `<style>` 标签注入 |
| **G5: WorkingMemory 边界**（R10） | P2 | storage.session 跨 SW 重启保留 | 改 storage.local + TTL |

闸口失败时：**停止本阶段后续派发**，先解决闸口再继续。
