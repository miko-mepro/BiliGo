## 0. 实现边界

### 0.1 本阶段必须实现

- 将 P1/P2 已冻结的状态和消息完整呈现为 L5 内容组件与 L6 外壳，不改变工具业务结果。
- 完成面板开关、拖拽缩放、主题、消息/视频/洞察/错误展示、筛选排序和 clarification 回传。
- 用正式 App/Panel/ToggleButton 替换 P1 的临时外壳；临时设置入口可继续挂载，但不在本阶段扩展为正式 Provider 管理。
- P3 拥有主题引擎（`useTheme`、CSS 应用、跨标签页同步）；P5 只提供设置页选择器。Header 只预留历史入口位置，历史行为由 P4 实现。

### 0.2 本阶段明确不做

- 不实现历史存储、hydrate/rehydrate、HistoryDropdown 和标题生成；这些属于 P4。
- 不实现 ProviderList/ProviderForm/TestConnectionButton、设置迁移或自定义 origin 授权；这些属于 P5。
- 不修改 L3 工具算法、L4 工具选择/事件顺序或 Provider 工厂；若发现契约缺陷，只提交阻塞报告并回到所属阶段修订。
- 不引入虚拟滚动等“可选优化”，除非现有验收出现可量化性能问题。
- 不以“原样移植”为由恢复旧仓库的零尺寸 host、旧 Port/useStreamConsumer 或其他已废弃路径；当前 P1 全视口 host 和单 Port 是适配基线。

### 0.3 临时资产退出规则

- P1 的极简输入/列表/按钮被正式组件替代后必须删除，不保留两套 UI 路径。
- `content/settings-panel.tsx` 的最终删除归 P5；P3 只保证设置入口没有因外壳替换而失效。

### 0.4 阶段出口与冻结契约

- 3.2 手动验收九项与组件/hook 测试通过，且 G4 注入方案已确定，P3 才完成。
- 完成后冻结：ChatState/Action 的可观察行为、组件 props、Shadow DOM 挂载方式和样式注入方案。P4/P5 只能增加历史/设置入口，不得重做主界面架构。

## 1. 前置闸口 G4：样式注入验证（R3）

**主对话直接执行**（先于一切组件移植）：

1. 从旧仓库 `styles.ts` 截取任一组件的 CSS 片段
2. 经 `new CSSStyleSheet() + replaceSync + adoptedStyleSheets` 注入 Shadow DOM
3. Chrome 中该片段样式生效 → 通过
4. **失败预案**：降级为 `<style>` 标签注入（保持 Shadow DOM 隔离，仅体积增大）
