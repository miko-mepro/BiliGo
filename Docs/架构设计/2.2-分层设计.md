## 分层原则

### 1. 依赖方向规则（不可违反）

- **上层可以依赖下层，下层不能依赖上层**
- **同层模块之间可以互相依赖，但要最小化**
- **跨层跳级依赖禁止**（L5 不能直接调 L2，必须通过 L3）

### 2. 为什么这样分层

每层的存在理由：

| 层 | 职责 | 为什么在这个位置 |
|---|------|----------------|
| L0 | 构建管线、manifest、SW/CS 入口 | 所有代码的容器，没有它代码跑不起来 |
| L1 | 类型定义、B站API、静态数据 | 一切的类型地基，上面所有层需要这些类型 |
| L2 | 设置读写、Provider 工厂 | L3 需要 model，model 从这里创建 |
| L3 | Port 通信、streamText 调用 | **关键路径**，数据流的"血管" |
| L4 | 7 个 tool 定义、工具执行 | 跑在 L3 管道内部（streamText.tools） |
| L5 | React 状态、消息渲染 | 消费 L3 管道输出，渲染 L4 工具结果 |
| L6 | Panel 外壳、拖拽、样式 | 包裹 L5 内容，纯展示层 |
| L7 | 历史存储、跨标签页同步 | 存 L5 的 state 快照，与管道正交 |
| L8 | 设置 UI、测试 | 最后打磨，依赖 L2+L6 |

## 各层详细定义

### L0 - 构建基础设施 ✅

**职责**：
- Vite 8 + CRXJS 构建管线
- manifest.json（MV3）
- SW 入口骨架（Port 监听）
- CS 入口骨架（Shadow DOM 挂载）

**依赖**：无

**产出物**：
- `dist/` 目录（可加载到 Chrome）
- `service-worker-loader.js`
- `manifest.json`（CRXJS 处理后）
- 打包后的 SW + CS bundle

**状态**：✅ 已完成

### L1 - 共享基础

**职责**：
- 全部类型定义（ChatMessage / BilibiliVideoCard / ProviderConfig / ...）
- bilibili-client（WBI / searchVideo / searchHot / suggest / tags）
- 静态数据（slang-dictionary.json / tag-categories.json）

**依赖**：无

**被依赖**：L2-L8 全部

**为什么是地基**：
- Port 消息里传的是 `ChatMessage[]`
- 工具返回的是 `BilibiliVideoCard[]`
- UI 渲染的是 `ChatMessage`
- 没有类型，上面每层都不知道接收/输出什么

**文件**：

### L2 - 配置与 Provider

**职责**：
- 读写 `chrome.storage.local`（BiliAgentSettings）
- 9 个内置 Provider 定义

- 设置迁移逻辑

**依赖**：L1（需要 ProviderConfig 类型）

**被依赖**：
- L3（需要 model）
- L5（读主题模式）
- L8（设置 UI 读写）

**为什么独立成层**：
- 如果塞进 L3，会产生循环依赖（L3→L2 读配置，L8→L3？）
- settings 是多个层共享的基础设施

**接口**：
```typescript
// 输入
interface ProviderConfig {
  id: string
  name: string
  format: 'openai' | 'anthropic' | 'gemini'
  baseUrl: string
  apiKey: string
  model: string
}

// 输出
function createModel(config: ProviderConfig): LanguageModel
```

### L3 - 通信管道 ⭐ 关键路径

**职责**：
- Port 消息协议定义（CS ↔ SW 通信）
- SW 端：`streamText` 调用 + `onChunk` 推流
- CS 端：`port.onMessage` 消费 + 回调分发
- Port 心跳 / 断连检测
- SESSDATA 获取

**依赖**：L2（需要 model）

**被依赖**：
- L4（工具在 streamText 内执行）
- L5（UI 消费管道输出）

**为什么是关键路径**：
- 这是扩展的"血管"
- 用户输入 → SW → LLM → 工具 → LLM → SW → CS → UI，全走这条管道
- 管道不通，其他层都无法验证

**数据流**：
```
CS 发送:
  { type: 'chat', messages, conversationId }

SW 推流:
  { type: 'chunk', delta: "文本" }
  { type: 'tool_start', toolName: "bilibili_search", args }
  { type: 'tool_result', toolName, result }
  { type: 'videos', videos: BilibiliVideoCard[] }
  { type: 'done' }
  { type: 'error', message }
```

**文件**：
- `background/port-protocol.ts`（新增）
- `background/stream.ts`（新增）
- `content/port-connection.ts`（新增）

- 工具是 `streamText({ tools })` 的参数

```typescript
})
```

## 依赖验证

检查是否违反依赖规则：

✅ **合法依赖示例**：
- L5（UI 内容）→ L3（消费 Port 消息）
- L3（管道）→ L2（创建 model）
- L4（工具）→ L1（调 bilibili-client）

❌ **非法依赖示例**（如果出现就是设计错误）：
- L2 → L3（配置层不能依赖管道）
- L1 → L4（基础层不能依赖工具）
- L5 → L2（UI 不能直接读 settings，必须通过状态传递）

## 总结

**核心设计原则**：依赖方向从下到上，L3 是关键路径。

**分层价值**：
1. 每层可独立验证（L1 完成后能跑 bilibili-client 单测）
2. 职责清晰（业务逻辑 L1-L4，UI L5-L6，基础设施 L7-L8）
3. 替换成本低（换 UI 框架只影响 L5-L6）
4. 测试容易（Mock 下层接口即可测试上层）
