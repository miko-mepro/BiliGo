## 风险详情

### R1 - SW 休眠导致流中断

**问题**：
MV3 Service Worker 在无活动约 30 秒后会被 Chrome 回收。如果 `streamText` 正在执行（比如 LLM 生成较长回复或工具执行慢），SW 被杀后：
- `streamText` 的 Promise 会 reject
- Port 连接断开
- CS 端收不到 `done` 消息，UI 显示无限 loading

**影响**：用户体验极差，看起来"卡住了"

**应对策略**：
1. **Port 长连接保活**：每 25s 发一次心跳 ping/pong
2. **CS 端断连检测**：`port.onDisconnect` 监听，断连后提示用户"连接已断开，请重试"
3. **SW 端错误捕获**：`streamText` Promise 的 catch 里发送 error 消息
4. **超时机制**：前端设置 60s 超时，超时后显示"响应超时"

**代码示例**：
```typescript
// content/port-connection.ts
port.onDisconnect.addListener(() => {
  dispatch({ type: 'SET_ERROR', error: { message: '连接已断开' } })
})

// background/stream.ts
setInterval(() => {
  port.postMessage({ type: 'ping' })
}, 25000)  // 每 25s 心跳
```

### R2 - host_permissions 覆盖不全

**问题**：
当前 manifest 只声明了 3 个 LLM API 域名：
```json
"host_permissions": [
  "https://api.openai.com/*",
  "https://api.anthropic.com/*",
  "https://generativelanguage.googleapis.com/*"
]
```

9 个内置 provider 中的其他 6 个会被拦截：
- DeepSeek: `https://api.deepseek.com/*`
- Moonshot: `https://api.moonshot.cn/*`
- 智谱 GLM: `https://open.bigmodel.cn/*`
- 通义千问: `https://dashscope.aliyuncs.com/*`
- OpenRouter: `https://openrouter.ai/*`
- Ollama: `http://localhost:11434/*`

**影响**：用户选择这些 provider 时完全无法使用

**应对策略**：
立即在 manifest 补全：
```json
"host_permissions": [
  "*://*.bilibili.com/*",
  "https://api.openai.com/*",
  "https://api.anthropic.com/*",
  "https://generativelanguage.googleapis.com/*",
  "https://api.deepseek.com/*",
  "https://api.moonshot.cn/*",
  "https://open.bigmodel.cn/*",
  "https://dashscope.aliyuncs.com/*",
  "https://openrouter.ai/*",
  "http://localhost:11434/*"
]
```

**处理时机**：L2 阶段（配置 Provider 时）

### R3 - Constructable Stylesheets 移植

**问题**：
旧仓库 `content/styles.ts` 有 1734 行 CSS，注入到 Shadow DOM：
```typescript
const sheet = new CSSStyleSheet()
sheet.replaceSync(cssText)
shadow.adoptedStyleSheets = [sheet]
```

不确定 CRXJS 打包后这段代码能否正常工作（旧仓库需要 `fix-content-script.mjs` 内联）。

**影响**：如果失败，整个 UI 没有样式，无法使用

**应对策略**：
1. **M3 阶段先验证**：只移植 1 个组件的样式，验证 `adoptedStyleSheets` 能否工作
2. **备选方案**：如果失败，改用 `<style>` 标签注入（但会增加 Shadow DOM 尺寸）
3. **最坏情况**：保留 Vite 的 CSS 模块化，但会失去 Shadow DOM 完全隔离

**验证命令**：
```typescript
// 最小验证
const sheet = new CSSStyleSheet()
sheet.replaceSync('.test { color: red; }')
shadow.adoptedStyleSheets = [sheet]
// 如果 UI 显示红色文字，说明成功
```

### R4 - AI SDK 在 SW 环境兼容性

**问题**：
AI SDK 可能依赖 Node.js API（如 `Buffer`、`stream`），而 SW 环境不完全支持这些 API。

**影响**：`streamText` 调用失败，整个扩展无法工作

**应对策略**：
1. **M1 阶段优先验证**：最简单的 `streamText` 调用能否跑通
2. **查看官方案例**：vercel-labs/ai-sdk-chrome-extension 仓库已验证可行
3. **查看 zenn.dev 实测**：已确认 SW 里跑 `streamText` 成功
4. **如果失败**：查看具体报错，可能需要 polyfill（但概率低）

**风险评估**：概率低，因为官方已有 Chrome 扩展案例

---

### R5 - content script CSP 限制

**问题**：
MV3 content script 不允许 `eval`、`new Function`、动态 `import()`。如果 AI SDK 内部用了这些，会报错。

**影响**：content script 加载失败

**应对策略**：
1. **CRXJS 静态打包**：CRXJS 会把所有代码打包成静态 bundle，不需要动态加载
2. **AI SDK 不在 CS 执行**：AI SDK 的 `streamText` 在 SW 里跑，CS 只负责 UI，风险更低
3. **如果真的失败**：检查是否有动态 import，改为静态 import

**风险评估**：概率低，因为 AI SDK 在 SW 跑，不在 CS

---

### R6 - Shadow DOM `mode: 'open'` 安全性

**问题**：
旧仓库使用 `attachShadow({ mode: 'open' })`，bilibili 页面 JS 可以通过 `document.getElementById('bili-agent-host').shadowRoot` 访问扩展 UI，理论上可以篡改。

**影响**：低，因为：
1. bilibili 页面 JS 没有动机攻击扩展
2. 即使篡改 UI，也无法窃取 API Key（在 chrome.storage，页面 JS 无法访问）

**应对策略**：
1. **保持 `open` 模式**：因为 React DevTools 需要访问 Shadow DOM
2. **如需加固**：改为 `{ mode: 'closed' }`，但会失去 DevTools 调试能力
3. **监控**：可以定期检查 shadowRoot 是否被篡改（比较 DOM 结构哈希）

**风险接受**：旧仓库也是 open 模式，风险可接受

---

### R7 - API Key 明文存储

**问题**：
用户的 API Key 明文存储在 `chrome.storage.local`。虽然不同扩展的 storage 是隔离的，但：
1. 同源的扩展理论上可以读取
2. 如果设备被入侵，攻击者可以直接读取

**影响**：API Key 泄露，用户可能产生意外费用

**应对策略**：
1. **当前可接受**：Chrome 扩展 storage 沙箱隔离，其他扩展无法访问
2. **L8 阶段评估加密**：可以考虑用 Web Crypto API 加密存储，但密钥存哪里又是问题
3. **最佳实践**：提示用户定期轮换 API Key，设置使用限额

**风险接受**：旧仓库也是明文存储，行业通用做法（因为浏览器扩展的密钥管理没有完美方案）

---

### R8 - AI SDK 版本变更

**问题**：
AI SDK 5→6 升级可能 break API（比如 `streamText` 参数变化、`tool()` 格式变化）。

**影响**：npm 升级后扩展突然不工作

**应对策略**：
1. **锁定版本号**：`package.json` 里写死版本，不用 `^` 或 `~`
   ```json
   "ai": "5.2.3"  // 不要写 "^5.2.3"
   ```
2. **升级前跑测试**：先在本地测试，确认没问题再发布
3. **查看 changelog**：AI SDK 发布时查看 breaking changes

---

### R9 - WBI 签名失效

**问题**：
B 站可能更新 WBI 签名算法，导致旧的 `wbi.ts` 生成的签名无效，搜索 API 返回错误。

**影响**：视频搜索功能完全失效

**应对策略**：
1. **bilibili-client 独立模块**：可以单独更新，不影响其他层
2. **社区监控**：关注 B 站 API 逆向社区（如 bilibili-API-collect），有更新及时同步
3. **降级方案**：如果签名失效，可以暂时去掉 SESSDATA（降级为游客搜索）

---

### R10 - SW 被杀后 WorkingMemory 丢失

**问题**：
`working-memory.ts` 使用 `chrome.storage.session`，数据绑定 SW 生命周期。SW 被回收后，会话记忆（`triedKeywords`、`rejectedBvids`）丢失。

**影响**：用户换了关键词重试，LLM 可能又搜一遍已经试过的

**应对策略**：
1. **改用 chrome.storage.local + TTL**：手动管理过期时间（5 分钟）
2. **或者接受数据丢失**：WorkingMemory 是优化，不是核心功能，丢失影响不大

**处理时机**：L4 阶段（实现 working-memory 时）

---

### R11 - content script 重复注入

**问题**：
bilibili 是 SPA，路由切换（如从首页到视频页）可能触发 content script 重复注入。

**影响**：出现多个扩展面板

**应对策略**：
已有防御代码：
```typescript
if (document.getElementById(HOST_ID)) return  // 防重复
```

**风险评估**：旧仓库已处理，低风险

---

### R12 - 跨标签页状态冲突

**问题**：
多标签页同时使用，历史同步的 `syncId` 机制可能冲突（两个标签页同时写入）。

**影响**：历史记录混乱或丢失

**应对策略**：
旧仓库已有 `HistorySync` 机制：
- 每次写入生成唯一 syncId
- pending write ID 追踪（200ms TTL）
- 避免自身写入触发回调

直接移植即可。

## 优先处理计划

| 优先级 | 风险 | 处理时机 | 处理方式 |
|--------|------|----------|----------|
| **P0** | R2 | L2 阶段 | manifest 补全 9 个 provider 域名 |
| **P0** | R1 | L3 阶段 | Port 心跳 + 断连检测 + 错误重试 |
| **P1** | R4 | M1 验证 | 最小 streamText 测试 |
| **P1** | R7 | L8 阶段 | 评估加密方案（可选） |
| **P2** | R3 | L6 阶段 | 先验证 1 个组件样式 |
| **P2** | R10 | L4 阶段 | 改用 storage.local + TTL |
| **P3** | R6-R12 | 各层实现时 | 按现有方案处理 |

## 总结

**高风险项（2 个）**：
- R2 host_permissions - 必须立即修复
- R1 SW 休眠 - M1 必须处理

**中风险项（6 个）**：
- R4, R5 需要 M1 验证
- R3, R10 在实现时处理
- R7, R8 长期监控

**低风险项（4 个）**：
- 旧仓库已处理或影响可接受
