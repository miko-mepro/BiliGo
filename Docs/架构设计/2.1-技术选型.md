# 2.1 技术选型

## 已确定的技术栈

| 层面 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| 构建工具 | Vite | 8.x | 2026 最快前端构建工具，HMR 极快，ESM 原生 |
| 扩展打包 | @crxjs/vite-plugin | 2.x | 自动处理 manifest、SW 模块化、content script 打包与 HMR |
| UI 框架 | React | 19.x | 旧仓库已用 React，15 个组件直接移植 |
| 语言 | TypeScript | 6.x | 旧仓库已用 TS，类型安全 |
| AI SDK | Vercel AI SDK (`ai`) | 7.x | 替换自写 adapter（1300 行），官方支持 Chrome 扩展 |
| Provider 包 | @ai-sdk/openai / anthropic / google | 4.x | openai/anthropic/google 三种格式 |
| 参数校验 | zod | 4.x | AI SDK tool() 的 inputSchema 必需 |
| Chrome API | @types/chrome | 0.2.x | MV3 API 类型声明 |
| 测试 | Vitest + Playwright | 待迁移引入 | 旧仓库已用，29 单测 + 4 E2E |

## 核心选型决策

### 1. Vite 8 + CRXJS

**为什么选**：
- Vite 8 在 2026 年已成为前端构建标准（比 Webpack 快 10-100 倍）
- CRXJS 是当前项目采用的 Vite MV3 扩展插件，负责 manifest 多入口和扩展构建
- 旧仓库需要 `fix-content-script.mjs` 手动内联 settings 代码，CRXJS 自动处理

**对比**：
| 方案 | 优点 | 缺点 |
|------|------|------|
| **Vite + CRXJS** | HMR 快、自动处理 manifest、零配置 | CRXJS 是 beta（但广泛使用） |
| Webpack + CRX | 成熟稳定 | 构建慢、配置复杂 |
| 纯 Vite 手动 | 完全可控 | 需要处理 CSP、content script 内联等坑 |

### 2. Vercel AI SDK

**替换内容**：

旧仓库自写的 llm-provider 包（~1300 行）：
- `adapters/openai.ts` (444 行) - SSE 流解析、delta 拼接、错误处理
- `adapters/anthropic.ts` (~300 行)
- `adapters/gemini.ts` (~300 行)
- `provider.ts` (427 行) - OpenRouter 支持、provider 工厂、自动回退
- `vision.ts` (19 行) - Vision 检测
- `factory.ts` (50 行)

**为什么替换**：

| 维度 | 自写 adapter | AI SDK |
|------|-------------|--------|
| 代码维护 | 需要跟随每个 provider API 变更 | npm 升级 |
| Provider 切换 | 手写 switch-case，每种格式不同 | 统一接口 `createOpenAI()` |
| SSE 流解析 | 手写 parseSse + delta 拼接（~200 行） | 内部处理 |
| tool_call 分发 | 手写 switch-case 5 个 tool（router.ts ~20 行） | `tools` 参数自动执行 |
| 多步工具循环 | 手写 MAX_TOOL_ROUNDS=5 + while loop（~75 行） | `stopWhen: stepCountIs(5)` 一行 |
| 错误重试 | 手写 shouldRetryWithFallback（~30 行） | 内置 middleware |
| Vision 支持 | 手写检测（~19 行） | 原生支持 |

**官方支持证据**：
- AI SDK 官方博客（v5 起）：明确提到 "browser extensions" 使用场景
- 官方 vercel-labs/ai-sdk-chrome-extension 仓库
- zenn.dev 实测案例：SW 里跑 streamText

**风险**：AI SDK 版本变更可能 break API → 应对：锁定版本号

### 3. React 19

**为什么保留**：
- 旧仓库 15 个 UI 组件全是 React，重写成本高
- React 19 与旧仓库组件和 Hooks 结构兼容；React Compiler 需要额外配置，不作为本项目的默认能力
- Shadow DOM + React 19 兼容性已验证（旧仓库正常运行）

**备选方案否决**：
- Vue 3 / Svelte：需要重写所有组件（15 个 + 3 hooks）
- 原生 Web Components：失去 React 生态（状态管理、hooks）

### 4. TypeScript 6

**为什么保留**：
- 旧仓库已全 TS，类型定义完整（shared-types 173 行）
- TS 6 新特性：更好的类型推断、性能提升
- MV3 API 需要类型安全（@types/chrome）

### 5. zod

**为什么选用**：
- AI SDK 7 的 `tool()` 使用 `inputSchema`（旧版字段名为 `parameters`）。AI SDK 类型接受 `FlexibleSchema`，本项目选用 Zod 4 来同时获得类型推断与运行时校验：
  ```typescript
  tool({
    inputSchema: z.object({ input: z.string() }),  // 本项目选用 Zod 4
    execute: async ({ input }) => { ... }
  })
  ```
- 自动生成 JSON Schema 给 LLM
- 运行时参数校验
- 注意：项目实际安装 Zod 4.x；网上大量教程基于 Zod 3，错误定制等 API 有差异，以 Zod 4 文档和本地类型定义为准

## Provider 支持矩阵

旧仓库 9 个内置 provider 映射到 AI SDK：

| Provider | 旧格式 | AI SDK 包 | 兼容性 |
|----------|--------|-----------|--------|
| OpenAI 官方 | openai | @ai-sdk/openai | ✅ 原生 |
| Anthropic 官方 | anthropic | @ai-sdk/anthropic | ✅ 原生 |
| Google Gemini | gemini | @ai-sdk/google | ✅ 原生 |
| DeepSeek | openai | @ai-sdk/openai | ✅ 兼容（baseURL 换） |
| Moonshot/Kimi | openai | @ai-sdk/openai | ✅ 兼容 |
| 智谱 GLM | openai | @ai-sdk/openai | ✅ 兼容 |
| 通义千问 | openai | @ai-sdk/openai | ✅ 兼容 |
| OpenRouter | openai | @ai-sdk/openai | ✅ 兼容 |
| Ollama 本地 | openai | @ai-sdk/openai | ✅ 兼容 |

**实现方式**：
```typescript
function createModel(config: ProviderConfig): LanguageModel {
  switch (config.format) {
    case 'openai':
      return createOpenAI({ 
        apiKey: config.apiKey, 
        baseURL: config.baseUrl 
      }).chat(config.model)
    case 'anthropic':
      return createAnthropic({ ... }).chat(...)
    case 'gemini':
      return createGoogle({ ... }).chat(...)
  }
}
```

## 测试框架

| 工具 | 用途 | 旧仓库状态 |
|------|------|-----------|
| Vitest | 单元测试（29 个） | ✅ 已有 |
| Playwright | E2E 测试（4 个） | ✅ 已有 |
| @testing-library/react | React 组件测试 | ✅ 已有 |

**移植策略**：
- 单测：需要适配 AI SDK 改动（mock streamText 而不是 mock adapter）
- E2E：基本不变（测 UI 交互，不测 LLM）

## 未选方案及原因

| 方案 | 否决理由 |
|------|---------|
| LangChain.js | 过重（~100MB），抽象层太多，Chrome 扩展场景不匹配 |
| 直接用 OpenAI SDK | 只支持 OpenAI 格式，Anthropic/Gemini 需要 separate SDK |
| Web Component 原生 | 失去 React 生态，需重写所有组件 |
| Webpack + CRX | 构建慢（旧仓库构建 ~15s vs Vite ~200ms） |
| Parcel | MV3 支持不成熟 |

## 技术选型风险

| 风险 | 概率 | 应对 |
|------|------|------|
| CRXJS beta 状态 | 低 | 已被大量扩展使用（GitHub 2k+ stars），社区活跃 |
| AI SDK 版本变更 | 中 | 锁定版本号，升级前跑测试 |
| React 19 breaking changes | 低 | React 19 正式版，向后兼容 |
| TS 6 新特性不稳定 | 低 | 只用稳定特性，不用 experimental |

## 总结

核心决策：
1. **构建**：Vite 8 + CRXJS → 省掉 1300 行自写 adapter + fix-content-script
2. **AI**：AI SDK 7 → 替换自写 llm-provider，减少维护成本
3. **UI**：保留 React 19 + TS 6 → 最小化移植成本
4. **测试**：保留 Vitest + Playwright → 已有 33 个测试

**代码减少**：~1500 行（adapter + SSE 解析 + tool loop + fix-script）  
**维护减少**：OpenAI/Anthropic/Gemini API 变更不需要手动改 adapter
