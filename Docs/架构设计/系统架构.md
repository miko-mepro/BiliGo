# BiliGo 系统架构

## 架构概述

BiliGo 采用 **8 层分层架构**，从底层构建基础设施到顶层用户界面，严格遵循单向依赖原则（下层不依赖上层）。

## 分层详解

### L0: 构建基础设施 (Build Infrastructure)

**职责**: 
- 提供开发构建能力
- 生成符合 Chrome MV3 规范的扩展包

**技术栈**:
- Vite 8: 开发服务器 + HMR
- @crxjs/vite-plugin: Chrome 扩展构建插件
- manifest.json: MV3 清单文件

**状态**: ✅ 已完成

---

### L1: 共享基础层 (Shared Foundation)

**职责**:
- 定义跨上下文共享的 TypeScript 类型
- 封装 Bilibili API 客户端

**模块**:
- `shared-types/`: Port 消息类型、ChatState、Tool 参数类型
- `bilibili-client/`: 视频搜索、视频详情、评论获取 API

**依赖**: 无（纯粹的工具库）

**状态**: 🔄 待迁移（M1 阶段）

---

### L2: 运行时上下文 (Runtime Contexts)

#### L2-SW: Service Worker

**职责**:
- 接收 CS 发来的聊天请求
- 调用 Vercel AI SDK 的 `streamText`
- 将流式响应分块通过 Port 发送回 CS

**核心逻辑**:
```typescript
// 伪代码
chrome.runtime.onConnect.addListener((port) => {
  port.onMessage.addListener(async (msg: ChatRequest) => {
    const stream = await streamText({
      model: getProvider(msg.provider),
      messages: msg.messages,
      tools: { searchBilibiliVideos, getVideoInfo }
    });
    
    for await (const chunk of stream.textStream) {
      port.postMessage({ type: 'chunk', data: chunk });
    }
    port.postMessage({ type: 'done' });
  });
});
```

**状态**: 🔄 待实现（M1 阶段）

#### L2-CS: Content Script

**职责**:
- 在页面中创建 Shadow DOM
- 建立与 SW 的 Port 连接
- 将用户输入发送给 SW
- 消费 SW 返回的流式响应并渲染到 UI

**状态**: 🔄 待实现（M1-M3 阶段）

---

### L3: 通信管道 (Communication Pipeline) 【关键路径】

**职责**:
- 定义 CS ↔ SW 消息协议
- 处理流式响应的分块传输
- 错误处理和重连机制

**消息类型**:
```typescript
// Port 消息协议
type PortMessage =
  | { type: 'chat-request'; payload: ChatRequest }
  | { type: 'chunk'; payload: string }
  | { type: 'tool-call'; payload: ToolCall }
  | { type: 'done' }
  | { type: 'error'; payload: Error };
```

**风险**: 
- R1: SW 休眠导致 Port 断连（需保活机制）
- R3: 流式响应丢块（需序列号 + 重传）

**状态**: 🔄 待设计（M1 阶段）

---

### L4: AI 提供商抽象层 (AI Provider Abstraction)

**职责**:
- 使用 Vercel AI SDK 包装所有 LLM 提供商
- 提供统一的 `LanguageModel` 接口

**支持的提供商** (9 个):
1. OpenAI (gpt-4o, gpt-4o-mini, o1-preview, o1-mini)
2. Anthropic (claude-3.5-sonnet, claude-3-opus)
3. Google (gemini-2.0-flash-exp, gemini-1.5-pro)
4. DeepSeek (deepseek-chat, deepseek-reasoner)
5. XAI (grok-2-1212, grok-2-vision-1212)
6. Alibaba Qwen (qwen-plus, qwen-turbo)
7. 01.AI (yi-lightning, yi-large)
8. OpenRouter (统一网关)
9. Cloudflare Workers AI (llama-3.3-70b)

**实现**:
```typescript
// Provider 工厂
export function getProvider(config: ProviderConfig): LanguageModel {
  switch (config.provider) {
    case 'openai':
      return openai(config.model, { apiKey: config.apiKey });
    case 'anthropic':
      return anthropic(config.model, { apiKey: config.apiKey });
    // ... 其他 7 个提供商
  }
}
```

**状态**: 🔄 待实现（M1-M2 阶段）

## 架构原则

### 1. 单向依赖原则
- 依赖方向：L0 → L1 → L2 → ... → L8
- **禁止**: L6 直接调用 L3（需通过 L5 或 L4）
- **允许**: L6 依赖 L1（共享类型）

### 2. 上下文隔离原则
- Content Script 和 Service Worker 是独立的 JS 上下文
- **禁止**: CS 直接导入 SW 模块（会导致代码重复打包）
- **正确**: 通过 Port 消息通信

### 3. 接口稳定性原则
- L3（通信管道）的消息协议是最稳定的契约
- 修改协议需同时更新 CS 和 SW 两端

### 4. 风险前置原则
- 优先实现高风险模块（L3 通信管道）
- 延后实现低风险模块（L8 设置界面）

---

## 关键路径分析

### 最短路径: L0 → L1 → L2 → L3 → L4
这是 **M1 里程碑**的核心路径，必须首先打通：

1. L0: 构建系统 ✅（已完成）
2. L1: 移植 shared-types + bilibili-client
3. L2: 实现 SW 和 CS 的基本骨架
4. L3: 定义 Port 消息协议 + 实现流式传输
5. L4: 包装 1 个 Provider（如 OpenAI）

M1 完成标准：**CS 可以通过 SW 调用 OpenAI API 并显示流式响应**

## 扩展性设计

### 新增 LLM 提供商
只需修改 L4 层，无需改动其他层：

```typescript
// providers/baichuan.ts
import { createBaichuan } from '@ai-sdk/baichuan'; // 假设有这个包

export function createBaichuanProvider(config: ProviderConfig) {
  return createBaichuan(config.model, { apiKey: config.apiKey });
}
```

### 新增工具函数
只需修改 L5 层：

```typescript
// tools/getBilibiliComments.ts
export const getBilibiliComments = tool({
  description: '获取B站视频评论',
  parameters: z.object({
    bvid: z.string().describe('视频 BV 号'),
    count: z.number().optional().describe('评论数量')
  }),
  execute: async ({ bvid, count }) => {
    // 调用 L1 的 bilibili-client
    return await bilibiliClient.getComments(bvid, count);
  }
});
```
