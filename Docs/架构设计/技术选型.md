# BiliGo 技术选型

## 选型概览

| 技术领域 | 选型方案 | 版本 | 选型理由 |
|---------|---------|------|---------|
| 构建工具 | Vite | 8.x | 开发体验最佳，HMR 快速 |
| Chrome 扩展插件 | @crxjs/vite-plugin | latest | Vite + MV3 最佳集成方案 |
| UI 框架 | React | 19.x | 组件化开发，生态成熟 |
| 类型系统 | TypeScript | 6.x | 类型安全，IDE 支持好 |
| AI SDK | Vercel AI SDK | 5.x | 流式响应标准化，多模型统一接口 |
| Schema 验证 | Zod | latest | AI SDK 官方推荐，类型推断强 |

---

## 核心选型详解

### 1. Vercel AI SDK 5.x

#### 选型理由

**为什么不继续使用自写 llm-provider？**

| 对比维度 | 自写 llm-provider | Vercel AI SDK |
|---------|------------------|---------------|
| 开发成本 | 需自己实现所有 Provider 适配器 | 官方维护 9+ Provider |
| 流式响应 | 需自己处理 SSE 解析 | 内置 `streamText` API |
| 工具调用 | 需自己解析 Function Calling | 标准化 `tools` 参数 |
| 错误处理 | 需自己实现重试逻辑 | 内置重试机制 |
| 类型安全 | 手动维护类型定义 | 自动推断返回类型 |
| 社区支持 | 无 | Vercel 官方维护 + 活跃社区 |

**技术优势**:
1. **统一接口**: 所有模型使用相同的 `streamText` API
2. **自动流式处理**: 内置 `textStream` / `fullStream` 迭代器
3. **工具调用标准化**: Zod Schema → JSON Schema 自动转换
4. **多模态支持**: 内置图片 / 音频处理（未来扩展）

#### 风险评估

| 风险 | 缓解措施 |
|-----|---------|
| SDK 版本升级破坏性变更 | 锁定 5.x 大版本，定期 review changelog |
| 某些 Provider 不支持 | 使用 OpenRouter 作为兜底网关 |
| Service Worker 环境兼容性 | M1 阶段优先验证 SW 环境 |

### 2. Chrome Extension MV3

#### 为什么必须使用 MV3？

Chrome 官方已宣布：
- 2024 年 1 月：停止接受新 MV2 扩展
- 2025 年 6 月：现有 MV2 扩展强制下架

**MV3 核心变化**:
1. **Background Page → Service Worker**: 
   - 无法使用 DOM API
   - 需处理休眠和唤醒
2. **网络请求限制**: 
   - 需在 `host_permissions` 中声明所有 API 域名
3. **内容安全策略**: 
   - 禁止 `eval()` 和内联脚本

#### 架构影响

**必须适配的点**:
- ✅ 使用 `chrome.runtime.onConnect` 建立持久连接（Port）
- ✅ 所有 LLM API 域名写入 `manifest.json` 的 `host_permissions`
- ⚠️ SW 休眠处理：需保活机制（30s 心跳包）

### 3. Vite + @crxjs/vite-plugin

#### 为什么不用 Webpack？

| 对比维度 | Webpack | Vite |
|---------|---------|------|
| 开发启动速度 | 10-30s | <1s |
| HMR 速度 | 2-5s | <100ms |
| 配置复杂度 | 高（需配置 content/background 多入口） | 低（CRXJS 自动处理） |
| 生态成熟度 | 非常成熟 | 快速成长中 |

**CRXJS 优势**:
- 自动解析 `manifest.json` 并生成多入口配置
- 自动处理 Service Worker 和 Content Script 的打包
- 支持 HMR（Hot Module Replacement）

**已知问题**:
- CRXJS 对 MV3 的支持仍在完善（可能有小 bug）
- 解决方案：遇到问题优先查阅 CRXJS GitHub Issues

---

### 4. React 19

#### 为什么选 React？

**对比 Vue 3 / Svelte**:

| 框架 | 优势 | 劣势 |
|------|-----|-----|
| React 19 | 生态最大，RSC 支持，团队熟悉 | 包体积较大 |
| Vue 3 | 上手简单，性能好 | Chrome 扩展案例较少 |
| Svelte | 包体积最小，编译时优化 | 生态较小，学习曲线陡 |

**选择 React 的原因**:
1. 团队已有 React 经验（减少学习成本）
2. Chrome 扩展 + React 案例丰富
3. Shadow DOM 集成方案成熟

#### React 19 新特性利用

```typescript
// 使用 use() hook 简化异步数据获取
function ChatMessage({ messagePromise }) {
  const message = use(messagePromise); // React 19 新 API
  return <div>{message.content}</div>;
}
```

### 5. TypeScript 6.x

#### 为什么必须用 TypeScript？

**类型安全收益**:
1. **Port 消息协议类型检查**: 
   ```typescript
   // CS 和 SW 共享类型定义
   type ChatRequest = {
     messages: Message[];
     provider: ProviderConfig;
   };
   ```
2. **工具参数自动推断**:
   ```typescript
   // Zod Schema 自动推断出 TypeScript 类型
   const schema = z.object({ keyword: z.string() });
   type Params = z.infer<typeof schema>; // { keyword: string }
   ```

#### TypeScript 6 新特性

- **类型缩窄优化**: 更智能的类型推断
- **装饰器标准化**: 未来可能用于依赖注入

---

### 6. Zod

#### 为什么选 Zod 而非其他验证库？

| 验证库 | 优势 | 与 AI SDK 集成 |
|-------|-----|---------------|
| Zod | 类型推断强，链式 API 优雅 | ✅ 官方推荐 |
| Yup | 社区大，异步验证支持好 | ❌ 需手动转换 |
| Joi | Node.js 生态成熟 | ❌ 不支持浏览器 |
| io-ts | 函数式编程风格 | ❌ 学习曲线陡 |

**Zod 与 AI SDK 的完美结合**:

```typescript
import { z } from 'zod';
import { tool } from 'ai';

export const searchTool = tool({
  description: '搜索B站视频',
  parameters: z.object({
    keyword: z.string().describe('搜索关键词'),
    page: z.number().optional().describe('页码')
  }),
  execute: async ({ keyword, page }) => {
    // 参数类型自动推断为 { keyword: string; page?: number }
  }
});
```

## 不选方案及理由

### 为什么不用 Plasmo Framework？

Plasmo 是专门为 Chrome 扩展设计的框架，但我们选择 Vite + CRXJS 的原因：

| 对比维度 | Plasmo | Vite + CRXJS |
|---------|--------|--------------|
| 学习成本 | 需学习 Plasmo 特有 API | 使用标准 Vite 配置 |
| 灵活性 | 高度封装，定制困难 | 完全掌控构建流程 |
| 社区规模 | 小众 | Vite 社区极大 |
| 调试体验 | 黑盒，出问题难排查 | 透明，容易定位问题 |

### 为什么不用 LangChain？

LangChain 是更上层的编排框架，但不适合 BiliGo：

| 对比维度 | LangChain | Vercel AI SDK |
|---------|----------|---------------|
| 定位 | Agent 编排框架 | LLM 调用基础库 |
| 包体积 | >500KB | <100KB |
| 学习曲线 | 陡峭（概念多） | 平缓（API 简单） |
| Chrome 扩展适配 | 未优化（依赖 Node.js API） | 原生支持浏览器 |

**结论**: BiliGo 只需简单的 LLM 调用 + Tool Calling，无需 LangChain 的复杂编排能力。
