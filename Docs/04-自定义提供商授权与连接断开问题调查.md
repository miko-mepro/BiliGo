# 自定义提供商授权与连接断开问题调查

## 调查范围

本次仅记录问题和调查结论，不修改业务代码，不进行问题修复。

调查对象是自定义提供商配置过程中出现的两条提示：

1. 保存配置时显示“需要授权访问该域名”。
2. 点击“测试连接”后显示“连接失败：连接已断开”。

## 结论

两条提示不是同一个直接问题，也不在同一条错误处理链路中。

- “需要授权访问该域名”属于 Chrome 扩展的动态 Host 权限申请失败，发生在保存自定义提供商配置阶段。
- “连接失败：连接已断开”属于扩展内部 Runtime Port 在发送测试消息时已经失效，发生在测试连接阶段。
- 自定义提供商的远端网络错误、鉴权错误和接口错误，在消息已经成功发送到 Service Worker 后，会通过 `connection_result` 返回，通常不会显示“连接已断开”。
- 两者存在一个可能的间接关联：设置页关闭、重建或卸载时会释放设置专用 Port。如果释放 Port 与点击测试连接发生竞态，可能看到“连接已断开”；这仍然是 Port 生命周期问题，不是 Host 权限申请失败直接导致的结果。

## 两条提示的触发链路

### “需要授权访问该域名”

触发位置：`Main/src/components/model-settings/SettingsPanel.tsx:176-248`。

保存时，组件遍历 provider 列表，只对满足以下条件的 provider 申请动态权限：

- `provider.isCustom === true`。
- `baseUrl` 非空。
- `baseUrl` 不属于内置 provider 域名。
- `resolveOriginPattern(baseUrl)` 可以生成有效的权限匹配规则。

具体调用链如下：

1. `SettingsPanel.tsx:187-207` 收集自定义 provider 的目标域名。
2. `origin-pattern.ts:66-98` 将 `baseUrl` 转换成 `http(s)://.../*` 权限规则。
3. `SettingsPanel.tsx:209-213` 调用 `chrome.permissions.request({ origins: patterns })`。
4. `SettingsPanel.tsx:214-218` 在 API 返回 `false` 时显示“需要授权访问该域名”。
5. `SettingsPanel.tsx:220-224` 在 Chrome API 抛异常时也显示同一提示。

因此，当前 UI 不区分“用户拒绝授权”和“权限 API 异常”，这两种情况会显示相同文案。该权限对应的可选 Host 权限在 `Main/manifest.json:30-33` 声明为 `https://*/*` 和 `http://*/*`；内置 provider 的固定域名在 `Main/manifest.json:17-28` 已列入 `host_permissions`，保存时会被跳过。

### “连接失败：连接已断开”

触发位置：`Main/src/components/model-settings/TestConnectionButton.tsx:161-172`。

具体调用链如下：

1. `Panel.tsx:425-445` 在设置页打开时创建设置专用 `chrome.runtime.Port`，并将其传给 `SettingsPanel` 和 `TestConnectionButton`。
2. `TestConnectionButton.tsx:132-148` 注册 `port.onMessage` 监听器，等待 `connection_result`。
3. `TestConnectionButton.tsx:164-165` 调用 `port.postMessage({ type: "test_connection", provider })`。
4. 如果 Port 在发送瞬间已经断开，`postMessage` 同步抛异常。
5. `TestConnectionButton.tsx:166-171` 捕获异常，设置 `errorMessage` 为“连接已断开”并清理监听器和定时器。
6. `TestConnectionButton.tsx:215-222` 将其渲染为“✕ 连接失败：连接已断开”。

这条路径反映的是扩展内部通信通道不可用，而不是远端 provider API 返回了连接错误。

## 后台测试连接的错误边界

测试消息正常送达后，由 `Main/src/background/stream.ts:514-557` 处理：

- `stream.ts:521-530` 校验 provider 配置。
- `stream.ts:534-542` 创建临时 model 并执行 `generateText`，后台超时为 10 秒。
- `stream.ts:545` 在请求成功时返回 `{ type: 'connection_result', ok: true }`。
- `stream.ts:546-555` 在网络错误、鉴权错误、超时等情况下返回 `{ type: 'connection_result', ok: false, error }`。
- `stream.ts:591-596` 对调用侧未捕获异常提供兜底的失败结果。

错误文案还会经过 `Main/src/background/port-protocol.ts:96-132` 的错误码映射。例如鉴权错误通常映射为“API Key 无效，请检查设置”，网络错误通常映射为“网络连接失败”。这些错误属于 provider 请求或后台处理阶段，与前端 `postMessage` 同步抛出的“连接已断开”不同。

## 可能的间接竞态

设置专用 Port 的创建和销毁位于 `Main/src/components/Panel.tsx:425-445`：

- 设置页打开时调用 `chrome.runtime.connect({ name: "bili-agent-chat" })`。
- 设置页关闭或组件 effect 清理时调用 `port.disconnect()`。
- `SettingsPanel.tsx:437-446` 将当前 Port 传给测试按钮。

如果用户在设置页关闭、切换导致组件重建或 Port 即将被清理的时间窗口内点击“测试连接”，测试按钮可能拿到已经失效的 Port，从而进入“连接已断开”路径。这是设置页生命周期与测试操作之间的竞态，不是 `chrome.permissions.request()` 返回 `false` 或抛异常后自动造成的同一错误。

另外，测试按钮当前只监听 `port.onMessage`，没有在测试等待期间监听 `port.onDisconnect`。如果消息发送成功后 Port 才异步断开，前端可能收不到 `connection_result`，最后由 `TestConnectionButton.tsx:155-159` 的 12 秒兜底显示“连接超时”，而不是“连接已断开”。

## 后续复现时应区分的现场证据

为了确认实际用户环境属于哪一条链路，应分别记录：

1. 保存按钮触发时 `chrome.permissions.request()` 的 origins 参数、返回值或异常信息。
2. 点击测试连接时 Port 是否已经触发 `onDisconnect`，以及 `postMessage` 是否同步抛异常。
3. 如果消息已成功发送，记录 Service Worker 是否收到 `test_connection`，以及是否返回 `connection_result`。
4. 设置页是否在点击测试连接的同时发生关闭、切换或组件重建。

## 最终判定

当前代码证据支持的判定是：

> “需要授权访问该域名”与“连接失败：连接已断开”不是同一个直接问题。前者是动态 Host 权限申请失败或被拒绝，后者是设置专用 Runtime Port 在发送测试请求时已经断开。只有在设置页生命周期导致 Port 失效的情况下，两者才可能在用户操作层面先后出现或被误认为有关联。
