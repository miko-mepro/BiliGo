## 发现的问题清单

### 问题 1 · ⑦并发/资源泄漏 · 🟡警告

- **位置**：`src/background/stream.ts:316` + `src/background/stream.ts:422-426`
- **问题**：并发 chat 请求覆盖 abortController。`stream.ts:571` 使用 `void handleChatMessage(...)` 发起异步处理，若 CS 在首个 chat 流尚未结束时发送第二个 chat，第二个请求在 `stream.ts:316` 执行 `session.abortController = abortController` 会覆盖首个请求的 controller 引用。首个流仍在迭代但 `handleStop` 只能中止第二个请求，且两个流的消息会交错推送到同一 Port。
- **修复建议**：在启动新 chat 前 abort 旧流：

```ts
// stream.ts handleChatMessage 开头，readBiliAgentSettings 之前
if (session.abortController) {
  session.abortController.abort()
}
```

### 问题 2 · ⑦并发/资源泄漏 · 🟡警告

- **位置**：`src/background/stream.ts:312-329`（try 起始于 331 行，finally 在 404 行）
- **问题**：try 块（331 行）滞后于 WorkingMemory 创建（312 行）。`WorkingMemoryStore.create(traceId)` 写入 chrome.storage.session，但 `try {` 在 331 行才开始。中间的 `buildTools(traceId)`（313 行）、`new AbortController()`（315 行）、`streamText({...})`（322-329 行）若同步抛出，`finally` 块不会执行，`WorkingMemoryStore.release` 不会被调用。虽有 5 分钟 TTL 兜底但属于资源泄漏。
- **修复建议**：将 try 块起始位置提前到 create 之前，并用标志位守卫 release：

```ts
const traceId = createTraceId(msg.conversationId)
let memoryCreated = false
try {
  await WorkingMemoryStore.create(traceId)
  memoryCreated = true
  const tools = buildTools(traceId)
  // ... 其余 streamText 及流循环逻辑不变 ...
} catch (err) {
  if (!isAbortError(err)) {
    const message = err instanceof Error ? err.message : String(err)
    const code = inferErrorCode(message)
    postToPort(port, session, { type: 'error', message: friendlyMessage(code, message), code })
  }
} finally {
  if (memoryCreated) {
    try { await WorkingMemoryStore.release(traceId) } catch { /* 静默 */ }
  }
}
```

### 问题 3 · ⑩错误处理缺失 · 🟠严重

- **位置**：`src/background/stream.ts:571`、`src/background/stream.ts:574`、`src/background/stream.ts:577`
- **问题**：`void handleChatMessage(...)` 丢弃 Promise。`handleChatMessage` 中 `stream.ts:295`（readBiliAgentSettings）、`stream.ts:309`（createModel）、`stream.ts:312`（WorkingMemoryStore.create）、`stream.ts:313`（buildTools）、`stream.ts:322`（streamText）均在 try 块（331 行）之外。若这些调用 reject/throw，Promise 无 catch 处理，变为 unhandled rejection。同理 `handleGenerateTitle`（574 行）和 `handleTestConnection`（577 行）的 `void` 调用也存此风险。
- **修复建议**：为 setupPortListener 中的 void 调用添加 catch：

```ts
case 'chat':
  void handleChatMessage(port, session, msg).catch(() => {
    // 兜底：try 块外异常，确保推送 error + done
    if (!session.disconnected) {
      try {
        postToPort(port, session, { type: 'error', message: friendlyMessage('NETWORK_ERROR'), code: 'NETWORK_ERROR' })
        postToPort(port, session, { type: 'done' })
      } catch { /* 端口已断开 */ }
    }
  })
  break
```

### 问题 4 · ⑩错误处理缺失 · 🔵建议

- **位置**：`src/background/stream.ts:54-57`
- **问题**：`postToPort` 先检查 `state.disconnected`，再调用 `port.postMessage`。若在检查通过后、postMessage 前端口断开，`port.postMessage` 会抛出 `Error: Attempting to use a disconnected port`。
- **修复建议**：在 postToPort 内部吞掉断开端口的异常：

```ts
export function postToPort(port: chrome.runtime.Port, state: PortState, msg: SWMessage): void {
  if (state.disconnected) return
  try {
    port.postMessage(msg)
  } catch {
    // 端口在检查后断开，忽略
    state.disconnected = true
  }
}
```
