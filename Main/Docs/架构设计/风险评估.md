## R1: SW 休眠导致 Port 断连

### 风险描述
MV3 的 Service Worker 在 30 秒无活动后会被 Chrome 休眠。休眠后所有 Port 连接断开，正在进行的流式响应会丢失，用户看到对话中断。

### 影响范围
- L2-SW: Service Worker 生命周期
- L3: Port 通信管道
- 间接影响 L6: UI 显示断连状态

### 严重程度: 🔴 高

### 触发条件
1. 用户发送消息后，LLM 正在流式响应
2. 期间无其他 SW 活动（如 chrome.alarms、其他 Port 消息）
3. 30 秒后 SW 被休眠
4. Port.onDisconnect 在 CS 端触发

### 缓解措施

**方案 A: Port 心跳保活（主方案）**
```typescript
// background/port-keepalive.ts
const HEARTBEAT_INTERVAL = 25_000; // 25 秒，留 5 秒余量

export function attachKeepalive(port: chrome.runtime.Port): void {
  const timer = setInterval(() => {
    try {
      port.postMessage({ type: 'ping' });
    } catch {
      clearInterval(timer);
    }
  }, HEARTBEAT_INTERVAL);
  port.onDisconnect.addListener(() => clearInterval(timer));
}
```

**方案 B: chrome.alarms 兜底（备用）**
```typescript
// 流式响应期间设置 alarm
chrome.alarms.create('keepalive', { periodInMinutes: 0.4 }); // 24 秒
chrome.alarms.onAlarm.addListener((alarm) => {
  if (alarm.name === 'keepalive') {
    // alarm 触发会唤醒 SW
  }
});
// 流结束后清除
chrome.alarms.clear('keepalive');
```

### 验收标准
- [ ] 流式响应持续超过 30 秒时，Port 连接不中断
- [ ] CS 端每 25 秒收到 ping 并回复 pong
- [ ] SW 不会在流式传输期间被休眠
- [ ] 模拟测试：发送一个需要 60 秒响应的长消息，验证连接稳定

## R2: host_permissions 缺失导致 API 调用失败

### 风险描述
当前 `manifest.json` 仅声明了 3 个 API 域名，但项目支持 9 个 Provider。缺失的 6 个域名会导致 `fetch` 请求被 Chrome 阻止，返回 CORS 错误或 net::ERR_FAILED。

### 影响范围
- L0: manifest.json 配置
- L4: 所有 Provider 的网络请求
- L1: Bilibili API（已有权限）

### 严重程度: 🔴 高

### 触发条件
用户选择未声明 host_permissions 的 Provider（如 DeepSeek、OpenRouter 等）并发送消息时，SW 中的 `fetch` 调用失败。

### 缓解措施

补全 `manifest.json` 的 `host_permissions`：
```json
{
  "host_permissions": [
    "*://*.bilibili.com/*",
    "https://api.openai.com/*",
    "https://api.anthropic.com/*",
    "https://generativelanguage.googleapis.com/*",
    "https://api.deepseek.com/*",
    "https://api.x.ai/*",
    "https://dashscope.aliyuncs.com/*",
    "https://api.lingyiwanwu.com/*",
    "https://openrouter.ai/*",
    "https://api.cloudflare.com/*"
  ]
}
```

### 验收标准
- [ ] `manifest.json` 包含全部 9 个 Provider 的 API 域名 + Bilibili 域名
- [ ] 每个 Provider 至少完成一次成功的 API 调用测试
- [ ] Chrome 控制台无 CORS 或 net::ERR_FAILED 错误

## R3: 流式响应丢块

### 风险描述
Chrome Port 消息虽然在大多数情况下有序，但在高频发送（如流式响应每秒数十个 chunk）时可能出现乱序或丢失。若 CS 端未正确处理，会导致显示的文本不完整或错乱。

### 影响范围
- L3: 通信管道的分块/去块机制
- L6: UI 渲染的文本完整性

### 严重程度: 🟡 中

### 触发条件
1. LLM 流式响应速度极快（如每秒 50+ chunk）
2. SW 端 `port.postMessage` 调用过于密集
3. Chrome 内部消息队列排队导致乱序或丢弃

### 缓解措施

**序列号机制 + 重组缓冲**:
```typescript
// CS 端 ChunkReassembler
class ChunkReassembler {
  private expectedSeq = 0;
  private buffer = new Map<number, string>();
  private static MAX_BUFFER = 50;

  push(chunk: { seq: number; text: string }): string {
    this.buffer.set(chunk.seq, chunk.text);
    let out = '';
    while (this.buffer.has(this.expectedSeq)) {
      out += this.buffer.get(this.expectedSeq);
      this.buffer.delete(this.expectedSeq);
      this.expectedSeq++;
    }
    if (this.buffer.size > ChunkReassembler.MAX_BUFFER) {
      throw new ChunkGapError(this.expectedSeq);
    }
    return out;
  }
}
```

**SW 端批量发送（降低消息频率）**:
```typescript
// 累积 16ms 的文本后一次性发送，减少 Port 消息数量
class BufferedChunker {
  private buffer = '';
  private timer: ReturnType<typeof setTimeout> | null = null;
  private seq = 0;

  push(text: string, port: chrome.runtime.Port): void {
    this.buffer += text;
    if (!this.timer) {
      this.timer = setTimeout(() => this.flush(port), 16);
    }
  }

  flush(port: chrome.runtime.Port): void {
    if (this.buffer) {
      port.postMessage({ type: 'chunk', payload: { seq: this.seq++, text: this.buffer } });
      this.buffer = '';
    }
    this.timer = null;
  }
}
```

### 验收标准
- [ ] 每个 chunk 携带递增的 seq 序列号
- [ ] CS 端能正确重组乱序到达的 chunk
- [ ] 检测到丢块（缓冲超限）时触发 resend-request
- [ ] SW 端能处理 resend-request 并从指定 seq 重传
- [ ] 压测：模拟 100 个 chunk 快速发送，CS 端文本完整无损

## R4: 跨域请求被阻止

### 风险描述
即使声明了 `host_permissions`，某些 LLM API 或 Bilibili API 可能因 CORS 策略而在特定上下文（如 Content Script）中请求失败。Service Worker 上下文虽不受同源策略限制，但需验证。

### 影响范围
- L4: Provider 网络请求
- L1: Bilibili API 请求

### 严重程度: 🟡 中

### 触发条件
1. 在 CS 上下文中直接调用 LLM API（架构不允许，但需防范）
2. Bilibili API 启用更严格的 CORS 检查
3. 某些 Provider API 返回的 CORS 头不完整

### 缓解措施

**架构约束: 所有 LLM API 调用必须在 SW 中执行**（SW 不受同源策略限制）。

```typescript
// 架构约束: CS 永远不直接 fetch LLM API
// 错误: CS 直接调用 OpenAI
// fetch('https://api.openai.com/v1/chat/completions', ...)

// 正确: CS 通过 Port 请求 SW 调用
port.postMessage({ type: 'chat-request', payload: request });
```

**Bilibili API 的 credentials 处理**:
```typescript
// SW 中调用 Bilibili API 时带上 cookie
const res = await fetch(url, {
  credentials: 'include',  // 携带 B 站登录 cookie
  headers: { 'Referer': 'https://www.bilibili.com' },
});
```

### 验收标准
- [ ] 所有 LLM API 调用均在 SW 中执行
- [ ] CS 代码中无直接 `fetch('https://api.openai.com')` 等调用
- [ ] Bilibili API 调用携带正确 credentials 和 Referer
- [ ] 9 个 Provider 在 SW 中均能成功调用

## R5: API Key 泄露风险

### 风险描述
API Key 若以明文存储在 `chrome.storage` 中，可能被其他扩展或恶意脚本读取。用户配置的 9 个 Provider 的 API Key 均属敏感信息，泄露后可能被盗用产生费用。

### 影响范围
- L7: 持久化层（存储）
- L8: 设置界面（输入）

### 严重程度: 🔴 高

### 触发条件
1. API Key 明文存储在 `chrome.storage.local`
2. 恶意扩展通过 `chrome.storage.local.get` 读取（同扩展 ID 限制下不易，但仍有风险）
3. 扩展源码被反编译，硬编码的 Key 泄露

### 缓解措施

**方案: Web Crypto API 加密存储**:
```typescript
// storage/crypto.ts
const ENCRYPTION_KEY_NAME = 'bili-encryption-key';

async function getEncryptionKey(): Promise<CryptoKey> {
  // 从 chrome.storage 中取已存储的 key
  const stored = await chrome.storage.local.get(ENCRYPTION_KEY_NAME);
  if (stored[ENCRYPTION_KEY_NAME]) {
    return crypto.subtle.importKey(
      'raw',
      new Uint8Array(stored[ENCRYPTION_KEY_NAME]),
      { name: 'AES-GCM' },
      false,
      ['encrypt', 'decrypt']
    );
  }
  // 首次使用: 生成随机 key
  const key = await crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, true, ['encrypt', 'decrypt']);
  const raw = await crypto.subtle.exportKey('raw', key);
  await chrome.storage.local.set({ [ENCRYPTION_KEY_NAME]: Array.from(new Uint8Array(raw)) });
  return key;
}

export async function encryptApiKey(plaintext: string): Promise<{ ciphertext: string; iv: string }> {
  const key = await getEncryptionKey();
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const encoded = new TextEncoder().encode(plaintext);
  const ciphertext = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, encoded);
  return {
    ciphertext: btoa(String.fromCharCode(...new Uint8Array(ciphertext))),
    iv: btoa(String.fromCharCode(...iv)),
  };
}
```

### 验收标准
- [ ] API Key 存储前经过 AES-256-GCM 加密
- [ ] chrome.storage 中不存在明文 API Key
- [ ] 每个加密条目使用独立 IV
- [ ] 设置界面输入框 type="password"
- [ ] API Key 不会出现在日志或 console.log 中

## R6: Vercel AI SDK 在 SW 环境兼容性

### 风险描述
Vercel AI SDK 主要面向 Node.js 和浏览器环境设计，Service Worker 是无 DOM 的特殊环境。SDK 内部若依赖了 `window`、`document` 或某些 Node.js API（如 `Buffer`、`stream`），会在 SW 中报错。

### 影响范围
- L4: AI Provider 抽象层
- 间接影响 L2-SW: 整个 SW 运行

### 严重程度: 🟡 中

### 触发条件
1. SW 中调用 `streamText()` 时 SDK 内部访问 `window` 或 `document`
2. SDK 使用 `Buffer.from()` 处理二进制（SW 无 Buffer）
3. SDK 使用 Node.js 的 `stream.Readable`（SW 使用 Web Streams）

### 缓解措施

**M1 阶段优先验证**: 在正式开发前，写一个最小 SW 脚本调用 `streamText` 验证兼容性。

```typescript
// 兼容性验证脚本 (M1 第一个任务)
import { streamText } from 'ai';
import { createOpenAI } from '@ai-sdk/openai';

const openai = createOpenAI({ apiKey: 'test-key' });
try {
  const result = streamText({
    model: openai('gpt-4o-mini'),
    messages: [{ role: 'user', content: 'hi' }],
  });
  for await (const chunk of result.textStream) {
    // 若执行到这里，说明 SDK 在 SW 中可用
    break;
  }
} catch (err) {
  console.error('AI SDK SW 兼容性失败:', err);
}
```

**Polyfill 预案**:
```typescript
// 若需要 Buffer polyfill
import { Buffer } from 'buffer';
if (typeof (self as any).Buffer === 'undefined') {
  (self as any).Buffer = Buffer;
}
```

### 验收标准
- [ ] M1 阶段第一步完成 SW 兼容性验证
- [ ] streamText() 在 SW 中能正常返回流
- [ ] 无 "window is not defined" / "Buffer is not defined" 错误
- [ ] 流式迭代器 for await...of 正常工作

## R7: Chrome 扩展 CSP 限制

### 风险描述
MV3 的 Content Security Policy 禁止 `eval()`、内联脚本、动态导入远程模块。若 Vercel AI SDK 或其依赖内部使用了这些特性，会被 CSP 阻止。

### 影响范围
- L0: 构建配置
- L6: UI 渲染（若有 eval）

### 严重程度: 🟡 中

### 触发条件
1. SDK 内部使用 `new Function()` 或 `eval()`
2. React 组件使用内联样式或内联事件
3. 动态 `import()` 远程模块

### 缓解措施

**manifest.json 显式声明 CSP**（MV3 默认严格）:
```json
{
  "content_security_policy": {
    "extension_pages": "script-src 'self'; object-src 'self'"
  }
}
```

**避免内联样式**: 使用 CSS 文件或 CSS-in-JS 库（如 vanilla-extract）。
**验证 SDK 依赖**: 使用 `vite build` 后检查产物无 `eval()`。

### 验收标准
- [ ] Chrome 控制台无 CSP 违规错误
- [ ] 构建产物中无 `eval()` 调用
- [ ] React 组件无内联事件处理器（如 `onClick="..."`）

## R8: 对话上下文超长导致 Token 溢出

### 风险描述
随着对话轮数增加，messages 数组的 token 总量可能超过模型的上下文窗口（如 GPT-4o 为 128K，Claude 为 200K）。超长会导致 API 返回 400 错误或被截断。

### 影响范围
- L4: Provider 调用
- L7: 历史存储

### 严重程度: 🟡 中

### 触发条件
1. 单次对话超过 20 轮
2. 工具调用结果包含大量数据（如视频列表）
3. 用户粘贴长文本

### 缓解措施

**消息截断策略**:
```typescript
// 保留 system + 最近 N 轮对话
function truncateMessages(messages: Message[], maxTokens = 8000): Message[] {
  const system = messages.filter(m => m.role === 'system');
  const conversation = messages.filter(m => m.role !== 'system');
  // 从后往前累加，直到接近上限
  const kept: Message[] = [];
  let tokenCount = 0;
  for (let i = conversation.length - 1; i >= 0; i--) {
    const msgTokens = estimateTokens(conversation[i].content);
    if (tokenCount + msgTokens > maxTokens) break;
    kept.unshift(conversation[i]);
    tokenCount += msgTokens;
  }
  return [...system, ...kept];
}
```

### 验收标准
- [ ] 发送前自动截断超长对话
- [ ] Token 估算误差 < 20%
- [ ] 截断后保留 system prompt + 最近对话

## R9: Bilibili API 反爬限制

### 风险描述
Bilibili 对高频 API 请求有反爬限制。若用户频繁触发搜索工具，可能被临时封禁 IP 或要求验证码。

### 影响范围
- L1: Bilibili API 客户端
- L5: 工具执行

### 严重程度: 🟡 中

### 触发条件
1. 短时间内多次调用 searchBilibiliVideos
2. 未携带有效 cookie（未登录状态）

### 缓解措施

**请求限流 + 重试**:
```typescript
class BilibiliClient {
  private lastSearchAt = 0;
  private static MIN_INTERVAL = 1000; // 最小 1 秒间隔

  async searchVideos(keyword: string): Promise<SearchResult> {
    const elapsed = Date.now() - this.lastSearchAt;
    if (elapsed < BilibiliClient.MIN_INTERVAL) {
      await sleep(BilibiliClient.MIN_INTERVAL - elapsed);
    }
    this.lastSearchAt = Date.now();
    // ... fetch
  }
}
```

### 验收标准
- [ ] 连续搜索请求间隔 >= 1 秒
- [ ] 收到 412（反爬）时自动等待并重试
- [ ] 重试 3 次仍失败时返回友好错误

## R10: 流式响应 UI 渲染性能瓶颈

### 风险描述
高频 chunk 到达时若每次都触发 React 重渲染，可能导致 UI 卡顿，尤其在长文本输出时。

### 影响范围
- L6: Chat UI

### 严重程度: 🟢 低

### 缓解措施
使用 `requestAnimationFrame` 批量更新，合并 16ms 内的多个 chunk。

### 验收标准
- [ ] 流式输出时 FPS >= 30
- [ ] 消息超过 1000 字时无明显卡顿

## R11: Shadow DOM 样式隔离与全局样式冲突

### 风险描述
Content Script 注入的 UI 使用 Shadow DOM 隔离，但 B 站页面的全局样式可能通过 `inherit` 影响 Shadow DOM 内的元素。

### 影响范围
- L6: Chat UI

### 严重程度: 🟢 低

### 缓解措施
Shadow DOM 内使用 CSS Reset，所有样式显式声明。

### 验收标准
- [ ] Shadow DOM 内 UI 不受 B 站页面样式影响
- [ ] 所有 CSS 属性显式设置

## R12: 多 Provider 模型能力差异导致工具调用失败

### 风险描述
9 个 Provider 的模型对 Tool Calling 的支持程度不同。某些模型（如 Cloudflare 的 llama）可能不完全支持 Function Calling，导致工具调用失败或参数解析错误。

### 影响范围
- L4: Provider 抽象
- L5: 工具链

### 严重程度: 🟡 中

### 缓解措施

**Provider 能力声明**:
```typescript
interface ProviderCapabilities {
  supportsToolCalling: boolean;
  supportsStreaming: boolean;
  maxContextTokens: number;
}

const CAPABILITIES: Record<ProviderId, ProviderCapabilities> = {
  openai: { supportsToolCalling: true, supportsStreaming: true, maxContextTokens: 128000 },
  anthropic: { supportsToolCalling: true, supportsStreaming: true, maxContextTokens: 200000 },
  cloudflare: { supportsToolCalling: false, supportsStreaming: true, maxContextTokens: 8000 },
  // ...
};
```

**降级策略**: 不支持 Tool Calling 的模型，禁用工具并提示用户。

### 验收标准
- [ ] 每个 Provider 声明能力支持情况
- [ ] 不支持工具的模型在 UI 中禁用工具选项
- [ ] 工具调用失败时有降级处理

  R4 (跨域阻止)       ─── 架构约束

  R7 (CSP 限制)       ─── 构建验证

  R8 (Token 溢出)     ─── 长对话
  R9 (B 站反爬)       ─── 工具稳定性
  R12 (模型差异)       ─── 多 Provider

优先级 P3（M4-M5 优化）:
  R10 (UI 性能)       ─── 体验优化
  R11 (样式隔离)       ─── 视觉一致性
