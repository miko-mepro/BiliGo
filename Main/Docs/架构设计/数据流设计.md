# BiliGo 数据流设计

## 文档概述

本文档描述 BiliGo 中数据在各层之间流动的完整路径，包括：用户输入到 UI 渲染的端到端数据流、Port 消息序列图、ChatState 状态机、流式分块传输机制、错误处理流程以及工具调用生命周期。

## ChatState 状态机

ChatState 是 Content Script 端维护的聊天状态，驱动 UI 渲染。

### 状态定义

```typescript
type ChatState =
  | { status: 'idle' }                              // 空闲，等待用户输入
  | { status: 'sending'; request: ChatRequest }     // 请求已发送，等待 SW 响应
  | { status: 'streaming'; seq: number; text: string }  // 正在接收流式响应
  | { status: 'tool-calling'; toolName: string; toolCallId: string }  // 工具调用中
  | { status: 'done'; finalText: string }           // 完成
  | { status: 'error'; code: string; message: string };  // 错误
```

### 状态转换图

```
                        ┌─────────┐
                        │  idle   │<──────────────────────────┐
                        └────┬─────┘                            │
                             │ 用户发送消息                      │
                             ▼                                  │
                        ┌─────────┐                            │
                        │ sending │                            │
                        └────┬─────┘                            │
                             │ 收到第一个 chunk                  │
                             ▼                                  │
              ┌──────────────────────────┐                    │
              │       streaming          │                    │
              │  (seq 持续递增)           │                    │
              └─────┬──────────┬─────────┘                    │
                    │          │                              │
       收到 tool-call │          │ 收到 done                     │
                    ▼          ▼                              │
         ┌──────────────┐  ┌─────────┐                        │
         │ tool-calling │  │  done   │────────────────────────┘
         └──────┬───────┘  └─────────┘   (用户发送下一条消息)
                │ 收到 tool-result          │
                │ + 新的 chunk               │
                ▼                          │
         回到 streaming ─────────────────────┘
                │
                │ 收到 error
                ▼
         ┌──────────────┐
         │    error     │──> (用户重试) ──> idle
         └──────────────┘
```

### 状态转换触发规则

| 当前状态 | 触发事件 | 目标状态 | 副作用 |
|---------|---------|---------|--------|
| idle | 用户点击发送 | sending | 构造 ChatRequest 并 postMessage |
| sending | 收到第一个 chunk | streaming | 初始化 seq=0，显示打字指示器 |
| streaming | 收到 chunk (seq 匹配) | streaming | 追加文本到当前消息 |
| streaming | 收到 chunk (seq 不匹配) | streaming | 缓存乱序块，等待补齐 |
| streaming | 收到 tool-call-start | tool-calling | 显示"正在搜索..." |
| tool-calling | 收到 tool-call-result | streaming | 渲染视频卡片，重置 seq |
| streaming | 收到 done | done | 标记消息完成，停止打字动画 |
| * | 收到 error | error | 显示错误提示 |
| error | 用户点击重试 | sending | 重新发送请求 |
| done | 用户发送新消息 | sending | 开启新一轮对话 |

## 流式响应分块传输机制

### 为什么需要分块？

1. **Port 消息有大小限制**: 单条消息不宜过大，需将长文本切片
2. **乱序风险**: Chrome Port 不保证严格顺序，需 seq 序号重组
3. **丢块检测**: 通过 seq 跳变可检测丢块并触发重传

### 分块格式

```typescript
interface ChunkPayload {
  seq: number;       // 序列号，从 0 递增
  text: string;      // 文本增量（可能是一个或多个字符）
}
```

### 传输流程

```
SW 端 (分块器)                    Port 通道                    CS 端 (去块器)
─────────────                    ──────────                   ─────────────
text-delta "你" ──> seq=0  ──>  chunk{seq:0,text:"你"}  ──>  buffer[0]="你"
text-delta "好" ──> seq=1  ──>  chunk{seq:1,text:"好"}  ──>  buffer[1]="好"
                                                                  │
                                                    顺序检查: 有 seq=0
                                                    输出: "你", expectedSeq=1
                                                    顺序检查: 有 seq=1
                                                    输出: "好", expectedSeq=2
```

### 乱序处理

```
SW 发送顺序: seq=0, seq=1, seq=2
Port 实际到达: seq=0, seq=2, seq=1  (seq=1 延迟)

CS 端 buffer 状态:
  收到 seq=0: buffer={0:"你"}, 输出"你", expectedSeq=1
  收到 seq=2: buffer={0:..,2:"好"}, 无法输出(缺 seq=1), 缓存
  收到 seq=1: buffer={0:..,1:"世",2:..}
              顺序补齐: 输出"世"(seq=1), 输出"好"(seq=2)
              最终输出: "世好"
```

### 丢块检测与恢复

```typescript
// CS 端检测丢块
class ChunkReassembler {
  push(chunk: { seq: number; text: string }): string {
    this.buffer.set(chunk.seq, chunk.text);
    let out = '';
    while (this.buffer.has(this.expectedSeq)) {
      out += this.buffer.get(this.expectedSeq);
      this.buffer.delete(this.expectedSeq);
      this.expectedSeq++;
    }
    // 缓冲积压超过阈值，判定为丢块
    if (this.buffer.size > MAX_BUFFER) {
      throw new ChunkGapError(this.expectedSeq);
    }
    return out;
  }
}

// 丢块处理：请求 SW 从指定 seq 重传
function handleChunkGap(error: ChunkGapError) {
  port.postMessage({ type: 'resend-request', payload: { fromSeq: error.expectedSeq } });
}
```

## 错误处理流程

### 错误分类与处理矩阵

| 错误类型 | 来源 | 严重度 | CS 表现 | 恢复策略 |
|---------|------|--------|--------|---------|
| 网络错误 | fetch 失败 / 断网 | 高 | "网络连接失败" | 提供重试按钮 |
| API Key 无效 | LLM 返回 401 | 高 | "API Key 无效" | 跳转设置页 |
| API 限流 | LLM 返回 429 | 中 | "请求过于频繁" | 指数退避重试 |
| 模型不存在 | LLM 返回 404 | 中 | "模型不可用" | 提示选择其他模型 |
| 超时 | 30s 无响应 | 中 | "请求超时" | 自动重试一次 |
| Port 断连 | SW 休眠 | 高 | 连接断开 | 自动重连 + 恢复对话 |
| Bilibili API 错误 | B 站接口异常 | 低 | "搜索失败" | 工具内重试 |
| 流式丢块 | seq 跳变 | 中 | 文本不完整 | 请求重传 |

### 超时处理

```typescript
// CS 端：请求超时监控
const REQUEST_TIMEOUT = 30_000;

function sendWithTimeout(request: ChatRequest): void {
  const timer = setTimeout(() => {
    if (chatStore.state.status === 'sending' || chatStore.state.status === 'streaming') {
      chatStore.transition({ status: 'error', code: 'TIMEOUT', message: '请求超时' });
      // 可选: 通知 SW 取消请求
      port.postMessage({ type: 'cancel', payload: { signal: request.signal } });
    }
  }, REQUEST_TIMEOUT);

  // 收到第一个 chunk 或 done/error 时清除定时器
  chatStore.onTransition((state) => {
    if (state.status !== 'sending') clearTimeout(timer);
  });
}
```

### 多轮工具调用

LLM 可能在一次对话中多次调用工具：

```
用户: "搜索 Python 教程，然后告诉我第一个视频的详情"

轮次 1:
  LLM -> tool-call: searchBilibiliVideos(keyword="Python 教程")
  SW 执行 -> 返回视频列表
  LLM 获得列表

轮次 2:
  LLM -> tool-call: getVideoInfo(bvid="BV1xxx")  (取第一个视频)
  SW 执行 -> 返回视频详情
  LLM 获得详情

轮次 3:
  LLM -> 流式文本总结
  CS 渲染最终回答
```

## 数据完整性保障

### Port 消息确认机制

为保证关键消息可靠到达，对 `chat-request` 和 `done` 实现确认：

```
CS                                SW
 │  chat-request {id: msg-001}     │
 │────────────────────────────────>│
 │                                 │
 │  ack {id: msg-001}              │
 │<────────────────────────────────│
 │                                 │
 │  (未收到 ack, 3s 后重发)         │
 │  chat-request {id: msg-001}     │
 │────────────────────────────────>│
```

### 幂等性设计

- **chat-request**: 携带唯一 `requestId`，SW 侧去重，避免重复执行
- **chunk**: 依赖 seq 重组，重复的 seq 会被自然忽略
- **tool-call**: 每次调用有唯一 `toolCallId`，重复 ID 不执行

## 总结

BiliGo 的数据流设计围绕三条核心通道：

1. **用户输入 → SW → LLM API**: 请求通道，通过 Port 传输 ChatRequest
2. **LLM API → SW → CS UI**: 响应通道，通过分块流式传输
3. **SW ↔ Bilibili API**: 工具调用通道，SW 内部直接 fetch

这三条通道通过 ChatState 状态机协调，确保 UI 始终反映正确的系统状态。
